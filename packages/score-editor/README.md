# @neta-art/score-editor

A browser score editor for song projects. A host app mounts it onto an element, maps its own theme through CSS variables, and receives one-time messages through a callback. No framework is exposed.

Work in progress: today the package shows a song project's score as an arrangement: a ruler with bar numbers, section bands, key and meter marks, a chord track, and one piano-roll track per voice, with zoom and scrolling. The first edits are in: select a note (by pointer or by keyboard), turn it into a rest with the Delete key or the Delete button, undo and redo, drop an insertion point on the grid and move it with the keys, place, change and remove a chord on the chord track, choose bars in the ruler to insert or delete them, change one section's meter, and repair a score whose text stops early. Selected notes move in time and pitch and change length by dragging them or their edges, or with the arrow keys and Shift, on a grid that the toolbar's Grid menu sets (1/4, 1/8, 1/16 and their dotted steps, and 1/32 where the score allows it). A section band opens a menu to rename, move, duplicate or delete the section, or start a new one at a bar. The score also has two more views, chosen by a switch in the toolbar's always-visible bar: the score on a staff, and the score text, which a person can edit as text. The rest of editing arrives in later versions.

## Mount

```ts
import { createDialectRegistry, mount } from "@neta-art/score-editor";
import { song2Dialect } from "@neta-art/score-dialect-song2";

const editor = mount(element, {
  language: "en", // "zh" or "en"
  project, // a SongProject: the score text and the model ID are read
  dialects: createDialectRegistry([song2Dialect]), // the formats this editor can read
  drafts: store, // optional: a DraftStore; edits are kept as a draft of this project (see Drafts)
  tools: [myTool], // optional: the host's tools, beside the built-in note tools (see The Tools panel)
  source: { kind: "generated" }, // optional; a scoreFile source saves explicitly (see Score files)
  onSaveAs: (text) => saveNewFile(text), // optional: adds Save as to a generated score
  onUnsavedChange: (unsaved) => guardClose(unsaved), // optional: a score file's unsaved state
  requiredInputs: ["style"], // optional: blocks the handoff until these project fields are filled
  title: "My Song", // optional: the work's title in the handoff instruction
  onHandoff: (handoff) => openChatInput(handoff), // optional: adds the handoff button (see Change log and handoff)

  notify: (notice) => showToast(notice.message), // already in the current language; `notice.code` is one of `NOTICE_CODES`
});

editor.update({ project: nextProject }); // only the given keys change; language-only changes keep the view
editor.hasUnsavedChanges(); // false for a generated score
editor.destroy(); // removes every listener, node and stylesheet it added
```

- The toolbar ends with a switch of three views of the one project: the arrangement, the staff (drawn by abcjs, read-only) and the score text. Text that reads becomes the project's score as one undo step per burst of typing (after a pause of 600 ms, or when the box loses the focus), and the other views follow. Text that cannot be read stays in the box with its problems listed by line, the project keeps the last readable score, and a notice above the arrangement and the staff says they are behind the text. The switch works while the editor is read-only; the text box is then read-only too.
- A score that cannot be read shows the dialect's diagnostics in the interface language instead of the view. A project whose model has no dialect in the registry shows one short sentence.
- `editable` (default `true`) says whether the user may change the score. While it is true the toolbar has undo, redo, Delete, the pencil (B), the Select and Grid menus (Select all, Invert selection, Clear selection; the grid step), a Bars menu and a meter control, a click or tap selects a note or drops the insertion point, the pencil makes a single click draw or delete and shows a short "Draw" word in each editable voice track head while it is on, a double click or double tap draws or deletes with the pencil off, Shift with a click or tap, a box on empty space and a touch and hold pick several notes, Ctrl or Cmd with C, V and D copy, paste and duplicate inside the session, Alt with a drag copies, Tab reaches the notes, and every key and pointer gesture is in [the key map in DESIGN.md](../../DESIGN.md#moving-and-resizing). While it is false none of that exists: no editing control, no selection frame, no insertion point, and the keys do nothing; the toolbar shows a read-only badge instead. `update({ editable })` switches it without remounting, and a selection made before comes back with it.
- A command the user's keys caused that the score would not take (the dialect refuses to write the result) changes nothing and reaches `notify` once as `{ code: "command-refused", level: "warning", message }`, in the interface language.
- `abcjs` is the package's one runtime dependency. It is loaded with `import()` when a staff view is first mounted, never when the package is imported, so a host that does not show the staff does not fetch it. The drawing sits in a shadow root of its own inside the part; see [DESIGN.md](../../DESIGN.md#staff-view).
- Importing the package runs nothing that touches the DOM, so a server render can import it. `mount` and the view parts' mount functions need a browser and throw a clear error elsewhere; call them from client-side code. `createEditingSession` needs none.
- The headless layer is dialect-agnostic: `applyScoreCommand(dialect, text, command)` and `applyProjectCommand(dialect, project, command)` apply one command to the shared score model, write it with the dialect, and run `dialect.check`. A refusal returns the input unchanged and one diagnostic. The meter rule helpers `meterAllowed(meter, rule)`, `meterChoices(constraints)` and `COMMON_METERS` read the same `constraints.meter` the commands enforce, so a host's own meter control can offer only what the dialect accepts.
- Styles: every class is prefixed `sce-`. The host maps its theme onto `--sce-color-bg`, `--sce-color-text`, `--sce-color-accent` and a few more; unmapped colours fall back to neutral defaults derived from the mapped ones. The full list is in [DESIGN.md](../../DESIGN.md).
- A host whose own CSS uses ID selectors or `!important` on plain elements should mount the editor inside a shadow root. See [docs/spike.md](../../docs/spike.md).
- The package assumes a browser with native popovers, `:has()` and `light-dark()`. Only Chromium has been run so far.
- `drafts` (optional) is the host's `DraftStore`. With it, and while the editor is editable, `mount` makes one draft keeper for the project and keeps the user's edits under `project.sourceKey`; the toolbar gets a Restore original button and a draft that another window changed first gets a conflict banner with one Choose button. Without it, or while the editor is read only, nothing is kept and the store is never called. What the editor shows and does is under [Drafts](#drafts).
- `source` (optional) says where the score came from. Absent or `{ kind: "generated" }` is a generated score, with drafts as before. `{ kind: "scoreFile", name, version, save, read }` is a document: Save is explicit, `drafts` is ignored entirely, Restore original goes back to the last saved version, a conflict offers overwrite or load theirs, and the change log compares with the last saved version. `onSaveAs` adds Save as to a generated score; `onUnsavedChange` and `editor.hasUnsavedChanges()` expose a file's unsaved state; `requiredInputs` names the model inputs that must be filled before a handoff. See [Score files, save and save-as](#score-files-save-and-save-as).

## Commands

`applyScoreCommand` takes one `ScoreCommand` and changes the score text; it refuses a `ProjectCommand`. `applyProjectCommand` takes a `ScoreCommand` or a `ProjectCommand`, the one-word name of the second union, for edits to the project itself. A refusal is what the headless layer above describes; a notice is the third, non-failure diagnostic class, and it comes with the changed project. `isNoticeDiagnostic` tells it from a refusal. A successful result also carries `rewrittenBars`, the 1-based bars the command rewrote, omitted when none was; a tie change names the bar on each side of the barline, a tempo change names none, and `session.rewrittenBars` keeps the last edit's list through undo and redo.

A cut score's `Truncation` has an optional `unfinishedChord: true` when the cut ends inside an unfinished chord string (RULES.md C8 and X4). It is absent otherwise, and it is why `hasChords` stays true for such a tail; removing all chords drops both the flag and the tail bytes.

Keys and chord roots in `constraints` share one spelling: a letter A-G, then `#`, `##`, `b` or `bb`, and `m` for a minor key; a chord name is a root, one quality from the vocabulary, and optionally `/` and a bass root.

Score commands, in the order `ScoreCommand` lists them:

- `toRest` (`noteId`): turns a note and its whole tie chain into rests. Refuses with `note-not-found` or `not-a-note`.
- `toRests` (`noteIds`): `toRest` for several notes as one edit. Every id is checked first, so the first id that names no note, or a rest, refuses the whole command; otherwise all of them become rests, the score is written once and `check` runs once. Refuses with `note-not-found` or `not-a-note`.
- `setChord` (`noteId`, `name`): sets the chord on a note or rest whose voice allows chords, replacing every chord that starts at the note; an empty `name` removes it. Removing the last chord also removes an unfinished chord string at the end of the text, see [RULES.md C8](../score-dialect-song2/RULES.md). Refuses with `note-not-found`, `chord-voice` or `chord-vocabulary`.
- `insertBar` (`bar`, counted from 0): inserts a bar of rests at that index, before the bar now there or after the last one. Refuses with `bar-out-of-range`, `truncated-tail` or `tie-across-bar`.
- `deleteBars` (`from`, counted from 0, and `count`): deletes whole bars. Refuses with `bar-out-of-range`, `last-bar` or `truncated-tail`.
- `setSectionMeter` (`section`, `meter`): sets the meter of one section. Refuses with `section-out-of-range`, `meter-not-allowed`, `meter-does-not-fit`, or `truncated-tail` when the section reaches the cut bar or the end of a voice that stops early (a short or missing `Ins` block in a cut tail).
- `fillTruncatedBar` and `deleteTruncatedBar`: the two repairs that leave a score with no cut. `fillTruncatedBar` pads every short voice to the end; `deleteTruncatedBar` removes the incomplete measure when no other voice keeps material in it. Both refuse with `no-truncation` or `no-incomplete-bar`; `deleteTruncatedBar` also with `cut-in-complete-bar`, `last-bar` or `cut-other-voice-short`, which says another voice is short of whole bars and to fill the cut bar instead.
- `transpose`: moves every note, every chord root and bass, the header `K:`, every body `K:` line and every inline `[K:…]` by the same number of semitones. The new keys are the declared spellings with the fewest accidentals; a transposition by 0 changes nothing and returns the text as it is. A note that would leave MIDI 0-127 refuses the whole command. Refuses with `semitones-not-integer`, `pitch-out-of-range`, `key-unavailable` or `chord-invalid`.
- `setKey`: moves the notes and chords to the chosen key, like `transpose` by the shortest interval between the two tonics, and forces the chosen key's spelling. With `from`, only the score from that key-change position on moves; the header and earlier key changes stay. Refuses with `key-not-allowed` or `key-change-not-found`, and like `transpose` otherwise.
- `setTempo`: writes `Q:1/4=<bpm>` from the dialect's tempo range and changes no pitch. Refuses with `tempo-out-of-range`.
- `removeChords`: removes every chord from the score. It is the one-step fix for a `melody` project that carries chords.
- `deleteSection` (`section`, counted from 0): deletes the section's bars and marker. Deleting the unnamed section is allowed, and so is deleting the last section when it holds the cut tail; the result is then a complete score. Refuses with `section-out-of-range`, `truncated-tail` for a cut outside the last section, or `last-bar` when no bars would remain.
- `duplicateSection` (`section`): puts a copy of the section directly after it. The copy keeps the section's name, because the copy is the same musical material and the same label a lyric line binds to; rename it if it should read differently. A copy also keeps a tie at its end into the following section: in A, A copy, B the boundary A copy→B repeats the original A→B, so keeping it is the original music; only the newly formed boundary at the copy's start clears a tie. Refuses with `section-out-of-range`, `section-unnamed` for the unnamed section, or `truncated-tail` for a section that holds the cut tail.
- `moveSection` (`section`, `direction` = `"earlier"` or `"later"`): swaps the section with its neighbour. A named section cannot move before the unnamed section, which has no marker and can only stand first, and a move that would carry the cut tail out of last place is refused. Refuses with `section-out-of-range`, `section-unnamed`, `section-move-start`, `section-move-end`, `section-before-unnamed` or `truncated-tail`.
- `renameSection` (`section`, `name`): gives an existing section a new name; naming the unnamed section puts a marker at bar 0. `section-name-trailing-space` is refused because T2 trims `% verse ` to `verse`, so such a name would not read back as written. Refuses with `section-out-of-range`, `section-name-empty`, `section-name-blank`, `section-name-line-break` or `section-name-trailing-space`.
- `nameSection` (`bar`, counted from 0, and `name`): starts a named section at that bar. A bar at an existing section start renames that section; any other bar splits the section there, which the writer turns into a group boundary as W11 describes, with the group shape in W3 and W4. Refuses with `bar-out-of-range` or the same name codes as `renameSection`.
- `moveNotes` (`noteIds`, `timeTicks`, `semitones`, `grid`): moves the whole tie chain of every named note as one edit, in time and pitch together. A non-zero time offset puts the start on the nearest line of `grid`, a `Grid` whose `value` is a `GridValue` and whose optional `dotted` makes a step half as long again; a zero time offset leaves the time alone, so a pitch-only move does not snap an off-grid note, and the length is always kept. A placed note keeps one note at a time in its voice: a note whose start it covers is removed, a note it starts inside is shortened to the placed note's start, and every time it leaves becomes a rest without moving later notes. Placed notes are taken in start order; when two land on the same start the later one in that order stays. A result that crosses a bar line is split there and tied. Chords stay at their positions, because the chord track is a track of positions, not of notes; each chord is rebound to the Vocal note or rest now starting there. Refuses with `note-not-found`, `not-a-note`, `offset-not-integer`, `unit-unknown`, `grid-not-allowed`, `pitch-out-of-range`, `note-before-start` or `note-past-end`.
- `resizeNotes` (`noteIds`, `edge` = `"start"` or `"end"`, `timeTicks`, `grid`): moves the named edge of the whole tie chain of every named note to the nearest grid line and leaves the other edge exactly where it is, then applies the overlap, rest, bar-line and chord rules of `moveNotes`. A result shorter than one grid step is refused. Refuses with the codes of `moveNotes` and `note-too-short`.
- `addNote` (`voice`, `start`, `midi`, `grid`): puts one new note of one grid step at the nearest line of `grid` in that voice, under the same one-note-a-time rule. Refuses with `not-a-note` for a voice the score does not have, `pitch-out-of-range`, `offset-not-integer`, `unit-unknown`, `grid-not-allowed`, `note-before-start` or `note-past-end`.
- `pasteNotes` (`notes`, `at`, `grid`): puts copied notes at the insertion tick, keeping the distances between them, each on the grid and under the one-note-a-time rule. `notes` is a `CopiedNote[]`: `{ voice, start, duration, midi }`, a copied tie chain being one note. An empty list changes nothing. Refuses with the codes of `addNote` and `note-too-short`.
- `duplicateNotes` (`noteIds`, `grid`): repeats every named note's whole tie chain directly after the selection, as one edit. The copy starts on the first grid line after the selection's end and obeys the one-note-a-time rule. Refuses with `note-not-found`, `not-a-note`, `unit-unknown`, `grid-not-allowed`, `pitch-out-of-range`, `note-before-start` or `note-past-end`.
- `copyNotes` (`noteIds`, `timeTicks`, `semitones`, `grid`): the Alt-drag. Puts a copy of every named note's whole tie chain by the drag's distance and pitch, on the grid, leaving the originals where they are. Refuses with the codes of `duplicateNotes` and `offset-not-integer`.
- `voiceOctave` (`octaves`: `1`, `-1`, `2` or `-2`): moves only Vocal's pitched notes by that many whole octaves. Ins, the chords and the key timeline do not move, and the notes keep their starts, lengths and ties. The whole command is refused with `voice-octave-range` if any moved note would leave MIDI 0-127. `ApplyScoreResult.report` and `ToolResult.reports` carry `{ kind: "voiceOctave", octaves, medianMidi, singable }`: the lower median of the moved tie chains (null when Vocal has no pitched notes) and whether it is inside the singable range 60-82.
- `instrumentalVersion`: moves Vocal's pitched tie chains into Ins at the same starts and pitches, and leaves Vocal with rests only; Vocal's chords stay at their positions. An existing Ins note that overlaps a moved note gives way: the part before and after the moved note stays, so it is cut short or split, and a note the moved notes cover completely is dropped. When the score has no Ins voice it adds one with the two-voice samples' header line and body block, and fills its bars with rests; it refuses with `unit-unknown` when the score has no written duration unit. `ApplyScoreResult.report` and `ToolResult.reports` carry `{ kind: "instrumentalVersion", moved, shortened, dropped }`, counting tie chains: moved Vocal chains, Ins chains cut short (once each) and Ins chains dropped.

The editor keeps copied notes inside the editing session, not on the system clipboard: Ctrl or Cmd with C takes the selected notes, with V pastes them at the insertion point, and with D repeats the selection right after itself. Alt with a drag copies the selected notes where the pointer lands. The keys are taken only while the session is editable and the focus is not in a text field or a popover, so a host's own text copy and paste still work; pasted text from elsewhere is not read.

- `splitNotes` (`noteIds`, `at`, `grid`), `chopNotes`, `joinNotes`, `legatoNotes`, `reverseNotes`, `flipNotes`, `snapNotesToKey`, `scaleNoteLengths` (`factor` 2 or 0.5), `setNoteLength` (`lengthTicks`) and `fitNotesToRange` (`fromBar`, `toBar`): the commands the built-in note tools build. Every new start and length is snapped to `grid` before it is written, so a value off the grid is rounded onto it, and each voice keeps one note at a time by the `moveNotes` overlap rule. A selected note is found with its whole tie chain, and the result is written once, with rests filled and bar-line ties split. A tick that is not a whole number, a `lengthTicks` that is not a positive whole number, a grid the score cannot write, a bar range outside the score, a note that would end past the score or a result shorter than one grid step is refused with the codes of `moveNotes`, plus `bar-out-of-range` for a range. `splitNotes` with `at: null` changes nothing. `flipNotes` mirrors pitches around the lowest and highest selected, and refuses with `pitch-out-of-range` when a mirror leaves MIDI 0-127; `snapNotesToKey` moves each note to the nearest pitch in the key in force where it starts. The Tools panel passes the session's grid, insertion point and selection bars in the tool context (see [Custom tools](#custom-tools)).

A `Score`'s `unitTicks` is one written duration unit in ticks; it is optional so a 0.1.0-shaped score still type-checks, and a note command refuses with `unit-unknown` when it is absent. A grid step is allowed when it is a whole number of those units and that number can be made from the dialect's `constraints.durations`; so a 1/32 grid, and a dotted value finer than the written `L:` unit, exist only where the score can write them. A note shorter than the grid keeps its length when it moves, and a resize keeps the unmoved edge, so only a line the command moves is guaranteed to be on the grid. A move that would cross the start or end of the score is refused, not clamped, as `transpose` refuses an out-of-range pitch: a refusal leaves the whole score as it was.

Any score command also fails with `write-mismatch`, or with a reading code, when the dialect cannot write the result or read it back the same.

Project commands, the `ProjectCommand` union:

- `setStyle`: sets the style text.
- `setScoreMode`: sets `full` or `melody`.
- `setSeed`: sets a whole-number seed, or `null` to clear it.
- `replaceScoreText` (`text`): replaces the whole score text with another one. A text the dialect reads and checks is taken, and stored the way the dialect writes it; otherwise the command refuses with the dialect's first diagnostic and nothing changes. It is how the text view's typing reaches the project.
- `setLyricLineText` (`line`, `text`): changes one lyric line's text and keeps its phrase unless the phrase no longer fits the score.
- `insertLyricLine` (`line`, `text`, `phrase`): inserts a line at a position in the project's line order, with a phrase or `null` for the unaligned area.
- `deleteLyricLine` (`line`): removes a line.
- `splitLyricLine` (`line`, `offset`, optional `bar`): splits a line at a code-point offset, on a bar or into the unaligned area.
- `mergeLyricLines` (`line`): joins a line with the next stored line.
- `setLyricLinePhrase` (`line`, `phrase`): moves or places a phrase, or sends the line to the unaligned area with `null`.

`applyProjectCommand` also runs the song-project rules. A `setTempo` through it rewrites every BPM written in the style text (`120 BPM`, `120bpm`, `BPM: 120`, `bpm=120`, `BPM 120`, `BPM：120`) and reports the notice `style-no-bpm` when the style has none; a number not next to the word BPM stays as it is. A project in `melody` mode whose score has chords reports the notice `melody-with-chords`; delete the chords or switch back to `full`. `checkProject(dialect, project)` reports that notice for a project as it stands, without changing anything.

## Lyrics on the song project

`SongProject.lyricLines` is optional, so a project built by 0.1.0 still opens. It is a list of `LyricLine`s: `{ text, phrase }`, where `phrase` is `{ firstBar, barCount }` and `null` marks a line in the unaligned area. Only the text and the bar run are stored; syllables, note onsets and whether their counts are equal are computed when asked. A phrase is a run of consecutive bars inside one section. The binding is bar-based because bars are what commands move and sections have no identity beyond their place.

A project without `lyricLines` computes the layout from its legacy `lyrics` text: `lyricLinesOf(project, score)` returns the stored lines, or `layoutLyrics(score, project.lyrics)` when there are none. A `[name]` line matches the first unused section with that name and its lines go one per bar from the section's first bar. Lines before the first label go into the unnamed opening section when the score has one, and into the first section otherwise; a label with no section and a line that does not fit go to the unaligned area. Empty lines are skipped and do not take a bar. A section with no label stays empty. Computing the layout does not write it into the project. A score command that changes the lines or their join stores the layout and rewrites `lyrics`; a command that changes neither writes nothing.

`joinLyrics(score, lines)` writes the text in section order: one `[name]` label before each named section and its lines, no label for the unnamed opening section, and a label for an empty named section. Unaligned lines are left out. `checkProject` reports `lyrics-unaligned` when there are any and `lyrics-too-long` when the joined text is over `LYRICS_MAX_CHARACTERS` (4,000). `lyricCharacterCount` counts Unicode code points, line breaks included.

`lyricSyllables` and `syllableCount` count one per Han character, kana, digit and other letter, with combining marks staying on their base. A Latin word is split by vowel groups (`a e i o u`, and `y` when it is not next to one) and by a `-` written inside it; a word with no vowel group counts one. Spaces, punctuation and symbols are not sung and count nothing. `noteOnsets(score, phrase)` returns the `Vocal` notes in the phrase's bars that are not rests and not tied from the note before. `alignLyricLine(score, line)` returns the syllables, the onsets, whether their counts are equal, and one note per syllable when they are; `alignedLyricLines(lines, score?)` and `unalignedLyricLines(lines, score?)` split a line list by its area. Without a score they treat every non-null phrase as aligned, so pass the score to count a stale phrase as unaligned.

Lyric-line commands are `ProjectCommand`s: `setLyricLineText`, `insertLyricLine`, `deleteLyricLine`, `splitLyricLine`, `mergeLyricLines` and `setLyricLinePhrase`. A `line` names a line by its place in `lyricLinesOf(project, score)`. `setLyricLineText` keeps the line's phrase unless it no longer fits the score; `insertLyricLine` takes text and a phrase or `null`; `deleteLyricLine` removes one; `splitLyricLine` splits at a code-point offset, keeping the bars before an optional bar on the first part and putting the second part on the bar or in the unaligned area; `mergeLyricLines` joins a line with the next stored one; `setLyricLinePhrase` moves a boundary, places an unaligned line or sends a line back with `null`. The stored order is the one `joinLyrics` needs: aligned lines by first bar, then unaligned lines in their stored order.

A phrase is valid only when it is one or more whole consecutive bars inside the score and inside one section. A stored phrase that no longer fits is read as unaligned by `joinLyrics`, `alignLyricLine`, `alignedLyricLines(lines, score)`, `unalignedLyricLines(lines, score)` and `checkProject`, without rewriting the stored line; a lyric command that touches that line keeps it unaligned or gives it a valid phrase. A lyric line's text cannot be empty after trimming, contain a line break or be only a `[label]` line. A merge joins text with one space, or none when both sides of the join are Han or kana, and joins two adjacent phrases in one section; an aligned and an unaligned line keep the aligned phrase, and two unaligned lines stay unaligned. A phrase that would overlap another line's is refused rather than shrinking that line: a host moves a shared boundary with two `setLyricLinePhrase` commands through `applyCommandList`, which applies the list together or not at all. Every refusal has its own code (`lyric-line-out-of-range`, `lyric-phrase-invalid`, `lyric-phrase-overlap`, `lyric-text-invalid`, `lyric-lines-not-mergeable`, `lyric-split-invalid`), and leaves the project as it was.

A score command through `applyProjectCommand` remaps the stored lines, or an old project's computed layout, in one place. A deleted section takes its lines; a copied section copies them; a moved section moves them; a rename keeps them on their bars. A new section marker inside a phrase keeps the line in the section of its first bar, on the bars that remain there, so it never crosses the new marker. A bar inserted before a phrase shifts it and one inserted inside it is spanned; a deleted bar inside a phrase closes the gap. A phrase that loses every bar goes with those bars. The project's `lyrics` becomes the joined text whenever the lines or that join change; a command that changes neither adds no field and leaves `lyrics` as it was. Every result of `applyScoreCommand` is unchanged by this.

## The editing session and view parts

`mount` is one arrangement of smaller public pieces. An **editing session** holds the song project with its undo history, the selection, the insertion point, and the UI state that parts share (zoom, horizontal scroll, language). A **view part** mounts on an element of the host's own layout, binds to one session, and draws from it. Parts of one session zoom and scroll together; each is free to be as wide as the element the host gave it.

```ts
import {
  createDialectRegistry,
  createEditingSession,
  mountChordTrack,
  mountTimeRuler,
  mountToolbar,
  mountVoiceTrack,
  mountZoomControl,
} from "@neta-art/score-editor";

const session = createEditingSession({
  project,
  dialects: createDialectRegistry([song2Dialect]),
  language: "en",
  activeView: "arrangement", // optional: which of VIEW_NAMES is shown first; "arrangement" by default
});

const parts = [
  mountToolbar(toolbarElement, session, { onRefused: (diagnostics) => report(diagnostics) }),
  mountTimeRuler(rulerElement, session),
  mountChordTrack(chordsElement, session),
  mountVoiceTrack(vocalElement, session, { voice: "Vocal" }),
];

const done = session.dispatch({ type: "toRest", noteId }); // { ok, project, diagnostics }: a refused command returns the project it left untouched; a taken one may carry notices in diagnostics
session.undo(); // the whole project before that command
session.setView({ editable: false }); // every part follows: no editing control, no selection, no keys
session.setActiveView("text"); // a ViewName; the default editor's view switch does this, a host's own switch can too
const found = session.checkScoreText(typed).filter((diagnostic) => !isNoticeDiagnostic(diagnostic)); // what the dialect refuses a text for, without taking it; none when it reads
if (found.length === 0) session.dispatch({ type: "replaceScoreText", text: typed }); // a ProjectCommand: the text replaces the score, one history step
else session.setRejectedText({ text: typed, diagnostics: found }); // a RejectedText: text a view holds that was not taken
const stop = session.subscribe((change) => save(session.project)); // change.cause: "dispatch", "undo", "view", ...

for (const part of parts) part.destroy(); // each removes its own listeners, nodes and share of the stylesheet
stop();
```

- The session is headless: it touches no DOM, so it runs in Node and in a worker. `dispatch` applies a command through `applyProjectCommand`; a refusal comes back as the headless layer above describes. A successful dispatch may carry notices: when a command comes back with a notice only (`isNoticeDiagnostic`, for example `style-no-bpm` after a tempo change), the session takes it as one history step and returns `ok: true` with the notice in `diagnostics`. A list of commands, as a tool run applies, keeps going past a notice, returns each notice once, and is refused as a whole by any other diagnostic. Read `ok`, not whether `diagnostics` is empty, to tell a refusal. The history keeps whole song projects. Selection (note ids), insertion point, zoom, scroll, language and the grid are not fields of it, though an undo of a move or a resize puts the selection back on the notes it moved. A change of the project or of the dialects that cannot write the grid in force puts the default 1/4 grid back in that change, and the change carries `gridDropped` with the old grid; a later change carries none. `replaceProject` starts a new document from outside, the way `update({ project })` does.
- Parts: `mountToolbar`, `mountZoomControl`, `mountCutNotice`, `mountProblemView`, `mountTimeRuler`, `mountChordTrack`, `mountVoiceTrack(el, session, { voice })`, `mountProjectPanel` (a `ProjectPanel`, with `commit` for a host that closes its own container), `mountSynthPreview`, `mountToolPanel`, `mountFilterPanel`, the three views' parts: `mountTextView`, `mountStaffView`, `mountStaleNotice` and `mountViewSwitch`, `mountLyricTrack`, and the draft conflict banner, `mountDraftConflict(el, session, keeper)`. Each returns `{ destroy() }`, and a second `destroy` does nothing. Each part is styled and isolated as `mount` is, and the zoom menu uses the popover layer; the decisions are in [docs/spike.md](../../docs/spike.md).
- `mountStaffView` returns a `StaffViewPart`: the same `destroy()` plus `setPlayPosition(seconds | null)`, which draws the host player's position on the staff and scrolls it into view; null removes it. It works while the session is read-only, and the preview plays on the same cursor (see [The synth preview](#the-synth-preview)). It draws each `Z2`–`Z4` run as separate one-bar rests; the project's score text keeps the run.
- The ruler, the chord track and a voice track scroll in time on their own element, each by its own width. Each is a named region that Tab reaches, and the plus and minus keys zoom around the middle of the one that has the focus. Pass `{ scroller }` as the last argument to put several of them in one scroller of your own, as `mount` does. A part mounted late starts at the session's zoom and scroll.
- The toolbar part holds two rows when it has a bar: a one-line sideways-scrolling strip with the title, the zoom control, the read-only badge in the history group's place, undo, redo, Delete, the pencil, the Select and Grid menus, the Bars menu, the meter control, Restore original, Regenerate…, the tempo/key/transpose group, the Project button and the Tools and Filter buttons; and an always-visible bar with Save and its state (score file only), the view switch and the synth preview control with its whole caption. A generated score's Save as… stays at the end of the strip. A toolbar with neither the switch nor the preview control is the older single scrolling row. Its options are `ToolbarOptions`: `hintId`, `onRefused` for the diagnostics of an edit the score would not take, `viewSwitch`, which adds the view switch to the bar, `synthPreview`, which is on unless you pass `false` (see [The synth preview](#the-synth-preview)), `pencil`, which adds the Draw notes toggle after Delete (the default editor turns it on; see [Commands](#commands) for the placing keys), `draftKeeper`, a `DraftKeeper` whose state the toolbar shows (see [Drafts](#drafts)), `tempoKey` and `projectPanel`, which add the song controls and the Project button (see [Tempo, key and the song project panel](#tempo-key-and-the-song-project-panel)), `tools`, which adds the Tools button and panel (see [The Tools panel](#the-tools-panel)), and `onChooseBars`, which receives the bar the Bars menu chose so a host with a ruler can put the focus on it. The strip is reached by a sideways swipe or by Tab; the bar never scrolls out of view. Undo and redo are the session's `undo()` and `redo()`; Delete is muted until a pitched note is selected and then does what the Delete key does, so a touch screen can delete without a keyboard.
- The cut notice (`mountCutNotice(el, session, { onRefused? })`) is the sentence that says which voice and bar the score text stops at. When the cut is inside a bar and the session is editable it also holds "Fill with rests" and "Delete the incomplete bar"; both call the truncation commands, disappear with the cut when they succeed, and say a refusal in the notice's live region and through `onRefused`. A cut at a bar line has no incomplete bar, so the actions are not there. The rules are in [DESIGN.md](../../DESIGN.md#the-cut).

- Which view is shown is the session's too: `session.activeView` is a `ViewName`, one of `VIEW_NAMES` (`"arrangement"`, `"staff"`, `"text"`), given first by the `activeView` option of `createEditingSession`, set by `session.setActiveView(name)` or by the view switch, and not in the history. `session.rejectedText` is a `RejectedText`, `{ text, diagnostics }`, the text the text view holds that the project did not take, or null; `session.setRejectedText(next)` sets it, and `session.checkScoreText(text)` says what a `replaceScoreText` of a text would be refused with, without taking it. The text view's edit is the project command `{ type: "replaceScoreText", text }`, one of the `ProjectCommand`s that `session.dispatch` and `applyProjectCommand` take next to a `ScoreCommand`: readable text replaces the score, unreadable text is refused with its diagnostic and nothing changes, and the song-project rules run after it as after any command. The change a `dispatch` of a project command announces carries it as `change.command`, so a host can tell a text typed into the score from the other edits. A host with its own layout shows and hides its own views from `activeView`.
- The lyric track: `mountLyricTrack(el, session, options?)` takes the same `{ scroller?, onRefused? }` as a voice track and draws the project's lyric lines under the voice tracks (`mount` mounts it after them). A line on bars is a block over them with its syllable count over its note-start count, green when equal and yellow, with a broken line, when not; the words "equal" and "differ" are in its accessible name. When the counts are equal each syllable stands at its note. Lines that are not on bars, or whose phrase no longer fits, are listed under the lane. While `session.view.editable` is true the lines can be edited, each action as one command and one undo step, and a refusal is said in the part's live region and sent to `onRefused`; the actions, the gestures, the keys and what the choices rest on are in [DESIGN.md](../../DESIGN.md#lyric-track). A host with its own lyric view reuses the rules with no DOM: `lyricRows`, `lyricBoundaryPlan`, `lyricDropPlan`, `lyricSplitCommand` and `barLineTick` (the skill's headless-layer reference).
- Selection, the insertion point and the chosen bars live in the session, not in a part: `session.selection` holds note ids, `session.insertionPoint` a tick and `session.barSelection` a `{ from, count }` run of bars, and none of them is in the history. The ruler draws and takes the bar choice, and `session.setBarSelection(range | null)` trims a run to the bars that exist; a project change clears it. A voice track draws them and takes the clicks and taps. The editing keys are the map in [DESIGN.md](../../DESIGN.md#moving-and-resizing); they are heard by a part while the focus is inside it, a part that handles one keeps it from the browser, and a part given `{ onRefused }` (the option of `ToolbarOptions` and of every time-axis part) hears the diagnostics of a refused command. Left and Right keep scrolling while there is no insertion point; Home and End always place one.
- Selecting several notes: Shift held on a click or tap (a keyboard attached to a touch screen) adds a note to the selection or, when it is selected, takes it out with its whole tie chain; Shift on empty space does nothing, so a missed aim does not cost the selection. A mouse pressed on empty space and dragged draws a box: the notes it touches are framed while it is open and selected when it is let go, Shift held at the press adds to the selection, a box over no note clears it, and Escape gives it up. A press that starts on a note draws no box. On a touch screen a swipe on empty space still scrolls: rest a finger on empty space for 0.4 s and slide to draw the box, or rest it on a note to toggle that note, as Shift does. Ctrl or Cmd plus A selects every pitched note, Ctrl or Cmd plus Shift plus A selects the notes that are not selected and lets go of those that are, and Escape clears the selection, whatever its ids name (with an empty selection it is left to the host). The Select menu in the toolbar does the same three for a finger, and its second group (Copy, Paste, Duplicate) is the finger path to Ctrl or Cmd with C, V and D. While the focus is in the editor these keys are kept from the browser, so the page's own select all does not run. Edits keep the selection on the notes they edited: after Delete the ids stay selected as rests (select all leaves rests out), and an undo brings the notes back selected. While `session.view.editable` is false a click, a box, a hold and these keys select nothing, but `session.select(noteIds)` stays open, so a host's own filter panel can select. The decisions are in [DESIGN.md](../../DESIGN.md).
- Notes by keyboard: a voice track has one tab stop among its notes (the selected note, else the first). The keys and what they do, with a note selected and with none, are the map in [DESIGN.md](../../DESIGN.md#moving-and-resizing). A click or tap puts the focus on the note it selects, so the keys go on from there.
- Announcements: each part keeps one polite announcement region (`role="status"`) in the host's language; the chord picker's visible readout is a second live region inside the picker, as [DESIGN.md](../../DESIGN.md#chord-editing) says. A voice track says which of its own notes were selected, that a delete took some, and what an undo brought back or a redo took away, and the track of the score's first voice says where the insertion point moved; the ruler says which run of bars was chosen; the toolbar's Bars menu and the cut notice say what they changed; any part says why, and where, a refused edit its keys caused was refused (the toolbar for its Delete button and Bars menu), and the toolbar says when a grid the score cannot write is put back to 1/4. A part mounted alone speaks for what it draws, and nothing reads another part.
- Not tied to the DOM: `handleEditingInput(session, input)` takes one `EditingInput` as plain data and does what the parts do, so a host that builds its own layout or its own input handling can reuse it. The input is `{ type: "key", key, ctrlKey?, metaKey?, shiftKey?, altKey? }`, `{ type: "click-note", noteId }`, `{ type: "click-empty", tick }`, `{ type: "delete" }` (what a Delete control sends), `{ type: "toggle-note", noteId }` (a click on a note with Shift held), `{ type: "select-notes", noteIds, add? }` (a box: exactly the pitched notes among `noteIds` are selected, or with `add` join the selection; no note clears it unless `add`), `{ type: "select-all" }`, `{ type: "invert-selection" }`, `{ type: "clear-selection" }`, `{ type: "move-notes", timeTicks, semitones }` or `{ type: "resize-notes", edge, timeTicks }` (a drag, with the distance the pointer covered); the key input takes every key in [the map](../../DESIGN.md#moving-and-resizing). It returns an `EditingInputResult`, `{ handled, refused }`: `handled` says the input meant something here, so the caller should keep the browser from also acting on it, and `refused` holds the diagnostics of an edit the score would not take. While the session is not editable nothing is handled. Deleting several selected notes is one history step, and one refusal refuses the whole run.
- `mount` builds one session and assembles these parts in a toolbar, a scroller and a problem view; its options are those in [Mount](#mount), and `editable` and `notify` do what the first list says.
- Chords: while `session.view.editable` is true and the arrangement is shown, a click or tap on the chord track places, changes or removes the chord at the nearest allowed start (or at the chord pressed) through the package's own picker; each edit is one `setChord` and one history step, and a refusal changes nothing and is said in the part's live region and through `onRefused`. The picker reads the chord vocabulary from `session.dialect.constraints`; with no dialect for the project's model (`session.dialect` undefined) the chord track is not editable. The picker's appearance and keys are in [DESIGN.md](../../DESIGN.md#chord-editing).
- Chords by keyboard: the chord track's cursor is its one tab stop; the keys are in [DESIGN.md](../../DESIGN.md#chord-editing). `chordSlots`, `nearestChordSlot`, `chordChoices` and `splitChordName` are the headless half: which starts a score offers, which one is nearest a tick, which names a vocabulary offers, and how a name splits into root, type and bass. A type is offered only when the grammar can write it with every offered root.
- Selecting by condition: `filterNotes(score, filter)` returns the ids of the notes of a `Score` that satisfy a `NoteFilter` (pitch, time, length, in or out of key, one in every N, invert), and `mountFilterPanel(el, session)` is the part that asks for the conditions and selects the notes through `session.select`. The toolbar mounts the Tools panel before it and the Filter button last in the strip, while the arrangement is the view shown; a generated score's Save as… follows it. Selecting is not an edit, so the panel adds nothing to the history and works while `session.view.editable` is false. What the conditions mean is in [the skill's headless reference](skills/score-editor/references/headless-layer.md#picking-notes-by-conditions), the panel in [its view-parts reference](skills/score-editor/references/view-parts.md#selecting-by-filter), and the decisions in [DESIGN.md](../../DESIGN.md).
- `session.dispatchAll(commands)` applies a list of score and project commands as one history step through the same path as `dispatch`: all of them apply, in order, or none does, and the listeners hear one change. A notice does not stop the list; any other diagnostic refuses all of it, with the project and the history untouched. An empty list, or one that leaves the project as it was, adds no step. A gesture that needs several commands uses it, such as dragging a boundary that two lyric lines share.
- The section menu: while `session.view.editable` is true, each section band of the time ruler is a button over the whole band (a chevron after its name says so) that opens a menu of what can be done to the section: rename it (or name the unnamed opening), start a section at a bar, move it earlier or later, duplicate it, delete it. Each is one command and one history step. A choice the commands would refuse stays in the menu, muted, with the command's own words under it, and pressing it does nothing. The answer comes from a dry run of the command, so no rule is written twice, and a host that builds its own section control asks `sectionActions(session, index)` for the same answer. Rename and "start a section at a bar" ask for a name, and a bar, in a small form under the band; a refusal stays in the form and goes to `onRefused` as a refused key does, and the form sends the bar as typed, so the command decides what a bar may be. Bands are not Tab stops; the section-menu keys are in [DESIGN.md](../../DESIGN.md#section-menu). After a choice the focus and the view follow the section that was acted on, and a live region says what was done. While `session.view.editable` is false the bands are drawn and nothing opens. On a touch screen the row of bands is 25px tall, and the control reaches 12px above it, so the target is at least 37px. The decisions are in [DESIGN.md](../../DESIGN.md).

## Tempo, key and the song project panel

The default editor's toolbar holds four controls that act on the whole song. They are there while `session.view.editable` is true and the score reads: a tempo field (a whole number of BPM inside the dialect's `constraints.tempo`), a key menu (the dialect's `constraints.keys`, major and minor, with the score's key chosen) and two buttons that transpose by a semitone. Each change is one command (`setTempo`, `setKey`, `transpose`) and one undo step, and the rules are the [headless layer's](#commands), not the toolbar's: a tempo change rewrites the BPM written in the style text, or leaves the style as it is and the toolbar says so in a line under the row (`style-no-bpm`, gone when the project next changes); a transposition that would leave the dialect's range is refused as a whole, and the reason is said in the toolbar's live region and sent to `onRefused`, which the editor passes on as `command-refused`. `mount` turns the controls on; a host that mounts `mountToolbar` itself passes `tempoKey: true`.

The Project button after them (`projectPanel: true` in `ToolbarOptions`; `mount` passes it) opens the song project panel in a popover under it. The panel is a view part of its own, `mountProjectPanel(el, session, { onRefused })`, for a host that wants it somewhere else; it then leaves `projectPanel` off. It returns a `ProjectPanel`, whose `commit()` takes a field that has not been let go, for a host that closes its own container; `destroy()` changes no document. It holds:

- the style text, the score mode (`full` or `melody`) and the seed, each edited in place. The style text is taken as one command when its box loses the focus or the popover closes, the score mode when a radio is chosen, the seed when it is confirmed; each is one undo step. The Clear button sets the seed to `null`. A seed that is not a whole number is refused as `setSeed` refuses it, and the field goes back to the project's value.
- the lyrics as `joinLyrics` writes them, in a read-only region, with their length: "N of 4000 characters" (`LYRICS_MAX_CHARACTERS`). Over the limit nothing stops the person; the panel says so (`lyrics-too-long`), and a line with no bar to stand on is told as `lyrics-unaligned`.
- the notices the project carries (`checkProject`). For `melody-with-chords` there are two buttons, "Delete all chords" (`removeChords`) and "Switch to full" (`setScoreMode`), each one undo step. While the popover is closed the Project button's name says how many notices there are.
- a field the host did not give (an empty style, a `null` seed, a score mode that is missing) is empty and says "Not set"; the person can fill it. While the session is read-only the panel shows the values as text, edits nothing and offers no fix; the notices stay.

`session.dialect` is the dialect that reads the session's project, or `undefined` when the registry has none for its model; the controls and the Project button are hidden then. On a window narrower than 40em the popover spans the window under the button.

## Custom tools

A **tool** is a pure function from a song project, the selected note ids and its parameter values to a list of commands. It declares an id, a name in both languages and its parameters; it never touches a session or the DOM, so the same tool runs in a test, a worker or a panel.

```ts
import { song2Dialect } from "@neta-art/score-dialect-song2";
import {
  createDialectRegistry,
  createToolRegistry,
  previewTool,
  type ScoreTool,
  type ToolParameter,
} from "@neta-art/score-editor";

const every: ToolParameter = { name: "every", type: "number", min: 2, max: 8, default: 2 };

const restEveryNth: ScoreTool = {
  id: "rest-every-nth",
  name: { en: "Rest every Nth note", zh: "每隔 N 个音变休止" },
  parameters: [every],
  commands(_project, selection, values) {
    const step = values.every as number;
    return selection
      .filter((_id, index) => (index + 1) % step === 0)
      .map((noteId) => ({ type: "toRest", noteId }));
  },
};

const tools = createToolRegistry([restEveryNth]); // a second id or a malformed tool throws
const found = tools.find("rest-every-nth"); // tools.list() returns every registered tool

const dialects = createDialectRegistry([song2Dialect]); // the session was created with the same registry
const preview = previewTool(restEveryNth, session.project, session.selection, { every: 2 }, dialects);
const viaSession = session.previewTool(restEveryNth, { every: 2 });
const result = session.runTool(restEveryNth, { every: 2 });
```

- A tool may also declare a `group` (`"note"`, `"quantize"`, `"transform"`, `"generate"`, or `"more"`), a one-line `description` in both languages, and `needsSelection: false` / `needsGrid: false` for a tool that acts on the whole song and keeps the score's own timing; the Tools panel lists it under that group and shows the description. Every tool is called with a `ToolContext` as the fourth argument of `commands`: the session's `grid`, `insertionPoint`, and `selectionFirstBar` and `selectionLastBar` (1-based, null with nothing selected). A function written with three parameters ignores the fourth, so a 0.1.0-shaped tool is unchanged, and a tool written with a default or rest parameters still receives it. A parameter's `default` may be a value or a function of that context; the panel computes it when the tool opens, which is how Fit into bars starts at the selection's first and last bar.
- Parameters are declared as `number` (with optional `min`, `max` and `step`), `boolean`, `choice` (with `values`), or `text`. A missing value takes its default. A wrong type, an out-of-range number or a value outside a choice is refused with the command diagnostic code `tool-parameter` before the tool's function runs; `formatDiagnostic` gives it zh and en text. The registry also refuses a tool with no `commands` builder, an unknown parameter type, a choice without values, or a default its own declaration would refuse, so a broken tool never runs.
- `previewTool` and `session.previewTool` return `{ ok, project, diagnostics, commands }` without changing the session: no dispatch, no history step, no notification. The project is the tool's result, or the project it started from when a step fails.
- `session.runTool` checks the parameters, builds the commands once, and applies them through the same command path as `dispatch`. All commands are one history step: one undo goes back to the project before the run, one redo reapplies it. If any step fails its `check`, the run is refused, the result carries that step's diagnostic, and project and history stay as they were. A step that comes back with a notice does not fail the run: the result is `ok` and its `diagnostics` hold the notices.
- `applyCommandList(dialect, project, commands)` applies a list of score and project commands through the same path as `dispatch` and returns a `CommandListResult`. A notice does not stop the list; any other diagnostic refuses the whole list and leaves the project as it was.
- A tool's result must keep the rules the command layer keeps: one note at a time in a voice, and every note it creates or changes starting and ending on the grid in force. A result that breaks either is refused whole with the `tool-result` diagnostic, so the project and the history stay as they were; `formatDiagnostic` says which rule it was.
- Every export here is additive to the 0.1.0 entry and the editing-session entry; `commands`, `parameters`, `name`, `description` and `group` are the shape the registry and session read.

## The Tools panel

`mountToolPanel(el, session, { tools? })` is the view part that puts a **Tools** button in the toolbar's strip and opens a panel of the built-in note tools and the host's tools. The default editor passes its `tools` option to it and so always has the button; a host that mounts `mountToolbar` passes `tools` (an array, possibly empty) to get it, and a host with its own layout mounts the part itself. The registry is the only list the panel reads, so a host registers a tool once and the panel shows it.

- **Groups.** Note tools, Quantize, Transform and Generate, then More tools for a tool without a group; a group with no tool is left out. Each tool row is a button; choosing it opens its controls under it and closes the previous one.
- **Controls.** One per declared parameter: a number field with the declaration's `min`, `max` and `step`, a checkbox, a menu of a choice's `values`, a text field. Each starts at its default (or at the value the default function returns for the session's `ToolContext`), and each change previews again. On a coarse pointer a number field gets 40px − and + buttons that step by the declaration's `step` and stop at its `min` and `max`; a value typed outside the declaration still comes back as a `tool-parameter` diagnostic. The panel clamps nothing.
- **Voice results.** The two Transform tools put their command report in the status line. Voice octave: "Preview: Vocal moves 1 octave down; median pitch E3 (52), outside the singable range 60-82.", then "Applied. Vocal moved ..." after Apply; Chinese "预览：人声下移 1 个八度；中位音高 E3（52），不在可唱区间 60–82 内。" and "已应用：…". Instrumental version: "Preview: 3 Vocal notes move to Ins; 2 Ins notes are cut short, 1 is dropped." then the applied form; Chinese "预览：3 个人声部音符将移到器乐声部；截短 2 个，丢弃 1 个。". They need no selected notes and no grid, so the panel leaves "Select notes first." only for tools that do need a selection.
- **Preview.** `session.previewTool` is called with the session's grid, insertion point and selection bars; nothing is dispatched and nothing enters the history. While the panel is open the voice tracks draw the notes the result would change as dashed outlines where they would land, the same mark a drag makes, each with a 1px ground halo so a dense result still reads. If no outline is in the part of the arrangement the panel leaves uncovered, a preview scrolls the arrangement's own scroller (time and pitch, never the page) to put the first changed note there; nothing moves when an outline is already in view. The status line says how many notes would change or that the tool would change nothing; when Fit into bars changes nothing because its bars are already the selection's, it says which bars and to change From bar or To bar. Closing the panel, switching view, a read-only session or `destroy()` takes the outlines down; a parameter, the selection, the project or the grid changing previews again.
- **Apply.** One `session.runTool` call, so one undo step; the status line says "Applied. Undo takes it back." A refusal leaves the project and the history untouched, names the tool as the list does and says how to recover, and reaches `onRefused`, which `mount` turns into the host's `command-refused` notice. Apply with no tool chosen answers "Choose a tool first." There is one polite live region: it speaks on a committed value, on Apply and on a refusal, not on every keystroke, while the visible status line may follow each keystroke. With nothing selected and no tool open the line reads "Select notes, then choose a tool."; with notes selected it reads "Choose a tool."
- **Place.** In the toolbar the button comes after Project and before the Filter button in the strip, so Filter stays last except a generated score's Save as…; a wrapper holds the pair, so the panel hangs from the right and a preview on the arrangement stays in view on the left. Choosing a tool scrolls its row and controls below the measured sticky heading. A panel that hangs from a toolbar button starts at least 8px under the toolbar and shrinks and scrolls inside to fit the window, so it never covers the toolbar that opened it; the Filter panel uses the same rule. On a coarse pointer at a window of at most 640px the panel is a bottom sheet from the bottom edge, full width, capped at `100dvh − the chrome's bottom − the music floor` so DESIGN's floor stays in view, as the Filter panel is; its status line takes the sheet's full width above Apply and Close, and the two buttons share the row under it. It is an editing control: hidden while the session is read-only, while the score does not read, and while the staff or text view is shown.
- **The built-in tools** are exported as `NOTE_TOOLS` and written against the same `ScoreTool` shape: split at the insertion point, chop on the grid, join adjacent same-pitch notes, legato, reverse, flip up and down, snap to key, length ×2, length ÷2, set length and fit into bars in the Note tools group, and Voice octave and Instrumental version in the Transform group. The two Transform tools need no selection and no grid: Voice octave's status names the direction, the median pitch and whether it is inside the singable range 60-82; Instrumental version's status names how many Vocal notes moved and how many Ins notes were cut short or dropped. `NOTE_TOOLS` names the list, not the group: the two Transform tools are in it. Each returns one command, and every timing value lands on the current grid. A host may register its own tools beside them, or use `NOTE_TOOLS` in a registry of its own.

## The synth preview

A song can be heard in the browser as a plain synthesis of its melody and chords, with a playhead that follows it. The sound is made in the page from oscillators: there is no sample library, no worklet module and no request of any kind. It is a rough rendering, and the interface says so wherever it offers it: "Synthetic preview, not the final sound" (zh: 合成试听，不代表成品效果), in the session's language, beside the control.

```ts
import { mountSynthPreview, previewNote, previewPlayer, schedulePreview } from "@neta-art/score-editor";

const control = mountSynthPreview(transportElement, session); // a Preview and Stop button with its caption
const player = previewPlayer(session); // the one player of this session, whoever drives it
player.subscribe(() => draw(player.playing, player.tick)); // after every frame it moves in
const result = await player.start(1024); // from a click handler, from tick 1024; without it: the insertion point or the start; "started" | "nothing-to-play" | "unsupported" | "blocked" | "cancelled"
player.stop();

await previewNote(64, { duration: 0.35 }); // one pitch for a short time: true once it sounded

const { events, length } = schedulePreview(score, 512); // notes and chords in seconds from tick 512, with no browser involved
```

- `mountSynthPreview(el, session)` is a view part like the others: one button (a line icon and the word Preview, or Stop while it plays) and the caption. A second press stops. It is not an editing control, so it is there while the session is read-only, and it is hidden only while the session has no readable score. `mountToolbar` holds the same control by default, in the bar after the view switch, so the default editor has it; pass `{ synthPreview: false }` when you mount `mountSynthPreview` somewhere of your own, so it is not there twice.
- The preview starts at the session's insertion point, or at the start when there is none or while the session is read-only; `start(fromTick)` starts at a tick a host or a view chose. It plays the `Vocal` and `Ins` voices and the chord of each span. Seconds come from the score's tempo and every position from the score itself, so each bar is as long as its own meter makes it and a change of meter is followed. A `Score` may carry `tempoChanges`, each with a tick and the tempo from there; both the preview and the staff cursor count each stretch at its own tempo. The `song2` format writes no tempo change, so its scores have only the opening tempo. A tied chain sounds once, a rest is silent, and a cut score ends where its music ends. It stops when the project is replaced or changed, when the music ends, when Escape is pressed, when the browser interrupts the audio, and when an `<audio>` or `<video>` element in the page's own document starts to play. Sound the page is already playing is left alone: the preview does not pause it.
- `previewPlayer(session)` returns the session's one player, a `PreviewPlayer`: `playing`, `tick` (the tick under the playhead while it plays, a fraction between whole ticks), `from`, `start(fromTick?)`, `stop()` and `subscribe(listener)`. Making it touches no audio. The voice tracks of the session subscribe to it and draw the playhead, a hairline through each lane; the staff view subscribes to the same player and draws the same position on the staff, and a press on a staff note calls `start(tick)` so the preview begins at that note. The player knows no view, and a view reads only `tick`. A host that builds its own transport or its own playhead does the same. The position is not in the session's view state: that holds the UI state parts share (zoom, scroll, language) and notifies on change, and the playhead moves on every frame, so the player is its one source and has its own small subscription.
- Autoplay: a browser lets sound start only after a user gesture, so call `start()` and `previewNote()` synchronously from a click, tap or key handler, before any `await`. When the browser refuses, `start()` resolves `"blocked"` (the control says so, and the next press works) and `previewNote()` resolves `false`. Where there is no Web Audio at all, `start()` resolves `"unsupported"`, `previewNote()` resolves `false`, and the control is muted, with the reason in its tooltip and in place of its caption. When a press does nothing (nothing to play from here, or the browser refused the sound), the caption says why for a few seconds and then comes back. Everything shares one audio context, suspended again about a third of a second after the last sound, so an idle editor holds no audio device. What was checked in which browser is in [DESIGN.md](../../DESIGN.md).
- `previewNote(midi, { duration })` is the single-note preview, for a view that sounds a note as the user draws or selects it: a whole MIDI number from 0 to 127 (a `RangeError` otherwise), for 0.35 seconds unless `duration` says otherwise, kept between 0.02 and 10 seconds. It resolves `true` once the note sounded.
- `schedulePreview(score, fromTick = 0)` is the headless half: a pure function from a `Score` to `{ events, fromTick, secondsPerTick, length }`, where an event is a note (`voice`, `midi`) or a chord (`name`, `midis`, bass first) with `at` and `length` in seconds. `secondsPerTick` is the opening tempo's; `tickAtSeconds(score, seconds)` turns a host player's time back into a tick, tempo changes included, and stays at the end past the score's last second. Both run in Node and in a worker.

## Score files, save and save-as

`MountOptions.source` tells the editor where the score came from. A **score file** is a host document, so its edits are
saved only when the user asks:

```ts
const editor = mount(el, {
  language: "en",
  project, // project.score is the file's text; style, seed and lyric lines start empty
  dialects,
  source: {
    kind: "scoreFile",
    name: "tune.abc", // the handoff instruction's title
    version: file.version, // opaque, as a draft store's version is
    save: (text, expected) => writeFile(path, text, expected), // { ok: true, version } | { ok: false, reason }
    read: () => readFile(path), // { text, version } | null, for "load the other version"
  },
  onUnsavedChange: (unsaved) => guardWindowClose(unsaved),
  requiredInputs: ["style"],
  onHandoff,
});
editor.hasUnsavedChanges(); // the same answer, asked just before closing
await editor.save(); // "saved" | "unchanged" | "conflict" | "failed", the keeper's settled words
```

`editor.save()` is the host's Save: it runs the same path as the Save button and Ctrl/Cmd+S, waits for the write to settle, adopts the returned version and answers the score-file keeper's `ScoreFileHandoffResult` — `saved`, `unchanged`, `conflict` or `failed`. `unchanged` means nothing was written: a generated score (it does not call Save as), a read-only editor, no unsaved changes, a save already in flight, a standing conflict, or an editor destroyed. A generated score's Save as stays a user action only.

The toolbar has **Save** in its always-visible bar, before the view switch. It chooses one form for the bar from the room
the widest state needs (the pill word plus the button word over clean, dirty, saving, failed and conflict), re-chooses
only when the bar's width, the language or the font metrics change, and never because the state changed. While the
widest state's words fit in the height the bar has without the control, the state is in words: **Unsaved**,
**Saving…** in the button, **Save failed** in the pill with **Save again** on the button, and **Unsaved** in a conflict.
Where the words would add a row, every state uses the icon and one mark (`•`, `!`, `?`, `…` while saving). The pill is
`aria-hidden`; the button's description carries the state, and a failed save also has the recovery sentence there and as
its tooltip. The toolbar's live region says **Saved** after a successful write and the recovery sentence after a
failure. Ctrl/Cmd+S saves while the focus is inside the editor. While there is nothing to save, or a save is in flight
or a conflict stands, Save is `aria-disabled`. A failed save, and a handoff refused because the save failed, also draw a
one-action notice in the chrome: the recovery sentence, or `handoffNotSentFailed`, as an alert with **Save again**,
which saves through the same path as the Save button, Ctrl/Cmd+S and `MountedEditor.save()`, so the toolbar's live region
says **Saved** after it; it stands until the next successful save or the conflict's answer and takes no focus. A version conflict
shows the draft conflict's strip with **Overwrite with
my version** (read their version, then write ours over it; the other version can't be brought back) and **Load the other
version** (their text opens as a new document; your changes here are dropped); the banner is scrolled into the chrome's
visible box when it appears, the dialog opens where both choices fit, and the chrome returns to its earlier scroll when
the banner goes. Restore original asks about the last saved version, is muted while the file is clean, and
its answer is **Go back to last save**; it resets the history, so Undo cannot bring the changes back. The change log and
the handoff use the last saved project as their original. No draft call is made, even when `drafts` is also given.

The toolbar's first strip item is the source label: **Generated score (original kept)** or **Score file (saves to the file)**, in the interface language (「生成的乐谱（原版保留）」/「乐谱文件（存回原文件）」). It is plain text (no border or pill), one line on the desktop and two lines on a phone at the opening bracket, so it does not read as a control and never cuts a word. It follows the language and a source that changes after Save as through `update`, says the new label once through the toolbar's live region when the source changes, and is first in the strip, so it is in sight before the strip scrolls; it adds no toolbar row at 1280, 412, 360 or 320. A host that lays out its own chrome mounts it with `mountSourceLabel(el, session, { source: () => options.source })`.

A **generated score** (the absent source) keeps drafts as before and adds **Save as…** while `onSaveAs` is given; the
callback receives the current score text. `onSaveAs` is not shown in read-only mode.

`requiredInputs` is the host's list of `ProjectField` values (`"style"`, `"scoreMode"`, `"seed"`, `"lyrics"`). While
one is missing, the trigger names it (**Add style first…**, **Add lyrics first…**, or **Add 2 required inputs…**). Style,
score mode and seed open the Project panel on that field; lyrics show the arrangement and open the lyric track's new-line
editor, because the Project panel shows lyrics read-only. A required empty field's hint starts **Required to
regenerate.** The editor reads no model declaration. A score-file handoff saves first when the file is dirty (the review
says **Saves tune.abc first, then sends the song.**) and stays closed on a conflict or a failed save; a conflict is
answered by the conflict banner, and a failure says **Not sent: …** in the one-action notice in the chrome, through a
`handoff-not-sent` notice and the toolbar's live region; its instruction title is the file's name.

For a host with its own Save control, `createScoreFileKeeper({ session, original, source, notify?, onUnsavedChange? })`
returns a `ScoreFileKeeper` with `status`, `unsaved`, `failed`, `savedProject`, `version`, `save`, `overwrite`,
`loadTheirs`, `restoreOriginal`, `handoff`, `subscribe` and `destroy`. Versions are the host's opaque strings, and
`ScoreFileSaveResult` is the same shape as `DraftWriteResult`. The design is in [DESIGN.md](../../DESIGN.md#score-source-save-and-save-as).

## Drafts

The headless draft keeper saves a session's project through a host store, restores it on open, and inherits lyric lines into a regenerated song. It works in Node with no DOM, like the session. `mount` wires it for the default editor ([In the default editor](#in-the-default-editor)); a host that builds its own layout uses the keeper directly.

```ts
import { createDraftKeeper } from "@neta-art/score-editor";

const keeper = createDraftKeeper({
  session, // the editing session
  store, // a DraftStore: read, versioned write, versioned remove, list
  original: project, // the source project; the keeper never changes it
  notify: (notice) => showToast(notice.message), // draft-source-changed, draft-save-failed
});

await keeper.ready; // opening and inheritance are done
keeper.subscribe(({ status }) => showConflict(status === "conflict")); // "opening" | "ready" | "conflict" | "destroyed"
await keeper.overwrite(); // the conflict way out that keeps this window's project
await keeper.loadTheirs(); // the one that takes the other window's draft
await keeper.handoff(); // "written" | "unchanged" | "conflict" | "failed"
await keeper.restoreOriginal(); // the original back, history reset; true when the draft was cleared, false when it was not
keeper.destroy(); // stops the timer and the subscription, and starts a pending write once
```

A draft is JSON text, written and read by `draftText` and `readDraft`: a format version (`DRAFT_FORMAT_VERSION`, today `1`), the source key, the content hash of the original's lyrics and score, the draft's project (style, joined `lyrics`, lyric lines with their phrases, score text, score mode and seed), the content hash at the last handoff or null, and the update time in milliseconds. The project is the spec's list plus the joined `lyrics` field, which this package adds so a restored project is byte for byte the one the user left. A text of another version, or one that does not have that shape, reads as no draft.

`contentHash(lyrics, score)` is SHA-256 over the UTF-8 bytes of `JSON.stringify([lyrics, score])`, as lowercase hex, with no normalisation. It uses `globalThis.crypto.subtle`, which browsers, Workers and Node from 19 on have (Node 24 in this repository), so the same function makes the source and the handoff hashes.

The host's `DraftStore` takes keys and text; where a key maps (a file, a path, a record) is the host's business. `read(key)` answers `{ text, version }` or null. `write(key, text, expected)` and `remove(key, expected)` answer `{ ok: true, version }` or `{ ok: false, reason: "conflict" | "failed" }`; `expected` is the version last read or written, or null to create. `list()` gives the keys that hold a draft. A host without deletion may keep a tombstone, as long as `read` answers null and `list` leaves the key out.

- **Open.** A draft for the original's key whose source hash matches is put into the session. A stale one is removed; `draft-source-changed` says the original changed only when that removal succeeds, and `draft-save-failed` says it did not. No draft is normal and silent. A stale own draft stops there; it does not also inherit from another song. A text of a version this package does not know is left alone; the next write is a create (`expected: null`) and the store's conflict offers the two ways out.
- **Inherit.** With no own draft, the keeper reads the listed drafts (at most 50, in the host's order) and takes the matching `handoffHash` with the latest update time whose lyric lines join to the new song's own `lyrics` byte for byte. It then puts the original with those lyric lines into the session; the original's `lyrics` is not replaced. A matching draft whose lines join to other words is not inherited. Fifty bounds the work on a device with many drafts; a handoff is recent by nature, and a larger store is still read in order. The inherited project is kept under the new source key after the debounce, with no handoff hash of its own.
- **Keep.** About one second after the last project change, the draft is written; selection, view and insertion-point changes write nothing. A project equal to the original, in every field the draft stores and in its effective lyric lines, removes the draft instead, and writes nothing when there is none.
- **Conflict.** A versioned write or removal answered with a conflict stops further writes and sets the status to `conflict`. `overwrite()` reads their version and writes ours over it; `loadTheirs()` reads their draft and replaces the session's project, and leaves the conflict in place when the text cannot be read. A successful action returns the status to `ready`.
- **Failure.** A write or removal that is not a conflict sends `draft-save-failed`; the next project change tries again.
- **Restore the original.** `restoreOriginal()` uses `replaceProject`, so the history, selection and insertion point go with the edits the draft recorded; there is no history step back to a draft that no longer exists. It reads the key and removes whatever is there, including a draft this keeper did not know about or a text it cannot read; a conflict or failure there is reported as for a write, and the promise resolves `false` because the draft stayed.
- **Handoff.** `handoff()` hashes the current joined lyrics and score, cancels the pending write and saves at once with that handoff hash. When the project equals the original there is nothing to inherit, so no draft is written and the result is `"unchanged"`.
- **Destroy.** `destroy()` stops the timer and the subscription and starts one pending write, because unmounting is also how a route change leaves the editor. It does not wait for the write.
- The keeper calls the store only with the original's source key for writes and removals; inheritance reads other keys and never writes them. No path changes the original project.

### In the default editor

Give `mount` a `drafts` store and the editor does the keeper's half that a person sees. The keeper's rules above are unchanged; what `mount` adds is below.

- **Wiring.** While the editor is editable and has a store, and the source is a generated score, `mount` creates one keeper on the project and `destroy()` destroys it, which starts one pending write. A read-only editor, one without `drafts`, or one with a score-file source has no keeper: no read, no write, no list, no Restore original.
- **Opening.** Until the keeper is ready the editor shows the original, the toolbar badge says "Opening draft…" where a read-only editor says "Read only", and no edit can start: the editing controls are not there and the keys do nothing. When the draft is read (or none is found) the editing controls appear. A store whose reads never settle keeps the editor in this state; there is no timeout, because how long a read may take is the store's to decide.
- **Restore original.** A word button in the toolbar, shown while the keeper is ready or in conflict and the editor is editable. It opens a question in a native popover of the editor's own, so it stacks above a host's full-screen layer: "Go back to the original score?" and "Every change you made is discarded and the saved draft is deleted. You can't undo this." The focus starts on Cancel; the other answer is "Restore original", which calls `restoreOriginal()` and, once the store has answered, has the toolbar's live region say that the original is back. When the draft could not be cleared it says that too, and the host has had `draft-save-failed`. The question is asked once, and Escape or Cancel leaves everything as it was. The button is there from the first edit, and before it, so a person can always get back to the original; there is no muted state.
- **Conflict.** When another window wrote the draft first the editor keeps editing, the keeper writes nothing, and a banner between the toolbar and the views says that the draft was changed somewhere else and that nothing is saved until the user chooses. It has one **Choose** button; the two two-line choices live in the dialog under it: "Overwrite with my version" ("The other version is replaced and can't be brought back.") and "Load the other version" ("It opens here, and your changes in this window are dropped."). They call `overwrite()` and `loadTheirs()`; there is no second question, since the cost is in the button. The dialog opens under the banner when both choices fit there, and from the top of the editor, over the toolbar, when the room below is too short, so neither choice is cut and the dialog does not scroll. When the banner appears, the editor scrolls the chrome so the sentence and Choose are in its visible box, and when it goes the chrome returns to where it was. The banner never takes the focus; its sentence is an alert. Restore original stays available during a conflict.
- **Notices.** `draft-source-changed` and `draft-save-failed` reach the `notify` of the options, in the current language. The editor draws nothing of its own for them; a failed save is tried again after the next edit. A score file's failed save has its own visible notice; see [Score files, save and save-as](#score-files-save-and-save-as).
- **`update`.** A project with another `sourceKey`, `lyrics` or score text is a new original: the keeper is destroyed (it writes what it still holds under the old key), the project is replaced, and a new keeper opens on it. A project with the same original but another `style`, `scoreMode` or `seed` keeps the keeper and the user's edits, and those fields go to the session through the project commands, as one history step. A change to `modelId` has no project command, and a change to the stored `lyricLines` alone is not carried; the editor keeps what it has for those. Passing a project whose every field is equal (the lyric lines by content) is not news, so a host that re-renders does not take the user's edits away. `update({ drafts })` with another store ends the keeper of the old one (it writes what it holds) and opens one on the new, `update({ drafts: undefined })` takes the store away (a pending write is made first, and later edits write nothing), and `update({ editable: false })` ends the keeper in the same way while `update({ editable: true })` opens one again.
- **Parts.** A host with its own layout puts the strip where it likes with `mountDraftConflict(el, session, keeper)`. The Restore original button and the opening badge belong to the toolbar part and appear when it is given the keeper in its `draftKeeper` option.

## Change log and handoff

The change log is a pure function of the original and the current project. It reads both score texts with the project's dialect and returns one sentence per kind of change: a deleted, copied, moved or renamed section; the tempo, key, meter or chords; the lyrics, style description, score mode or seed; the bars whose notes changed, named by bar and range; and the text view's own edit. Score modes and the seed use the Project panel's words, and a meter change names the new meter and the bars. The package recomputes it every time; it never reads a stored draft. A score text that changed while it still reads as the same score is the text view's edit; when the text changed the music, the music changes are named instead.

```ts
import { changeLog, handoffInstruction } from "@neta-art/score-editor";

const changes = changeLog(original, current, { language: "en", dialect: song2Dialect });
const instruction = handoffInstruction({
  original,
  current,
  title: "My Song",
  language: "en",
  dialect: song2Dialect,
});
```

`changeLogEntries` is the structured form: the same sentences in order, each with the 1-based bars it names. The review marks the entries that name a bar the last step (an edit, an undo or a redo) rewrote with 600 weight and a text-colour dot, and shows a legend under **Changes** only while an entry is marked; the accent stays for focus. `changeLog` stays the string list.

`handoffInstruction` writes the prefilled text: the title, the request to regenerate with song2 and pass the attached score through `--text`, the final style description and joined lyrics (already synced, not to be changed), the score mode and the seed when there is one, and the change log. The joined lyrics come from the current score and lyric lines, not from the stored `lyrics` field alone.

`preHandoffNotices(dialect, project, language)` returns the four notices a project carries before a handoff: no section markers, the whole song's syllable count far from its note count (more than one syllable per lyric line away), Vocal's lower median outside the singable range 60-82, and a melody project with chords. Each sentence says what is wrong in the product's own words and what to do next, naming the control the editor uses: the Unnamed section bar, the lyric lines, the Voice octave tool, and the Project panel's Score mode names. The review puts them first, with a 600-weight lead line naming how many there are, then the change log; it follows edits while it stays open, and opening also says the lead line once in the toolbar's live region. The editor sends each through `notify` once each time the review opens, with the codes `prehandoff-no-sections`, `prehandoff-syllables-far`, `prehandoff-vocal-range` and `prehandoff-melody-chords`, so a host that toasts every notice may skip these: the review already shows them. A project with none shows no line and sends nothing. The review's first line says where the edits go for each source: the original is kept for a generated score, the file is saved for a saved score file, and a dirty file keeps **Saves [file] first, then sends the song.**

With `onHandoff`, and while the editor is editable, the toolbar has a **Regenerate…** button in the strip after Restore original and before the song controls. It opens a native popover headed **Check before regenerating**, with the change log and the action **Regenerate with this version**; the focus starts on Cancel. Pressing the action closes the popover, saves the draft through the keeper's `handoff()` so the draft carries the handoff hash, and then calls the host with a `HandoffPayload`:

- `attachment`: `{ name: "score.abc", mediaType: "text/plain", text }`, where `text` is the current score;
- `instruction`: the prefilled instruction in the interface language;
- `project`: the final song project.

The payload is taken before the save is awaited, from the project the review showed, so an edit made while a slow save is pending does not reach the attachment, instruction or project. While the save runs the trigger reads **Saving…** with `aria-busy="true"` and cannot open the review; afterwards it reads as before. The editor never calls a generation API and never sends anything itself. When the keeper answers `"written"` or `"unchanged"` the host is called; `"conflict"` leaves the draft conflict banner to answer, and `"failed"` leaves the `draft-save-failed` notice to answer, so neither calls the host. A host with no draft store still gets the handoff, without a draft to save. Without `onHandoff`, or while read-only, the button is not there. While the text view holds text the project did not take, the popover says that the last readable score is what is handed off; it is not disabled. The review is bounded by the room under the trigger and scrolls its change list in a short window. The control adds no fixed height to the toolbar: it is a word button in the scrolling strip, 28px high (36px on a coarse pointer), and the strip scrolls to it rather than wrapping it onto another row.
