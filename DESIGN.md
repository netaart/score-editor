# Design System: Score Editor

## Overview

**Creative North Star: "The Borrowed Instrument Panel"**

The editor has no brand. It is a tool panel that takes on the look of whatever host app embeds it. The package owns structure, interaction and legibility; the host owns colour and type. Everything stated below about colour and type is therefore a contract for hosts first, and a set of neutral fallbacks second.

It is an Operate surface: an arrangement view for people who generated a song and want to see how it is built before changing it, and who can now change the first thing: select one note or several, turn them into rests, take that back. DAW conventions are the reference: a pitch column at the left, a bar ruler on top with section bands, key and meter marks and a chord track under it, one piano-roll track per voice, a hairline grid with heavier bar lines, black-key rows shaded, zoom on the time axis. Touch and keyboard are first-class: the view scrolls with a finger, the arrow keys and the wheel, and zooms with buttons, a menu, the plus and minus keys and control plus the wheel; a tap selects, and the keys edit. The interface is dense on a fine pointer and roomier on a coarse one.

Two more views draw the same project, and a switch of three icon buttons at the end of the toolbar chooses among them: the arrangement above, the score on a staff (drawn by abcjs, read-only), and the score text in a box where a person can write it. They are not tabs of separate documents: the project is one, an edit in the text shows in the other two, and one undo history covers all three.

The one authored move is the cut: when the score text stops before the song does, the part that was never written is hatched and edged with a dashed line, an "Incomplete bar" flag sits at the bar where it stops, and one sentence above the view says what that means. A hatch reads as "nothing here yet", which is the opposite of a rest (a gap). The rest of the surface stays plain on purpose.

**Key Characteristics:**

- No identity of its own: colours and type come from the host; defaults are neutral.
- Hairline structure: 1px lines, tonal fills, almost no shadow.
- Two densities selected by pointer type, not by screen width.
- Meaning never rests on colour alone: a cut is hatched and dashed, a tie is one joined bar, a selected note is framed, the insertion point is a heavier line with a flag, a missing chord track says so in words, a lyric phrase whose counts differ has a broken line and the word "differ" in its name.
- Editing is a state of the session, not of a part: every control and every gesture that edits is there only while `session.view.editable` is true, and the read-only view is the same view with those left out.
- Text that does not fit its cell is left out whole, never cut mid-word: a cut "Dm" would read as "D". The one exception is the text of a lyric line inside its phrase block (see Lyric track).
- Isolated styles: a host's element and class selectors do not reach in; inside a shadow root nothing does.

## Colors

The package states no palette. It reads ten theme variables and falls back to neutral values only where the host has not mapped one. The ten hex values in the frontmatter are those fallbacks, one pair per light and dark scheme; they are defaults, not a brand.

### The theme variable contract (normative)

A host maps its own theme onto these public variables, set on the editor's root or any ancestor. Names are stable. Anything else the package declares is private.

| Variable | Controls | Default when unmapped |
| --- | --- | --- |
| `--sce-color-bg` | Ground of the roll, button fill | `#ffffff` light, `#1b1c1f` dark |
| `--sce-color-text` | Text | `#18181b` light, `#ececee` dark |
| `--sce-color-surface` | Toolbar, header rows, track head, pitch column, popover | 5% of text mixed into bg |
| `--sce-color-muted` | Secondary text: bar numbers, octave labels, the Chords label, the empty-chord message, the badge | 66% of text mixed into bg |
| `--sce-color-line` | Hairlines: beat lines, row rules, panel borders | 13% of text mixed into bg |
| `--sce-color-line-strong` | Bar lines, the edges of section bands, marks and chords, the cut hatch, button and badge borders, popover border | 28% of text mixed into bg |
| `--sce-color-accent` | Focus ring, checked menu dot | `#2457d6` light, `#7da3ff` dark |
| `--sce-color-note` | Note fill | the accent value |
| `--sce-color-equal` | The wash and line of a lyric phrase whose syllable count equals its note-start count | `#2e8b4f` light, `#4cc27a` dark |
| `--sce-color-unequal` | The wash and line of a lyric phrase whose two counts differ | `#c79100` light, `#f0c040` dark |
| `--sce-font-family` | Font family | the host's inherited font |
| `--sce-font-family-mono` | Font family of the score text and its line numbers | `ui-monospace`, `Cascadia Mono`, `SF Mono`, `Menlo`, `Consolas`, `monospace` |
| `--sce-radius` | Base corner radius | `4px` |
| `--sce-row-height` | Height of one pitch row (and of a note) | `14px` fine pointer, `24px` coarse pointer |
| `--sce-beat-width` | Width of one quarter note at 100% zoom | `40px` |
| `--sce-keys-width` | Width of the pitch column | `44px` |

Defaults follow the host's `color-scheme` through `light-dark()`: a host that sets `color-scheme: dark` gets the dark values with no mapping at all.

**Derivation.** Surface, muted, line and line-strong are computed from the mapped background and text with `color-mix(in srgb, ...)` at the percentages above. A host that maps only `--sce-color-bg` and `--sce-color-text` therefore gets a coherent set of greys in any scheme, and every text colour keeps a contrast of at least 4.5:1 (a test maps only those two and checks the title, zoom value, bar numbers, section names, chords, marks, track names and octave labels). A host that maps one of the four greys overrides only that one. Do not add a variable for a derived grey unless a host proves the derivation fails.

**Private variables.** The `--sce-_*` names (`--sce-_bg`, `--sce-_text`, `--sce-_surface`, `--sce-_muted`, `--sce-_line`, `--sce-_line-strong`, `--sce-_accent`, `--sce-_note`, `--sce-_radius`, `--sce-_row`, `--sce-_beat`, `--sce-_keys`, `--sce-_shade`, and the row heights `--sce-_ruler`, `--sce-_band`, `--sce-_chords` and their sum `--sce-_top`, and `--sce-_head-top`, where the editor's track heads pin; for the lyric track `--sce-_equal`, `--sce-_unequal`, the row heights `--sce-_phrase` and `--sce-_syllable`, and `--sce-_view`, the width of the surface the track scrolls in, which the part keeps) are aliases that resolve the public variable or its default. They are not public: hosts must not set them and new work must not document them as an API. Per-instance layout values (`--sce-ticks`, the length of the score in ticks, on the canvas; `--sce-rows`, the pitch rows of a lane) and per-item values (`--t` start, `--d` or `--w` length, `--r` row and, for the selection box, `--h` height, all in ticks or rows) are set by the editor itself.

### The two state hues

Green and yellow cannot be derived from a background and a text colour, so `--sce-color-equal` and `--sce-color-unequal` are the only colours of their kind in the contract, each with a neutral default. A phrase takes the hue only through two derivations: its wash is 20% of the hue over bg, and its line is the hue pulled 70% toward text, so the text on the wash and the line round the block keep their contrast whatever the page's colours are (a test checks text on the wash at 4.5:1 and the line against the page at 3:1, in both default schemes). Neither hue marks anything but the lyric phrases.

### Neutral defaults

- **Ground** (#ffffff light, #1b1c1f dark): the roll and the button ground.
- **Ink** (#18181b light, #ececee dark): text.
- **Cool accent** (#2457d6 light, #7da3ff dark): focus and checked state; also the note fill unless a note colour is mapped.
- **Equal green** (#2e8b4f light, #4cc27a dark) and **unequal yellow** (#c79100 light, #f0c040 dark): the two states of a lyric phrase.

Derived values used by the build: black-key row shading and the tint of every second section band are 5% of text over transparent; a hovered button is 6% of text over bg and an expanded one 10%; a hovered menu item is 8% of text; a note's border is 30% of text mixed into the note colour; the selection box's wash is 8% of text over transparent, and the tint of a lane while a box is armed or open is 6%; the drop mark of a lyric line is 10% of text over transparent (14% of muted when the bar is taken), and the lane under a dragged line is 4% of text.

### Named Rules

**The Borrowed Colour Rule.** The package never names a colour outside the variable contract and its neutral defaults. A new surface takes its colour from an existing variable or a derivation from bg and text. One exception: where the system forces its colours (`forced-colors: active`) the page's own colours are replaced, so the editor's own marks that would otherwise vanish (the selection box, the drag outline, the edge grips on a selected note and the Grid button's dot) are drawn in the system keyword `CanvasText`, and the lyric track's phrases, guide line and drop mark use `Canvas`, `CanvasText` and `Highlight`; these are the colours the user agent gives, not ones the package picks, and the line style (solid or broken) and the count carry the lyric states. Under forced colours only system keywords show, and each of these marks is the editor's own rather than a fill the system repaints. The lyric track's two state hues are no exception: they are in the variable contract above, with neutral defaults.

**The One Accent Rule.** Accent marks focus and the checked menu dot; the note colour defaults to the same value. Nothing else is tinted but the wash and the line of a lyric phrase, which take the two state hues ([The two state hues](#the-two-state-hues)); the playhead of the synth preview is the text colour, like the insertion point.

## Typography

**Font:** the host's inherited family unless `--sce-font-family` is set. The editor ships no font and loads none.

**Character:** whatever the host's text looks like, set small and quiet so that notes and grid carry the surface.

Sizes are keyword-relative so the user's browser font size applies and a host's rem tricks do not distort the tool: the root is `small`, and every other size is in `em` of it. The header rows and the pinned track heads are sized in `em` too, so a larger browser text size makes them taller instead of clipping their text.

### Hierarchy

- **Base** (400, `small`, line-height 1.3): toolbar buttons, menu items, the cut sentence, the problem view.
- **Title** (600, `small`): toolbar title, the zoom value, chord names.
- **Chord readout** (600, `1.35em`): the name the chord picker will write.
- **Label** (`0.92em`): bar numbers, section names (600), marks, track names (600, 0.02em tracking), badge.
- **Numeral label** (`0.85em`): octave labels in the pitch column and the Chords label.

### Named Rules

**The Tabular Numbers Rule.** Every number that can change (bar numbers, octave labels, the zoom value, marks) uses lining, tabular numerals (`font-variant-numeric: lining-nums tabular-nums`) so numbers do not shift as the zoom changes.

**The Keyword Size Rule.** No `px` or `rem` font sizes. The root is a keyword; descendants are `em`. One exception: on a coarse pointer a field that opens a phone's keyboard is at least 16px, since a phone zooms the page when a smaller field is focused. That is the text view's box and its numbers, the toolbar's tempo, key and panel fields, the meter popover's two fields, the text fields of the lyric track, and the section form's fields at `max(16px, 1em)`. The rule is stated here once; each field's stylesheet points back to it.

## Layout

A single scroller holds a canvas. Its width is the pitch column plus the score's length at the current zoom (the length in ticks times the beat width, over 256 ticks to the quarter note, times the zoom). The scroller scrolls both ways. A header block is pinned to the top only while the lane under it keeps at least six rows: the bar ruler, the section bands, the marks row and the chord track, in that order. Otherwise the header scrolls with the lane and only the track head stays pinned. Under it each voice has a track: a track head (the voice's name) pinned below the header, a pitch column pinned to the left, and a lane. Time runs left to right whatever the page direction. A lane's height is its rows times the row height, with each octave being twelve rows; a voice's rows run from a margin of a few semitones below its lowest note to a margin above its highest, rounded out to whole octaves.

Structure from top to bottom: the chrome wrapper (`.sce-chrome`), which holds the toolbar part, the draft conflict strip when it stands, the cut sentence when the score is cut and the stale notice; then the body, which holds the header block, the tracks (`Vocal`, then `Ins` when present, then the lyric track) and the other views. The root fills its parent (`height: 100%`, minimum 288px) and clips overflow; the host decides the size.

**The music's floor.** In every state the body keeps at least the header's place, a track head and three rows: `--sce-_floor = var(--sce-_head-top) + var(--sce-_band) + 3 * var(--sce-_row)`. The chrome wrapper is capped at `calc(100% - var(--sce-_floor))` and scrolls inside itself when it has more to say. This is a floor, not a cap on the chrome: nothing in it is truncated, hidden or disabled. In an auto-height host the percentage caps to none, so nothing changes there. The three rows are a design judgement: one coarse note is a 24px tap target, and three rows show it with a neighbour on each side.

**The pin rule.** The header block is pinned only while `scroller.clientHeight` is at least the header's height, one track head and six rows; the six rows are a design judgement, about half an octave in the lane. Below that the root carries `data-pin="none"`, which sets `--sce-_head-top: 0px` and makes `.sce-top` static. The track head, the insertion point, the lyric head and the scroller's `scroll-padding` all follow `--sce-_head-top`, so they move together. A `ResizeObserver` on the scroller sets the attribute, synchronously before the opening scroll and again whenever the scroller's height changes; the same observer keeps the content at the centre of the lane window where it was, so chrome that appears or a header that becomes static does not move the notes out from under the person.

**The time axis.** Zooming sets the width of the elements that carry the axis (the canvas, the four header timelines, the lanes), by writing `calc(var(--sce-ticks) * var(--sce-_beat) * <zoom> / 256)` as their width. Everything placed on the axis (notes, bar numbers, chords, flags, bands, the cut, the grid) is positioned in percent of its axis element from its start and length in ticks. Do not hold the zoom in an inherited custom property: a variable that changes on the root restyles every note (about 70 ms per step at 1500 notes, against about 3 ms for widths). The zoom steps are 10%, 25%, 50%, 100%, 150%, 200% and 400% (1% to 400% reachable with the control wheel), and "Fit whole song" fits the score to the width shown.

The opening view is scrolled to the middle of the first voice's notes in pitch and to the first bar in time.

Density follows pointer type, not viewport width. A fine pointer gets the compact set; a coarse pointer (`pointer: coarse`) gets the larger one:

| Element | Fine pointer | Coarse pointer |
| --- | --- | --- |
| Row height and note height | 14px | 24px |
| Toolbar button minimum height, and the width and height of an icon button | 28px | 36px |
| Menu item minimum height | 30px | 40px |
| Section band row | 1.7em (22px at the default text size) | max(1.7em, 25px) |
| Lyric phrase block and the line it is read on (`--sce-_phrase`) | 2.3em | 3em |
| Lyric phrase handle, the hit area of an edge | 16px wide | 44px by 44px |
| Item of the unaligned list, its grip, and the fields of the editor | 28px high, grip 28px wide | 36px high, grip 44px wide; fields 16px type |

A host that maps `--sce-row-height` overrides both. Header rows at the default text size are 24px (ruler), 22px (sections), 22px (marks) and 26px (chords); track heads are 22px. Spacing is a small set used as seen: 8px gaps in the toolbar (4px on a coarse pointer, so the song row keeps its line at 412px), 12px toolbar side padding, 10px button side padding, 5px before the text of a flag or chord.

Touch behaviour: the scroller takes one finger for panning in both directions and leaves the page's own pinch (`touch-action: pan-x pan-y pinch-zoom`). A pinch does not zoom the time axis; the buttons and the menu do. A press that ends within 6px of where it began is a tap and selects; a press that moves farther is a swipe, and the browser keeps it as a scroll. The one exception is a finger that has rested on empty lane space for 0.4 s first, which draws a selection box (see Selecting several notes); the lane's `touch-action` is never changed, because the browser fixes it when the finger goes down. The lyric track keeps that rule: only a phrase handle and a grip have `touch-action: none`, so a swipe on a phrase, on the syllable row or on empty track space is a scroll (see Lyric track).

## Elevation & Depth

Flat by default, tonal layering for depth: the toolbar, header rows, track head and pitch column sit on the surface tone; the lanes sit on the ground tone. The only shadow is the popover's.

### Shadow Vocabulary

- **Popover** (`box-shadow: 0 8px 24px color-mix(in srgb, var(--sce-_text) 22%, transparent)`): the zoom menu in the top layer.

### Named Rules

**The Flat Rule.** Nothing has a shadow at rest. A shadow marks a floating layer.

## Shapes

Small, even corners. The base radius is 4px and comes from `--sce-radius`. Notes use the smaller of the radius and 3px. The popover uses the radius plus 2px. The read-only badge is a full pill (999px). All borders are 1px hairlines in the line colours; a note's border is 1px in a darker mix of the note colour. The zoom value button's chevron is a 5px rotated border corner, and the minus and plus buttons draw 10px by 2px bars with 1px ends, both in CSS and not glyphs, so no font is involved. The checked menu dot is a 6px circle.

## Custom tools

Custom tools are not view parts: they are pure data and a function, exported from the package entry, that the tool panel (a later view part) reads beside the editing session. The panel draws a tool's `name` in the session's language and one control per declared parameter: a number field with the declared `min`/`max`/`step`, a checkbox for a boolean, a menu of the declared `values` for a choice, and a text field for text. A parameter without a `label` shows its `name`. Every control starts at the declaration's `default`, so a tool can always run.

The panel previews with `previewTool` or `session.previewTool`: the returned project is the result, and a `tool-parameter` or step diagnostic is shown in the same inline place a refused command is. Previewing never writes to the session, so moving a control and reopening the panel cannot change the document or its history. Running calls `session.runTool`, which is one history step and therefore one undo; the panel returns to the preview after it. The registry is the only list the panel reads, so a host registers a tool once and the panel shows it without another wiring step. The tool layer adds no colours, sizes or nodes of its own; the panel uses the controls, focus ring and diagnostic text the rest of this document already specifies.

## Components

### View parts

The arrangement is built from view parts bound to one editing session: the toolbar (which holds Restore original while a keeper is ready and the editor is editable), the zoom control, the cut notice, the draft conflict strip, the handoff control, the problem view, the time ruler, the chord track, one voice track for each voice, the lyric track, the synth preview control and the Filter panel. Three views share the editor's frame: the arrangement, the staff view and the text view, chosen by the view switch, with the stale notice above the two that draw the project. The staff view, the text view, the stale notice and the view switch are parts of their own too. A host can mount any of them on its own element; the default editor mounts all of them in the layout described above (the draft conflict strip only while the host gave a store), except that it mounts the staff view and the text view the first time each is shown, so an editor that is never switched to them draws neither (the text view draws a number for each line of the score, about 150 nodes for the 128-bar sample, and the staff view asks for abcjs). Every part's root carries the same context as the editor's root (the theme variables, the reset, the text size) and is a stacking context of its own, so a part is styled and isolated alike wherever it stands; the decisions are in [the spike](docs/spike.md). The root is a `div.sce-root.sce-part`. Inside the default editor it draws no box (`display: contents`), so the layout above is the layout of the parts; mounted alone it is a block as wide as its element.

- **The time axis.** The ruler, the chord track and a voice track share the session's zoom and horizontal scroll. Zoom writes the same width formula as above on every part in one pass, and only then scrolls them, so the document lays out once. Mounted alone, each of the three is its own horizontal scroll surface (`overflow-x: auto`) whose scroll offset the session sets and whose user scrolling the session takes back, so parts of different widths scroll together and each stops at its own end without pulling the others back. The ruler and the chord track hide their scrollbar; a track shows it. A part that draws is a focusable region with a name, so Tab reaches it. Each of the three also keeps one polite live region (see Announcements) that survives every redraw. Zoom actions (the menu, the steps, "Fit whole song") measure the first part on the axis; control plus the wheel and the plus and minus keys measure the part that received them. The default editor puts all of its parts in one scroller and gives it to each as the `scroller` option, so none of them is a scroll surface there.
- **Pinning.** The default editor pins its header block, which holds the ruler and the chord track, above the tracks only while the lane under it keeps at least six rows; otherwise the header scrolls with the lane and only the track heads stay pinned. The rule is the `data-pin="none"` attribute set from a `ResizeObserver` on the scroller (see [Layout](#layout)).

### Toolbar

A view part of its own (`mountToolbar`); in the default editor it is the first row and draws no box of its own. Surface-tone strip, minimum 40px high, 1px line under it. Title at the start in 600 weight, the zoom group (minus button, zoom value button with a chevron, plus button), the history group (undo and redo), the Delete button, the pencil when asked, the Select button, the Grid button, the Bars menu and the meter control while the session is editable, a flexible spacer, and at the end the read-only badge while it is not. In the default editor the row has the view switch (the `viewSwitch` option of `mountToolbar`) after the read-only badge, then the tempo, key and transpose group and the Project button, and then the preview control and the Filter button, and the title names the shown view ("Arrangement", "Staff", "Score text"). The group and the button are described in [Tempo, key and transpose](#tempo-key-and-transpose) and [Song project panel](#song-project-panel). The handoff control is a word button after the Select and Grid buttons, before Restore original and the spacer; it is not part of `mountToolbar`, so a host that mounts the toolbar alone gets no handoff. The zoom group, the Delete button, the Select button, the Grid button, the Bars menu and the meter control mean something only on the arrangement, so they are hidden while another view is shown; undo and redo stay, since the text view's steps are on the same history. A toolbar that holds the synth preview control or the view switch wraps where its controls do not fit; one that holds neither keeps the title's whole text and scrolls sideways when the controls do not fit (`overflow-x: auto`, scrollbar hidden), so the title is never squeezed out of sight. The wrapping is one rule for both controls: a control moves to a later row before the title gets narrower than its own text (the title counts at the width of its text when the row is broken into lines), the read-only badge and the switch move together to a line of their own, right-aligned, and the preview control and its caption take the row after it (see Synth preview), so every control is in sight at 320px. A title that does not fit even on a row of its own is cut with an ellipsis; the element keeps the whole name as its text, and as its tooltip. Either way every control can be reached by finger or by Tab down to a 190px box, and no control is squeezed below its size (the icon buttons keep 28px, 36px on touch) to make room. The history group, the Delete button, the Select button, the Grid button, the Bars menu and the meter control are hidden with the editing, and with the view when it is not shown (an unreadable score, no dialect). The screen-reader hint is the one sentence a view's `aria-describedby` points to; it is in the toolbar part, drawn only when the host gives it an id, and names the editing keys only while the session is editable. The Filter button is last of the editing controls, after the preview control (see Filter panel). The pencil toggle sits after Delete and before the Select button (see Placing notes). The preview control comes before it, unless the host turns it off with `synthPreview: false` (see Synth preview); where the row has the view switch, the control comes after the badge and the switch, in the drawing and in the Tab order: undo and redo, Delete, the pencil when it is on, the Select button, the Grid button, the Bars menu, the meter control, the handoff trigger when the host gave a callback, Restore original while a draft is kept, the three views, the tempo, key and transpose group, the Project button, the preview, and the Filter button. Bars and Meter sit directly after Grid, before the view switch, in the DOM, on screen and in the Tab order alike; no `order` rule draws them elsewhere. The switch comes first because a text typed into the text view is taken as its box loses the focus, which can be the press on the switch, and that moment makes the history group and the preview control appear. Nothing that comes after the switch can move it to a later line, and the history group, which comes before it, is small enough to leave it on its line down to 320px. The preview control is the widest item and, where it shares the line with the switch, would push the switch along it, so in a toolbar with the switch it keeps its place while it is not there: hidden from assistive technology and from the Tab order, with its width kept. A press on the switch right after typing, at a phone's width, in a 320px box and in a wide one, lands where the person aimed it (seam 5 checks the switch's position before and after the text is taken, in English and in Chinese).

The Grid button (74px at 412px, next to the Select button) takes room from the title as well. A bare toolbar at a phone's width, with neither the preview control nor the view switch, was already full at 412px with the title down to 1px; with the Grid button the title has no room at all, is still in the document with its tooltip, and the row scrolls sideways to the controls as it is designed to. The default editor, which wraps, puts the Grid button on its second row beside the Select button.

### Undo, redo and Delete

Two square icon buttons in a group named "History", after the zoom group: the same ground fill, 1px strong line and 4px radius as the zoom steps, 28px (36px coarse), with a 16px arrow that turns back on itself in a 1.5px stroke (redo is the same drawing mirrored). The arrows are polylines in an inline SVG styled from the stylesheet, so no font and no glyph is involved; a path would not do, because the reset reverts the `d` property of a path. Each has an accessible name ("Undo", "Redo") and a tooltip that also names its keys ("Undo (Ctrl/Cmd+Z)", "Redo (Ctrl/Cmd+Shift+Z)"). A button with nothing to do is `aria-disabled` and muted, as a zoom step at its end is, and does nothing when pressed. The keys are Ctrl or Cmd plus Z (undo), Ctrl or Cmd plus Shift plus Z and Ctrl plus Y (redo), and work with the focus anywhere inside the part that hears them.

The pencil is a fourth icon button of the same kind, after Delete and before the Select button: a 16px pencil in 1.5px polylines, named "Draw notes" ("画笔") with the tooltip "Draw notes (B)". It is opt-in (`ToolbarOptions.pencil`), so a bare toolbar gains no control or tab stop; the default editor turns it on. After the merge put Bars, Meter and the handoff trigger in the row, the end of the row added a phone row at 412px, so the pencil sits in the edit cluster where it adds none at that width. It is a mode, so its on state is the view switch's: a 12% text fill, a text-colour border, and a 2px icon stroke, with `aria-pressed`; it is never carried by hue. It is hidden with the other editing controls and with the arrangement. Measured in Chromium here, it adds no height at 412px with either pointer and none at 320px with a mouse; at 320px with touch it adds one row (285px to 325px), where the toolbar is already deeper. The later change to a two-row phone toolbar absorbs that; no other control was moved for height.

Delete is a third square icon button of the same kind, after the history group, with a bin drawn in the same 1.5px polylines (a lid with its handle, then the body). It is the pointer and touch path to what the Delete key does, since a phone has no key and double tap is a later gesture: it turns every selected pitched note into a rest as one history step. Its name is "Delete" and its tooltip "Delete (Del/Backspace)". It is `aria-disabled` and muted, like a history button with nothing to do, until a pitched note is selected, and a forced press then does nothing; after a delete the selection holds only rests, so it mutes again, and undo brings the note back selected and the button with it. It has no colour of its own: the action can be undone, so it is not drawn as a danger. When the score refuses the edit, the toolbar's live region says why and where.

### Select menu

One text button after the Delete button, labelled "Select" ("选择"), with the chevron of the zoom value button, and a native popover menu under it (the zoom menu's mechanics, shared in `popover-menu.ts`: top layer, Arrow keys, Home and End walk the items, Escape closes and returns the focus to the button) holding three items: "Select all", "Invert selection" and "Clear selection". It is the pointer and touch path to Ctrl or Cmd plus A, Ctrl or Cmd plus Shift plus A and Escape, because a phone has no keys, and each item's tooltip names its key. Choosing an item closes the menu and then does what the key does, through `handleEditingInput`. An item with nothing to do is `aria-disabled` and muted, as a history button is, and a forced press does nothing: Select all and Invert when the score has no pitched note, Clear when the selection is empty. The button has the same ground fill, 1px strong line, 4px radius and height as its neighbours (28px, 36px coarse) with 8px of side padding, and it is hidden with the other editing controls, and with the arrangement when the staff or the text is shown, since only the arrangement has notes to select. It announces nothing itself: the voice tracks say "Selected N notes".

Why one menu and not three icon buttons: three pictograms that a person must tell apart, with no word on them, in a row that already overflows a 412px phone, against one named button that a translation covers and that has room for a later entry. Logic Pro for iPad offers Select All and Invert Selection from a menu in the same way (cited under Selecting several notes). The cost, accepted: select all takes two taps. The button also takes room from the title, which gives way first: in the default editor at 412px the title is cut to about 25px in English and 33px in Chinese (measured in Chromium).

### Grid menu

One button after the Select button, drawn as three upright lines (the lines a note snaps to), the grid in force as a fraction ("1/4") and the chevron of its neighbours; a dotted grid has a 3px dot after the fraction, the dot of a dotted note, and is named in words for assistive technology ("Grid: Dotted 1/8"). Its tooltip says what the grid is for: the step that notes move and resize by and that the insertion point snaps to. It opens a native popover menu (the zoom menu's mechanics, shared in `popover-menu.ts`) of radio items: 1/4, 1/8, 1/16 and 1/32, a rule, then the same four dotted. The item in force is checked and takes the focus when the menu opens, and choosing an item sets the session's grid (`setGrid`) and closes the menu. 1/32 and dotted 1/32 are in the menu only for a score whose unit can write 1/32, since a score counted in sixteenths has no number for a thirty-second (the check is `allowsGrid`, which asks the same function the note commands ask), or while 1/32 is the grid in force; any other step the score cannot write is muted (`aria-disabled`, with a tooltip saying so) and choosing it does nothing, as an item of the Select menu with nothing to do. Home and End and the Arrow keys skip an item that is left out. The button is hidden with the other editing controls, and with the arrangement when the staff or the text is shown.

The grid is the session's view state and not a part of the song: a choice is not an undo step, and a host that makes its own control reads and sets `session.grid`. It starts at 1/4, so a quarter note in 4/4 is the step it was before there was a grid. Every line of a grid is counted from the start of the score, as the note commands count them, so in 6/8 a 1/4 grid has a line on every second eighth from bar 1, whatever the bar.

Why a menu of a dozen words and not a slider or a pictogram row: the values are a closed list of named things that a musician already reads as fractions, the button shows the one in force at a glance, and the menu has room for the translation and for a later entry. Why the plain values come before the dotted ones: a dotted step is the exception and shares its number with a plain one. The cost: a change of grid takes two taps, and a phone that wants a finer step for one note takes them twice.

### Bars menu

A text button drawn after the Grid menu, labelled "Bars", drawn as Select is (28px, 36px coarse, 8px side padding) and carrying the same chevron. It opens the shared popover menu with four items and a hint line above them: "Click a bar number, or tap one and then another" ("单击小节号，或先后点按两个小节号"). The hint is visible text, not a tooltip, because a finger cannot hover. "Choose bars" puts the choice on the insertion point's bar (the first bar when there is none) and gives the ruler's bar number the focus, so the keys can go on from there. "Insert bar before bar N" (or "at the end") acts on the insertion point, and `deleteBars` acts on the chosen run: "Delete bars 3 to 5" or "Delete bar 3". While there is no insertion point the Insert item is muted, and its own label says the way in: "Insert bar (click a lane first)" ("插入小节（先单击一条轨道）"). An item with nothing to act on is `aria-disabled` and muted, and a forced press does nothing, as the Select items are. "Clear bar selection" empties the run. A successful insert or delete is said in the toolbar's live region; a refusal is said there, reaches `onRefused`, and stays as a line of its own at the foot of the menu until the next successful action or the next project change. The menu is left out while the session is read-only or another view is shown.

### Meter control

A text button after Bars, labelled with the target section's meter ("Meter 2/4"), with the same make as its neighbours and the same chevron. The target is the section of the first chosen bar, else of the insertion point's bar, else the first section; the button's tooltip names it ("intro, bars 1 to 4"). Its popover is a native popover in the dialog role, because it holds a radio list and fields rather than a plain menu. It uses the shared placement (`placeUnder` with a `maxHeight`, then `keepInside`): it stays inside the window at 412x420 and scrolls inside its own box, so it adds no placement rule of its own. The summary names the section as its band does, and a line under the choices says what the change does to the bars before Apply: "At 4/4, bars 1-4 become bars 1-2; later bars renumber. Notes stay where they are." ("改为 4/4 后，第 1–4 小节变为第 1–2 小节；后面小节会重新编号。音符位置不变。") The same sentence is said on success. A grid of radio items offers the common meters `meterChoices` allows, with the current one checked even when it is not common; the choices are one Tab stop with a roving `tabindex`, the Arrow keys move and check, and Enter or Space checks and then Apply submits. A custom row offers "Beats per bar" and "Note value" fields and Apply, so every meter the dialect's `constraints.meter` accepts is reachable; those fields are 16px on a coarse pointer, as the Keyword Size Rule says. A field is bounded by that rule, and a value the command still refuses leaves the popover open and is said as its diagnostic in a line of its own at its foot, in the toolbar's live region and through `onRefused`. The control is hidden while the session is read-only, has no score, or shows another view.

### Zoom controls and menu

- **Buttons:** ground fill, 1px strong line, 4px radius, 28px high (36px coarse). The step buttons are square (28px or 36px). Hover darkens by 6% of text; expanded state 10%. A step that has nowhere to go is `aria-disabled` and muted.
- **Value button:** shows the zoom as a percentage in 600 weight and opens the menu; its accessible name is "Zoom 100%" and it carries the popover's expanded state.
- **Popover:** a native popover (`popover="auto"`), so it lives in the top layer and stacks above a host's full-screen layer. Surface fill, 1px strong line, 8px/24px shadow, positioned under the button with an 8px margin from the window's edges, or from the width the page lays out in when that is narrower: it is nudged left when it would run off the right, and when it would run off the bottom it is put above its anchor if it fits there, else it keeps its top 8px from the window's top, with a max-height to the bottom margin and its own scroll. A layer that grows after it opens keeps its top and moves up only as far as the bottom edge needs.
- **Menu items:** radio items for the presets, a rule, then "Fit whole song" as a plain item. A 6px dot at the start marks the checked preset in the accent colour; hover is 8% of text. Arrow keys, Home and End walk the items; Enter or Space picks; Escape closes and returns focus to the button.
- **Keys and wheel:** `+`, `=` step in; `-`, `_` step out (on the focused view); control plus the wheel zooms smoothly around the pointer, and stops the page from zooming itself.

### Ruler and bar numbers

A 1.85em row (24px at the default size). Each bar number sits at the left edge of its bar in muted text, with a strong line at its left; every number is named "Bar N" ("第 N 小节"), with ", selected" ("，已选中") when it is in the chosen run, and carries a title with the same words, so a mouse finds the handle before pressing. When bars get narrow the numbers thin out: only every 2nd, 4th, 8th, 16th or 32nd bar is numbered (the smallest power of two that leaves the coarse hit area between numbers), and the first is always shown.

**Choosing bars.** A bar number is the handle that chooses its bar. A click on it chooses that bar; a mouse press on the number and a drag across the ruler chooses the run from the first bar to the bar under the pointer, and Shift at a click extends the current run instead of replacing it. A mouse click deliberately leaves the focus alone, so it draws no focus ring. A finger taps the first bar and then the last to choose a run; the first tap says "Bar 1 chosen; tap another bar to extend" ("已选第 1 小节；再点按另一小节可扩展"), and the Bars menu's hint says the same before the gesture. A swipe on the ruler still scrolls, and a number does not claim the touch: the tap is read on the click, so a finger that moves scrolls as it would anywhere else. The chosen run is drawn as a full-height band over those bars, in the ruler and through every lane: an 8% text wash with a 2px text-colour edge at each end, under the numbers and under the notes; the chosen numbers change from muted to the text colour and 600 weight, so shape and weight carry the state. The lane band takes no pointer events, so a press or swipe on it reaches the notes and the lane as before. A chosen number's name is "Bar 3, selected" and the ruler's live region says "Bars 3 to 5 selected". The choice is `session.barSelection`, a separate UI state from the note selection and outside the history; a project change clears it. With the focus on a chosen number, Left and Right move the run one bar, Shift with either extends it, Home and End go to the first and last bar, Enter or Space chooses the focused bar, and Escape clears the run; the Bars menu's "Choose bars" is the keyboard way in, and it puts a visible focus ring on the number. On a coarse pointer a number takes the 36px control size of the density table, and the visible numbers are at least 36px apart because the thinning uses that number, so the larger target does not overlap.

### Section bands

A 1.7em row (25px on a coarse pointer). One band per section that has bars, from its first bar to the next band, with a strong line at its left and its name in 600 weight pinned to the left edge of the visible part. Every second band is tinted. Music before the first marker is named "Unnamed" ("未命名"); a marker with no bars after it draws nothing. While the session is editable a band opens the section menu (see Section menu).

### Marks row

A 1.7em row of flags. The first flag shows what is in force at the start (meter and key); each later flag stands where a meter or key change takes effect, which for a key change may be inside a bar. A flag has a strong line at its left, 5px of padding and its items in a row ("4/4", "Key D"). The items stay at the pitch column's edge while the flag's stretch is scrolled past, so the key and meter in force are always readable; they never leave the flag's stretch. The last flag of a cut score carries "Incomplete bar" or "Cut off" (see The cut). A flag too narrow for an item leaves that item out whole.

### Chord track

A 2em row labelled "Chords" in its corner. Each chord's name in 600 weight at the position where the score writes it, running to the next chord, with a strong line at its left. A chord name that does not fit its width is left out whole. A score with no chords shows one muted sentence, "No chords in this score", pinned at the left, instead of an empty row; while a press on the row places a chord, the sentence goes on with how ("No chords in this score. Click or tap a beat to add one."), so a person who cannot hover finds the gesture, and a read-only editor says only that the row is empty. While the session is editable a press on the row places, changes or removes a chord; that is [Chord editing](#chord-editing), below. Where a dialect lets more than one voice carry chords, the track keeps one place per tick: the cursor and placing use the voice listed first, a chord on another voice is reached by pressing its name, and a chord at the same start as a later chord has no width of its own.

### Track, lane and grid

A track is its head (the voice's name, 22px, pinned under the header), the pitch column and the lane. The pitch column labels each octave (C4, C5) in muted text, bottom-aligned on its C row. Black-key rows are shaded with 5% of text. The grid is drawn in each meter run of the score: a strong line at every bar start and a light line at every beat of the bar's own meter (a quarter note in 4/4, an eighth in 6/8), as gradients, so a line costs no node. Beat lines are dropped when beats are closer than 12px, leaving the bar lines; bar lines are dropped too when bars are closer than 10px (a whole long song fitted to the width), leaving the ruler's numbers and the bands to carry the structure, because a line every 5px is a comb over the notes.

### Selection

A selected note is framed by a 2px border in the text colour in place of its 1px border, with the fill unchanged; the frame sits inside the box, so nothing moves and no neighbour shifts. A tied chain is selected as a whole, since Delete takes the whole chain: the sides where its segments join keep no border, so the frame runs round the chain as one bar. A selected note's label ends with ", selected" ("，已选中" in Chinese). Shape and weight say the state, not hue, so it reads in any host palette. Measured with the neutral defaults, the frame is 14:1 or more against the lane and 2.9:1 (light) or 2.1:1 (dark) against the default note fill, so the outer edge carries the state; a host that maps a note colour close to its text colour is left with the 2px weight alone. While the session is editable the browser's own tap highlight is turned off, since the frame answers a tap. Only a pitched note is selectable: a click or tap on a note selects only it, a click or tap on empty lane space clears the selection. A note shows the pointer cursor only while the session is editable, and the move cursor once it is selected (Moving and resizing). Selecting several notes is the next section.

### Selecting by keyboard

Notes are reached the way an option is reached in a listbox (the roving tabindex of the WAI-ARIA authoring practices): exactly one note of a voice track is in the tab order, the selected note or else the first, so Tab enters the notes in one step and the next Tab leaves them. Moving from note to note follows a score editor, not a pointer: with a note in focus and no note selected, Left and Right step to the previous and next note of the voice and select it, Home and End go to the first and last, and Enter or Space select the note in focus (the way in when Tab has just arrived, because arriving does not select). Selection follows the stepping so that the ring and the frame are always on one note and Delete never acts on a note other than the one the eye is on; it costs nothing here, since selecting does no work that a slow step would repeat. A tied chain steps segment by segment and is framed whole, as it is when clicked. The stepping stays quiet in the live region, because the focus already speaks the note it lands on; Enter and Space say what they selected.

The keys belong to the notes only while a note has the focus. With the focus anywhere else in a part and no note selected, Left, Right, Home and End still move the insertion point or scroll as before. A key with a modifier is taken by the notes only in the two forms of the paragraph "A subset from the keyboard" below (Ctrl or Cmd with the four stepping keys, Shift with Enter or Space). Any other is left alone by the notes: Alt with any key, Ctrl or Cmd together with Shift, Ctrl or Cmd with Enter or Space, and Shift with Home or End. Shift with the arrows is an editing key (Moving and resizing), and Ctrl or Cmd with A and Escape belong to selecting. A click or tap puts the focus on the note it selects, so the keys go on from there; it is the browser that moves the focus for a tap, because a focus moved by script before it would count as keyboard focus and draw the ring. A note the keys step onto is scrolled out from under the pinned header, the track head and the pitch column (`scroll-padding` on the scroller, with 4px for the ring), not left half hidden where Delete would act on a note the eye cannot see; the left edge of the ring of a note at the very start still goes under the pitch column. A redraw that removes the note in focus (a delete, a language change) gives the focus to the same note if it is still drawn, else to the next and then the previous note, else to the track, so the history keys keep working; a note that has the focus keeps the tab stop when the selection is changed from elsewhere. Notes are focusable only while the session is editable.

Once a pitched note is selected the plain Left and Right are editing keys and not stepping keys, which is what the editing keys changed in this section: stepping with them selects each note it lands on, so one press would have walked and the next would have moved the note it had just selected. The walk goes on with Ctrl or Cmd and the arrows, which move the focus without selecting (and show the focus ring, since a key moved it), and Enter or Space selects the note in focus. The first plain press on a note with nothing selected still steps and selects, as it did. The cost is a habit: a keyboard user who walks the notes with the bare arrows and then keeps pressing them moves the note they stopped on; the key map under Moving and resizing is where each key is listed.

The notes keep the role of list items. A focusable list item is not the pattern an assistive technology expects of a selectable option (a listbox with `aria-selected`), and the label ending in ", selected" does the work of that state. The move to a listbox is deferred; the reason is under Roles in the next section.

### Selecting several notes

The selection frame does not change; a selection of many notes is many framed notes, with no counter and no control added. Three things are added to the lane: a box, a preview and a cue.

**Gestures.**

| Input | Mouse and pen | Touch |
| --- | --- | --- |
| Click or tap a note | Selects only it. | Same. |
| Shift held on a click or tap on a note | Adds it, or takes it out when it is selected, with its whole tie chain. | Shift on a keyboard attached to the screen does the same; without one, rest a finger on the note for 0.4 s. |
| Press on empty lane and move more than 6px | Draws a box; Shift at the press adds to the selection. | Rest a finger on empty lane for 0.4 s, then slide: the box is drawn. A swipe that starts at once still scrolls. |
| Click or tap empty lane | Clears the selection and drops the insertion point, as before. | Same. |
| Shift on empty lane | Nothing: an aimed click that misses must not cost the selection. | n/a |
| Let go of the box | Selects the pitched notes it touches (a tie chain whole); a box over no note clears the selection, and with Shift leaves it. | Same. |
| Escape while the box is open, `pointercancel`, the page losing the focus, the editor turning read-only, a second finger | The box is given up and nothing changes. | Same. |

A box is hit-tested in ticks and rows, not per note rectangle, so it costs one pass over the voice's notes at any size; it is kept inside the lane, and its corner stays on the same bars and pitches when the track scrolls under a pointer that stays still (the wheel during a mouse box). A press that starts on a note never draws a box: it is a click, or a drag that does nothing, as before. A press that starts on a selected note and moves is the start of a move (Moving and resizing), and a hold that has toggled a note is not.

**The box.** A 1px dashed outline in the text colour over an 8% wash of it, above the notes (`z-index: 3`), taking no pointer and hidden from assistive technology. Dashed says "not chosen yet", and the committed state is the solid 2px frame the notes already have, so the pair reads by shape and weight and in any host palette. While the box is open the notes it touches already wear the selected frame (`data-boxed`, the same look as `data-selected`, a tie chain included), so the result is seen before it is committed; their accessible names change only on release, so nothing is announced per move. A finger that rests on empty lane has no box yet and covers the place it rests on, so the moment the hold is recognised (0.4 s) the box exists as a marker: a 56px dashed square, larger than a fingertip, centred on the finger (`data-anchor`), and the device buzzes for 10ms where `navigator.vibrate` exists and the page has been touched before (the browsers insist on that). The first slide turns the marker into the box. The lane is also tinted by 6% of the text colour while a hold is armed or a box is open (`data-boxing` on the lane), so the state is seen away from the hand; that tint alone, at 4%, measured about 1.1:1 against the lane and was too quiet to be the cue, which is why the marker carries it. Where the system forces its colours (`forced-colors: active`) the box is a 2px dashed `CanvasText` outline with no wash. There is no motion and no shadow.

**Why a hold, and not a mode or a second finger.** The rule above is that a swipe on empty space scrolls, and the lane's `touch-action` is `pan-x pan-y pinch-zoom`, which the browser fixes at touch start (W3C Pointer Events, `touch-action`), so no later movement can turn a started scroll into a drag. Touch-and-hold is the gesture touch editors use for this: Apple's Logic Pro for iPad User Guide, "Select notes in the Piano Roll Editor" (https://support.apple.com/guide/logicpro-ipad/select-notes-lpip83b30b30/ipados: touch and hold the working area next to the first note and drag across the notes; a Select mode that taps notes in and out, which holding the Shift key of an external keyboard gives momentarily; Select All and Invert Selection from a menu) and the Material Design 1 Selection pattern (https://m1.material.io/patterns/selection.html: the selection gesture is a long press held in place for a moment, and to select several items one long presses and drags). A toolbar mode toggle was left out: it needs a state shared between the toolbar and the track (`ViewState` has a fixed shape that existing tests pin), another control on a row that already scrolls sideways on a narrow host, and it makes a swipe on empty space mean two things. The mechanism was tried before it was built: in Chromium, driven by CDP touch events (a throwaway probe, not kept in the repo), a finger that rests and then moves is cancelled by the browser and scrolled (`pointercancel`), unless a non-passive `touchmove` listener that exists from the start cancels the move once the hold has armed the box; with one, the pointer events go on to `pointerup`, and a quick swipe still scrolls. The listener is on the voice track's root and calls `preventDefault` only while a hold has armed or a box is open. WebKit and Gecko were not run. A hold that is lifted without sliding does nothing (it is not a tap), so a hesitating user cannot lose the selection; the browser's own menu on a long press is suppressed while a hold is pending. A resting thumb may drift 10px before the hold is lost (a mouse press 6px); a hold arms nothing once the editor is read-only or the lane was redrawn meanwhile.

**Keys.** The selection keys are in the key map under Moving and resizing (The keys). Escape is handled whenever the selection is not empty, whatever its ids name (after a Delete they name rests, and Escape must still clear them), so a host's own use of Escape (closing a panel) keeps working while the selection is empty; while a box is open Escape belongs to the box, in the capture phase of the document or shadow root, because the focus may be on the scroller above the track. While the focus is inside the editor the keys are kept from the browser, so the page's select all does not run (checked in Chromium: outside the editor Ctrl+A selects the host's text, inside it selects notes and no text). Ctrl or Cmd plus Shift plus A is the browser's own tab search or add-ons shortcut in some browsers, and a page may not be allowed to take a reserved shortcut: this was not checked in a headed browser. The Select menu is the way for a finger, and for a person whose browser keeps the key; a host may also send `invert-selection` to `handleEditingInput` from a control of its own.

**A subset from the keyboard.** With a note in focus, Ctrl or Cmd plus Left, Right, Home or End move the focus as the plain keys do and leave the selection as it is, and Shift plus Space or Shift plus Enter adds the note in focus to the selection or, when it is selected, takes it out with its whole tie chain, as Shift-click does; plain Space and Enter still select only that note. Sources: the WAI-ARIA Authoring Practices listbox pattern (https://www.w3.org/WAI/ARIA/apg/patterns/listbox/), in its model for a multi-select list that needs modifier keys, moves the focus with Control plus the arrows "without changing its selection state" and changes the state of the focused option with Control plus Space; its Shift plus the arrows toggle as they move. Both differ here for a reason. Shift plus the arrows are taken by the editing keys (octave and length). Ctrl plus Space and Cmd plus Space are not usable on macOS, where Command-Space shows or hides Spotlight and Control-Space selects the previous input source (Apple, "Mac keyboard shortcuts", https://support.apple.com/en-us/102650), so the toggle is Shift plus Space, with Shift plus Enter beside it for the key that already selects. Collision check against the keys listed in The keys: none uses Ctrl or Cmd with an arrow, or Shift with Space or Enter. A key the browser reserves was not checked: Cmd plus Left and Right is history back and forward in some browsers on macOS, and this was not run on a Mac; where it is taken, plain Space selects one note and the box and the Select menu build the rest.

**What stays selected.** The selection is note ids, and a note that becomes a rest keeps its id: after Delete the ids stay selected (as rests, which are drawn as nothing and left out by select all), and an undo brings the notes back framed. Delete takes every selected pitched note as one command, one history step, with one write and one check; if the score would refuse any of it, nothing changes and the selection stays. One check on the whole result cannot say which note caused a refusal, so a diagnostic with no place of its own is located at the first note the command names, which for Delete is the first selected note in score order.

**Read-only.** Every gesture and key above is gated on `view.editable`, like the rest of editing, so a read-only track has no box, no toggle and no selection key. `session.select(ids)` is left open on purpose: a host's own panel that selects notes by a filter and stays usable while the editor is read-only selects through the session, and the track draws no frame for it while read-only, as it did before the selection gained its frame; it comes back when the editor is editable again.

**Announcements.** The live region of a voice track says "Selected 5 notes" after a box, a toggle, a select all or an invert, through the announcement that already followed the selection; a box that is open, a cancel and a clear say nothing (a clear is announced by the notes' own names).

**Roles.** The notes keep the role of list items, named "..., selected". The listbox with `aria-multiselectable`, which several selected notes would make the right pattern, is deferred and not done here: the existing tests pin the list and list item roles and must stay unchanged, so the move waits for a change that brings its own tests. This is the one place the deferral is said.

**Screen reader and keys.** The hint that the scroller is described by (`hintEditing`, English and Chinese) names the new gestures and keys in one added passage. The passage covers the box, the hold, Ctrl and A, Escape, and the keys of a subset. A keyboard user can select all, invert and clear, reach one note at a time, and build any subset with the keys above.

**Known gaps.** No auto-scroll while a box is dragged to the edge of the view (the wheel scrolls during a mouse box, and "Fit whole song" shows everything for a touch box). A replacing box does not show the old frames going away until it is let go (a box, like a click, replaces; Shift adds). No visible count of the selected notes: a sighted user sees which notes are framed but not how many, or the ones off screen, where a screen reader hears "Selected N notes" per voice; a count beside the Delete button is the likely answer and belongs with the toolbar. Clearing, giving a box up and the selection falling to zero are silent in the live region. A sixteenth note at 100% zoom is about 10px wide, so a hold meant for it can land beside it and arm a box instead; the 56px marker makes that visible, and a larger coarse-pointer hit area would change how a tap on a note behaves, which this change leaves alone. One finger only: a second finger gives the box up. Chromium only: touch was driven by synthesized CDP touch events in an emulated phone, not on a device, and Safari and Firefox were not run.

### Moving and resizing

Moving and resizing the selected notes have three ways in, and each is one command and one history step: the drag, the arrow keys and Shift (below), and the same `move-notes` and `resize-notes` inputs of `handleEditingInput` that both of them send, so a host's own view can send them too. The grid (see Grid menu) is the step of all three, and every result lands on it. The editor calls `moveNotes` and `resizeNotes` and redraws from what they return: a note that a drop covers disappears or is shortened as the command says (a note whose start is covered goes, a note whose end is pressed on is made shorter), and nothing here predicts it.

**Gestures.**

| Input | Mouse and pen | Touch |
| --- | --- | --- |
| Press on the body of a selected note and move more than 6px (10px for a finger) | Carries the whole selection by the distance covered, in time and pitch: a row is a semitone, and the start lands on the grid. | Same, from the first slide: the browser keeps its hands off a selected note (see Touch). |
| The same press with Alt held | Carries copies of the selection, not the selection: the release writes the copies where the ghost is, leaves the originals, and selects the copies. | Same, with an attached keyboard's Alt; a finger alone has no Alt, and the keys of a subset still select. |
| Press on an edge zone of a selected note and move | Moves that edge of the note, or of its whole tie chain, to the grid; the other edge stays. | Same. |
| Let go | Sends one `move-notes` or `resize-notes` input; the selection goes with the notes to their new places. A drag that has come back to where it began sends nothing. | Same. |
| Escape, `pointercancel`, the page losing the focus, the editor turning read-only, the lane being drawn again | The drag is given up: the ghosts go, nothing changes, and the selection is kept (Escape does not clear it). | Same. |
| Press on a note that is not selected and move | Nothing: a drag on an unselected note does nothing, as before. | The slide scrolls the lane, as before. |
| Rest a finger on a selected note for 0.4 s | n/a | Takes it out of the selection, as a hold does on any note; a slide that starts before the hold is over carries the notes. |

**Edge zones.** The zone at each end of a selected note is 6px wide for a mouse. A finger or a pen gets the wider 12px zone, narrowed on a narrow note to 30% of the note's inside width, but never below an 8px floor. The grips drawn in the zone use the same numbers, the same share and the same floor (they are constants in `note-drag.ts`, which the stylesheet reads, and the hit test computes the same width from the same box). They are two layers of the note's own background, each 2px wide and centred in its edge zone, and a clamp on their width opens them only when the note's inside width is at least three zones, 18px with a mouse and 24px with a finger. That decision is made when the background is painted, so no selected note is a size container and no mark changes on a zoom: a zoom neither restyles nor measures a note. A mouse over an edge zone shows the resize cursor: the track asks `grabAt`, the same hit test a press uses, and marks the one note under the pointer, then takes the mark away when the pointer leaves that note or the lane. Under forced colours the grips are drawn once more on a pseudo-element in `CanvasText` that opts out of the system's repaint. Measured on the phone project, a quarter note at the default zoom is 34px inside its frame: the share gives it two 10.2px zones and 13.6px of body, so a finger can resize it without zooming in. A note narrower than three zones inside its frame has none and is all body, so a small note can always be moved and never resized by a slip: 18px with a mouse and 24px with a finger, so at the measured phone zoom an eighth and anything shorter are all body with either pointer, and a quarter keeps two zones with a finger. A note that continues into a tied note has no zone on that side, so a chain is resized from its two ends only, and its middle is body. The coarse zone stays below the 24px that WCAG 2.2 asks of a target (2.5.8), and it is not larger because a quarter note would have no body left to move it by; the same resize is offered by Shift and the arrow keys, which a phone does not have, and a wider touch handle is left for a change that takes on the touch target as a whole. Measured, a half note is 80px wide at the default zoom: the 12px zone is 15% of it at each end.

**What the drag shows.** The notes wait where they are, at 55% opacity, and a 2px dashed outline in the text colour marks where each tie chain of the selection would land: the box's dashed-for-not-yet-chosen language, in a heavier line. The outline is where the commands' own arithmetic puts the note (`landing`, the one function `moveNotes` and `resizeNotes` and this drag share), so it shows the snapped place and not the pointer's; it is drawn in every voice track that holds a selected note, through a channel the session shares (`dragChannel`), since a selection can span voices and each track draws its own notes. It takes no pointer and is hidden from assistive technology. The pointer is kept inside the lane: time stops at the ends of the score, and pitch at the lowest and highest row the lane draws, so a note that must go beyond them takes the keys (Shift and Up or Down is an octave). It does not preview a refusal: a drop the score cannot take is refused on release, the notes stay where they were, and the track says why in its live region ("The note would end past the end of the score.") and hands the diagnostic to `onRefused`, which the default editor turns into a `command-refused` notice for the host, as for every other refused command; the parts draw no notice of their own. The cursors: the move cursor over the body of a selected note, the resize cursor over its zones, and one cursor on the whole lane while the notes are carried (`grabbing`, or the resize cursor for an edge); forced colours keep the outline in `CanvasText`, draw the grips in it too (they opt out of the system's repainting, which drops a gradient from a fill it repaints) and draw the Grid button's dot in it.

**Touch.** The lane's `touch-action` stays `pan-x pan-y pinch-zoom`, so a swipe on empty space or on a note that is not selected scrolls, as the box section requires. A selected note alone has `touch-action: none`, which the browser fixes at the touch start: the note is already selected when the finger comes down, since the selection came first. A slide that starts on it is the drag's and not a pan, with no hold and no second gesture to learn; a non-passive `touchmove` guard cancels the scroll while a drag is open, as it does for the box.

**A note across a bar line.** The score holds it as two tied notes, split at the bar line (the command writes the split and the tie), and the screen draws one joined bar: the two halves meet on the bar line with no gap, no border and no rounding where they meet, and the line is not drawn over them. It is selected and carried as one, and has an edge at its two ends only. While it is carried its ghost is one outline over the bar line, which shows through it, so the place where the note will cross is seen. Why not a mark on the note at the line: the design asks for one note on the screen, and a tick or a notch in the middle makes the eye count two. What is lost: a reader cannot see where the bar line falls inside a note that is already written; the label says it ("bar 1 beat 4, length 2 beats"), and the carried ghost shows it.

**The keys.** The map as it stands, whatever has the focus inside a part or the toolbar unless it says a note must:

| Key | A pitched note is selected | Nothing is selected |
| --- | --- | --- |
| Left, Right | Moves the selection one grid step earlier or later. | With a note in focus: steps the focus to the neighbour and selects it. Elsewhere: moves the insertion point to the previous or next line of the grid, or scrolls while there is none. |
| Up, Down | Moves it a semitone up or down. | Scrolls, as the browser does. |
| Shift with Up, Down | An octave up or down. | Nothing. |
| Shift with Left, Right | Moves the end edge one grid step: longer to the right, shorter to the left. | Nothing. |
| Ctrl or Cmd with Left, Right, Home, End | Moves the focus between notes without selecting. | Same. |
| Home, End | With a note in focus: the first or last note, selected. Elsewhere: the insertion point to the start or end of the score. | Same. |
| Enter, Space; Shift with them | Selects the note in focus; adds it or takes it out. | Same. |
| Delete, Backspace | Turns the selected notes into rests. | Nothing. |
| Ctrl or Cmd with A, with Shift and A; Escape | Selects all, inverts, clears (Escape is left to the host when nothing is selected). | Same. |
| Ctrl or Cmd with Z, with Shift and Z; Ctrl and Y | Undo, redo. | Same. |
| B | Turns the pencil on or off (only while the arrangement is shown and the score reads). | Same. |
| Ctrl or Cmd with C, V, D | Copies the selection inside the session, pastes it at the insertion point, repeats it right after itself. | Same; nothing is taken from or written to the system clipboard. |
| Alt with any except a drag | Left to the system. | Same. |

The editing keys leave the keys of the system and the host alone: Ctrl, Cmd or Alt with an arrow is never an edit. Every edit key does nothing to the score while the session is read-only, and says nothing. A key that the score refuses (before the start, past the end, an end edge shorter than the grid) changes nothing and says why. The distances are whole ticks and semitones: a pointer's fraction is rounded before the command sees it, and the command's own rounding puts the start on the grid.

**What the screen reader hears.** The voice track that holds the selected notes says "Moved to D4, bar 1 beat 3" or "Moved 3 notes", and "Resized C4, bar 1 beat 2, length 3 beats" or "Resized 3 notes", in the session's language, for the edit and for its undo and redo. The command does not travel with the change a part hears, so a move and a resize are read off the notes: they pair up in the order of the selection, which the session keeps when it follows the edit, and a different length is a resize and a different place or pitch a move. Said once per voice, so a selection across voices is told by each.

**Not done here.** The lane does not scroll by itself when a drag reaches its edge. A drag makes no sound. The outline does not tell a drop that will be refused from one that will not. The lane's height follows the pitches its voice uses, so a note taken above or below them makes it taller when it is let go (the keys do the same), and the rows move under the pointer. The lane draws bar and beat lines and no line of the grid, so on a step finer than a beat the outline is what shows where a drop lands; lines that follow the grid have to start from tick 0 whatever the meter, and are left for a change that touches the lines layer. There is no way to move or resize a note by a single pointer without dragging (WCAG 2.2 criterion 2.5.7): the keys are the other way, and a host can send the `move-notes` and `resize-notes` inputs from controls of its own.

### Placing notes

The pencil is the mode that tells a tap on empty space from a tap that clears the selection. Off, a click or tap on empty space clears the selection and drops the insertion point, a double click or double tap on empty space draws a note there, a click or tap on a note selects it and a double click or double tap deletes it. On, a click or tap on empty space draws and one on a note deletes. The double is two clicks at the same note or grid place within 450ms, derived from pointer events so a touch screen gets it too; a mouse's own `dblclick` is the second path, and a touch double tap is timed. A drawn note is one grid step long, at the pitch of the row under the pointer, on the nearest line of the session's grid; it goes through the one-note-a-time rule of [Moving and resizing](#moving-and-resizing), so it removes a note whose start it covers and shortens one it starts inside. A tap on empty space is one that moves no more than the pointer slop, so a swipe on a phone still scrolls.

Copy is held by the editing session, not the system clipboard. Ctrl or Cmd with C takes the pitched notes of the selection, a whole tie chain as one note; with V it puts them at the insertion point, the earliest at the point and the rest at their distances, each on the grid; with D it repeats the selection on the first grid line after its end. Alt with a drag carries copies instead of the selection, by the drag's time and pitch. Paste, duplicate and the Alt drag all obey the one-note-a-time rule and are one history step, and their new notes are selected afterwards. The keys are taken only while the session is editable and the focus is not in a text field or a popover; with no selection, no copied notes or no insertion point they do nothing and the browser keeps its own copy, paste or bookmark. Text copied or pasted from elsewhere is not read: the unit is a note of the model, not a text format. The cost is that two editor windows cannot copy between each other.

A note that is drawn or carried is heard through ticket 11's single-note preview (`previewNote`): one pitch for each distinct selected pitch at the drag's offset, and the drawn pitch once it is placed. The sound is the preview's own shared audio context, so a page still has one; where there is no Web Audio, or the browser refuses to start it, the gesture is silent and nothing else changes.

**Verified.** Seam 1 (`tests/place-notes.test.ts`): the four commands on hand-worked texts and every sample, untouched bars and notes, the one-note-a-time rule, the grid, and the refusals. Seam 5 (`e2e/place-notes.spec.ts`, desktop and phone): the pencil on and off with mouse and finger, copy, paste, duplicate, Alt-drag, and the sound of a drawn and of a carried note through the page's audio constructor, not the schedule. Measured in Chromium here: the pencil adds no height at 412 with either pointer and none at 320 with a mouse; at 320 with touch it adds one row, which the later two-row toolbar absorbs (see Toolbar).

**Not verified.** A real phone's double tap and its 300ms click delay, Safari and Firefox, the system clipboard (it is deliberately not used), and a screen reader's speech (the names and pressed state are read from the accessibility tree, what it sounds like is not heard).

### Insertion point

A 2px line in the text colour through the whole height of every voice lane, with a flag at its top: a 10px wide, 5px tall triangle drawn with borders, so it costs no node beyond the line. It is heavier and darker than the 1px muted bar lines and sits on the nearest line of the grid (see Grid menu), a quarter note in 4/4 until the grid is changed, counted from the start of the score; a click puts it on the line nearest the pointer, and Left and Right move it to the previous or next line. The flag sticks just under the pinned track head, so it stays in view when the lane is scrolled past its top. At the start and the end of the lane the line is kept whole inside it, where the pitch column and the focus ring would otherwise cover half of it; the flag at the start is then half under the pitch column. It ignores the pointer, has no hover and no motion, and is drawn only while the session is editable. It is named for screen readers as a separator ("Insertion point, bar 1 beat 3" or "Insertion point, end of the score").

### Note

A block exactly one row high, filled with the note colour, with a border mixed 30% toward the text colour. Width is its duration less a 1px gap, with a 2px minimum. Rests are not drawn: a rest is the gap between blocks. A note tied to the next note of the same pitch loses its gap, its right border and its right corners, and the next note loses its left border and corners, so a tie reads as one connected bar. A note is a list item labelled "C4, bar 1 beat 1, length 1 beat" (with ", tied to the next note" when it is), in the host language, in a list named for its voice.

### The cut

When the text of a voice stops before the song does, three things say so: a strip of one sentence above the view, led by a small swatch of the hatch so the sentence and the texture read as one ("This score is cut off: bar 232 of Ins is incomplete." or "...after bar 5 of Vocal."), a flag in the marks row at the bar where it stops ("Incomplete bar" when the bar is unfinished, "Cut off" when the text stops at a bar line, which puts the flag at the end of the score), and in that voice's lane a hatched tail with a dashed left edge from where its last note ends to the end of the score. The hatch is 1px diagonal lines in the strong line colour at 7px (the swatch is 1.1em square with a dashed border); the sentence is a note landmark. None of it uses a new colour. When the cut is inside a bar and the session is editable, the strip also holds the two repairs after the sentence, wrapping on a narrow screen: "Fill with rests" and "Delete the incomplete bar". Their labels say what they do; their titles and descriptions add the target ("Fill bar 232 of Ins with rests", "Delete bar 232 of Ins"), so the sentence and the actions name the same voice and bar. Each is an ordinary button at 28px (36px coarse), inset with the sentence's 12px: the actions have no vertical padding of their own, so on a phone they take the second row without the extra 12px. The sentence uses `text-wrap: pretty`, which keeps a lone character such as zh's 整。 off its own line at 320px. A repair hides the strip with the cut; a refusal leaves it, keeps the score unchanged, and shows the same sentence as text in the strip (`.sce-cut-refusal`), in the strip's live region and through `onRefused`. The text clears when the next repair succeeds or the cut changes. A cut at a bar line has no incomplete bar to repair, so it shows the sentence alone.

### Problem view

When the score cannot be read, the view is replaced by an alert panel: one sentence in 600 weight ("This score can't be shown because it can't be read."), then the dialect's diagnostics as a list in the interface language ("The duration "5" is not allowed. (bar 1, line 10)"), at most 20 and then "and N more". A model with no dialect gets one sentence naming it. The toolbar keeps its title and loses the zoom group.

### View switch

Three square icon buttons in a group named "View", joined: they share their borders (a 1px overlap) and only the outer corners keep the radius. The buttons are 28px (36px on a coarse pointer) like the history buttons. Each has an accessible name and tooltip ("Arrangement", "Staff", "Score text") and `aria-pressed`; the shown one is filled with 12% of the text colour over the ground, has a text-colour border and draws its icon at 2px (the staff's five lines are the exception: they are 1px, and 1.5px when pressed, since five lines at 2px would merge into one block), so the state is carried by fill and weight and never by hue. The icons are polylines in an inline SVG, as the history arrows are: short bars at different starts for the tracks, five full-width lines at 1px for the staff, three left-aligned lines for the text. They work in a read-only session, since they change what is shown and not the score. The group follows a view that anything else sets (`session.setActiveView`), and the session's language.

### Text view

The score text in a plain `textarea`, with a gutter of line numbers on its left that scrolls with it, in the monospace face of `--sce-font-family-mono` (16px on a coarse pointer, since a phone zooms the page when a smaller box is focused). Under the box, one status sentence in the interface language ("No problems", "3 problems", and while the project keeps an older score, "1 problem. The other views still show the last readable score."), and when there are problems, a list of them: each is the diagnostic's sentence with its bar and line ("The duration “5” is not allowed. (bar 1, line 10)"), at most 20 and then "and N more", and it is a button that selects that line in the box and scrolls it into view. A line with a problem is marked in the gutter by a dot and a bold number as well as by colour, and an item of the list is underlined when it is pointed at or focused. The line numbers are lining, tabular numerals. The box and the items of the problem list draw the 2px accent focus ring inside their edge, not outside it with the 2px offset: the box and the list scroll, so an outside ring would be cut off. The box is `aria-invalid` while its text cannot be read.

**Live parse and check; one undo step for a burst.** Text is checked when typing pauses for 600 ms and when the box loses the focus, whichever comes first (`session.checkScoreText`, the same path `replaceScoreText` takes, so what the status says is what the command would do). Text that reads is dispatched as one `replaceScoreText` command, one history step, and the project holds the text as the dialect writes it. A notice is not a refusal (`isNoticeDiagnostic`): text that reads but comes back with one, such as the chords of a melody project (`melody-with-chords`), is taken as well and stays in the box, and the notice is said under the status sentence, apart from the problems: a plain sentence in the text colour with a 3px accent bar at its start, a `note` landmark that is also described by the box, with no list and no button, since a notice has no line to go to. While the box holds text that was not taken, the problems are what is said and the notice steps aside; it comes back when the box holds the project's text again, and it goes when the project changes from elsewhere, since it was said of the replacement that this view made. Text that does not read is dispatched nowhere: it stays in the box exactly as typed, the session is told (`setRejectedText`) and the project keeps the last readable score.

Why a pause and not every key, and not only on blur: a step for every keystroke would make undo a character at a time and fill the history with the half-typed texts that cannot be read; a step only on blur would keep a reader's edits from reaching the arrangement and the staff while they are still in the box, which is the point of a live view. A 600 ms pause is the length of a thought between two words, so one burst of typing, one phrase, is one step, and the other views follow within a second. Leaving the box, and so any click on the toolbar's Undo, commits first, so Undo pressed right after typing undoes that typing. Inside the box, Ctrl or Cmd plus Z is the browser's own (the editing keys skip text controls), which undoes keystrokes of the box; the toolbar's Undo and Redo are the project's steps. A dispatch that leaves the project as it was adds no step.

In the default editor the text view is mounted when it is first shown and kept from then on, with what its box holds; a view that was never shown holds nothing, so what it would show is read from the session when it is mounted (the project's score, or the rejected text the session holds). The box is read-only while the session is, or when the model has no dialect (with a sentence that says so). Text it holds but did not hand over is given up when the session turns read-only, since nothing may be handed over then. When the project changes from elsewhere (an undo, `replaceProject`), the box shows the project's score again and the rejected text is dropped.

### Stale notice

One sentence above the arrangement and the staff, shown only while the text view holds text that cannot be read: "The score text has a problem, so this view still shows the last score that could be read. Fix it in the text view." It is a note landmark like the cut notice, with a 3px text-colour edge at its start in place of the hatch swatch. The arrangement and the staff keep drawing the last score that read; the notice is what tells the reader that they are behind the text. It is not drawn for a project that came with an unreadable score, where the problem view says that already.

### Staff view

The project's score on a staff, drawn by abcjs 6.7.1 (the newest release published at least 7 days before it was added) into a scrolling region of its own: focusable and named, so Tab reaches it and the arrow keys scroll it; 12px of padding; the scrollbar's room is kept so the drawing's width does not change when it appears. The drawing is as wide as the region and is drawn again, with the abcjs line breaking told that width, when the region's width changes. It is read-only: a click or tap on it changes nothing. A score that cannot be read is not drawn, and the problem view above explains it. The drawing is never narrower than 240px, so in a box narrower than that and the region's padding the region scrolls sideways (the arrow keys move it) and the page does not (checked at 260px and 240px).

abcjs is loaded with `import()` when the staff view is mounted, and the default editor mounts it the first time the staff is shown: the package entries import no abcjs (a test imports both in a process that fails when abcjs is loaded), and a host that never shows the staff never fetches it. Until it arrives the part says "Loading the staff…"; if it cannot be loaded it says the staff could not be drawn and that the other views still work.

**How abcjs is isolated (the result of the check).** abcjs draws an SVG with its own presentation attributes and expects a page without rules for `svg`, `text` or `path`, and it measures text through a dummy SVG it puts in the document. The check was run in Chromium, in the default editor and with the part alone, in the light DOM, in a host's shadow root, with hostile page rules, and under a strict style policy:

- The drawing is made inside an open shadow root that the part attaches to an element of its own, inside the part's root. A host's rules for `svg`, `text`, `path` and `*`, even with `!important`, do not reach into it, with the editor in the page and with the editor in a host's shadow root (the nested shadow root is why). The reset of the package's own style sheet does not reach into it either, so the drawing carries a short sheet of its own (constructed where the browser has constructed sheets, a style element where it has not) that sets its box only. Nothing sets the colour: it is inherited across the shadow boundary, and abcjs draws in `currentColor`.
- The colour follows the part: the drawing takes the text colour of the part, so a dark scheme and a host's `--sce-color-text` apply with no variable of its own.
- A strict policy (`style-src 'self'`) refuses a style element that abcjs adds (the page sees `style-src-elem` violations, and none before the staff view is mounted) and the drawing is unchanged, since everything it needs is in attributes and in the sheet above.
- Global CSS: nothing is added to the page. The part adds no rule and no element to `document` or to the host's shadow root beyond its own node; after the drawing the page holds no svg and no style element of abcjs's, and once the layout is closed the page's markup is as it was. Of the `document` abcjs reads, only its dummy SVG for measuring text is used, and it is not left behind.
- What cannot be isolated, and is accepted: abcjs registers two `resize` listeners on `window` when it loads, which it offers no way to remove (the lifecycle test loads abcjs before taking its baseline of listeners for that reason), and it keeps a text-size cache of its own for the life of the page.
- `getBBox` needs a displayed box, so the part draws only when its region has a width: a staff view mounted in a hidden container waits until it is shown, and keeps what it drew before while it is hidden.

### Staff play cursor

The staff view's play position is the host's. `mountStaffView` returns a `StaffViewPart`; `setPlayPosition(seconds)` draws the cursor at that time from the start of the score, and `null` takes it away. It is a readout, not an edit, so it is drawn while the session is read-only too. The session's own preview drives the same cursor while it plays, and a press on a drawn note starts the preview at that note. A press lands on the box of the note it is over, not on the element the pointer reports: a staff line drawn across a note head is what the pointer hits, and it must not swallow the press. Seconds become a position through `tickAtSeconds`: each stretch of the score uses the tempo in force in it, and a time past the end stays on the last bar line.

A bar begins at the bar line abcjs draws to close the bar before it. The first bar of a system has no line of its own, so it begins at its first drawn note or rest. The cursor's x is the drawn line's box, not the first note of the bar: a rest or a note written after the line must not move the start, and a bar's later notes must not pull it back. That is why the cursor and the drawn bar lines line up exactly. The cursor is positioned in the drawing element's own box, and every box is read from the drawn elements in that same space; the scroller's padding and the host's offset must not move it.

The cursor is 1px in the text colour with a 1px edge in the ground colour on each side, so it reads over a staff line and over a note, and it spans the five staff lines plus 2px beyond each. It has no flag, so it is told from the insertion point by shape; it spends no accent, ignores the pointer, and is hidden from assistive technology. It has no transition or easing. Under forced colours it is `CanvasText`.

When a new position is outside the region, the region scrolls so the cursor comes in 16px from its left edge, and, when its staff line is outside, from the top or bottom; the host page itself never scrolls. A position already in view moves the view not at all, so the cursor does not drag the staff under the eye; a line is turned only when the cursor reaches its end. This is the same rule as the arrangement playhead's page turn, applied to the staff's own scroller.

The states a reviewer checks, at desktop and phone width: the cursor at the start, mid-bar, after a tempo change (the test page can open a score with one), at the end, and while the preview plays; also in a read-only session, since that is the host's case.

### Read-only badge

Pill, 1px strong line, muted text, label size, at the end of the toolbar. It appears only while the session is not editable, and takes the place of the history group. In that state nothing in the view offers an edit: no history or Delete button, no selection frame, no insertion point, no tab stop or pointer cursor on a note, nothing about editing said in the live regions, and Delete, the history keys, the note keys and the insertion point keys do nothing.

### Focus treatment

Interactive parts (buttons, menu items) get a 2px accent outline with 2px offset on keyboard focus, and so does a note reached by keyboard, outside the selection frame, so the ring (where the keys act) and the frame (what Delete takes) read as two things. A click or tap does not draw the ring. The text box and the items of the problem list draw the ring inside their edge (see Text view), and the chord cursor draws it 4px inside its frame (see Chord editing), because those containers clip an outside ring. The scroller is focusable; because its own outline would be hidden behind the sticky header and pitch column, a 2px accent ring is drawn over the whole body instead.

### Announcements

What a screen reader cannot see in the drawing is said in words, in the session's language, by one polite live region (a visually hidden `role="status"` node) that each time-axis part and the toolbar keep for their whole life; a redraw never removes it, so a sentence is not lost with the content it follows. Which part speaks follows who owns the state: a voice track says which of its own notes were selected ("Selected D4, bar 1 beat 2", "Selected 3 notes") and that a delete took some of them ("Deleted D4, bar 1 beat 2"), that a move or a resize changed them ("Moved to D4, bar 1 beat 3", "Resized C4, bar 1 beat 2, length 3 beats"; Moving and resizing says how it tells them apart), and for an undo or redo what it brought back ("Restored D4, bar 1 beat 2") or took away or moved, since the selection does not change with a history step; the track of the score's first voice also says where the insertion point moved ("Insertion point, bar 1 beat 3"), because the point is on the axis every track shares and one voice should say it once; a part that heard a refused edit says why and where, in the sentence the host's notice carries, and the toolbar does so for its Delete button. No part reads another part: each follows the session and the score alone. A part says nothing about editing while the session is read-only; the synth preview control is not an editing control, so what it says about the preview (that it started, stopped or could not start) is said in read-only mode too, because the person who pressed it has no other way to know. Stepping from note to note by keyboard is not announced, since the focus speaks the note it lands on. Keys pressed while the focus is on the scroller, outside every part, are heard by the frame, which keeps a region of its own for the refusals they cause and tells the host's notice as well.

### Motion

None. No transition or animation exists, so nothing needs a reduced-motion alternative. Zoom, scroll, selection and the insertion point change the view directly. The things that move by themselves are the playhead of the synth preview and the staff view's play cursor while the preview plays, and neither is an animation: both are readouts of where the sound is, set from the audio clock on every frame, with no transition or easing, and present only while the person has asked for sound. A reduced-motion setting therefore changes nothing about them.

### Synth preview

One button and a caption, in a view part of their own (`mountSynthPreview`) that the default toolbar also holds. In the toolbar they are the last items before the Filter button, after the read-only badge and, where the toolbar has one, the view switch, which come before them so that the control coming and going with the score cannot move the switch (see Toolbar). The badge keeps the place it had in a narrow host (it is still whole in a 320px box), and where the control does not fit beside the other controls it takes a row of its own, at the start of the row. The button is built as the other buttons are, 28px high (36px coarse), the same ground fill, 1px strong line and 4px radius, with a 16px line icon in a 1.5px stroke, drawn as polylines (a right-pointing triangle to play, a square to stop), and the word beside it, "Preview" or "Stop" (试听, 停止), so a person who does not read a play triangle as music finds it. The word has a minimum width, so the caption does not move when the word changes. It takes the focus ring and the hover of any button; a press, Enter or Space toggles it, and a second press stops.

The caption is always there, not only while it plays: "Synthetic preview, not the final sound" (合成试听，不代表成品效果). It is muted text at label size, at most 12em wide so it takes two short lines and the control keeps one size; it breaks at its comma (`text-wrap: balance`; in Chinese `word-break: keep-all`), and is never cut or hidden. It is also the button's `aria-description`, so a screen reader says it with the button wherever the text is drawn. The button and the whole caption are in view at rest, with nothing to scroll to, in a 412px phone and in a 320px box, editable and read-only (seam 5 checks both), and they stay so while the preview plays. Starting the preview scrolls nothing: it never moves the host page.

The control is not an editing control, so it is there in read-only mode, and it is hidden only while the session has no readable score (in a toolbar with the view switch its place is kept, as the Toolbar section says). In read-only mode it starts at the start of the score, not at an insertion point the session may still hold: a read-only view draws no insertion point, so a start there would begin where the visitor cannot see (the spec case "starts at the start whatever insertion point the session was left with, since a read-only view shows none"). Its states: stopped, playing, not supported (the browser has no Web Audio: `aria-disabled` and muted like a history button with nothing to do, the reason in its tooltip and, for good, in place of the caption, since a touch screen has no tooltip), and two that last a moment, "nothing to play from here" and "blocked by the browser, press Preview again": the sentence takes the caption's place in the text colour for four seconds, and then the caption is back. The same words are said by a polite live region, which is the toolbar's own when the toolbar holds the control and the part's own when it stands alone, in the session's language: where the preview starts ("Playing the preview from bar 1 beat 3"), that it stopped, and why it did not start.

### Playhead

A line through the whole height of every voice lane at the tick being played: 1px in the text colour with a 1px edge in the ground colour on each side, so it reads over a note as well as over the lane. It is told from the insertion point by shape, not colour: the insertion point is 2px with a flag, the playhead 1px with none, and both can be on screen at once. It is one node, hidden from assistive technology, ignores the pointer, and is the text colour like the insertion point and the selection frame, so no accent is spent on it. It is drawn from the tick the player publishes (see below), at a position in percent of the lane like everything on the time axis, and is removed when the preview stops or the position passes the end of the lane.

It follows the song by turning the page: when the line comes within a beat (48px) of the right edge of the view, the view scrolls so that the line is near the left, as a score is turned, not by scrolling continuously, which would move every note under the eye while the song is read. It scrolls the editor's own time axis (the session's `view.scrollLeft`), never the host page. When the preview starts, the start is brought into view first on that axis. If the user scrolls or zooms the line out of view, the view is theirs and is left alone until they bring the line back into it.

The position is read from the audio clock on every animation frame (the clock's time less the device's output latency, so the line is where the sound is, not where it was scheduled), so it has no transition or easing and never drifts from the sound. It is not kept in the session's `view`: that state is what parts share and notify on when the user changes it, and the playhead changes on every frame and is not the user's setting, so putting it there would notify every part sixty times a second and change what the state means. The player (`previewPlayer(session)`) is its one source; it has its own small subscription, and a voice track reads only the published tick. A view of a host's own subscribes to the same player.

### Autoplay, audio focus and what was verified

The synth preview is the one thing in the package that makes sound, so it has the browser's rules to follow. This section is the record of what was checked, on what, and how.

**The rule the code follows.** A browser lets a page start sound only after a user gesture. The player creates the page's audio context and calls `resume()` synchronously inside the click, tap or key handler that asks for the preview, before any `await`, and starts nothing if the context is not running after that (the control then says the browser did not allow sound and the next press works). All sound shares one audio context, which is suspended again about 0.3s after the last sound, so an idle editor holds no audio device. Nothing is started at load, at mount or from a timer.

**Verified directly, by tests kept in the repository.** `e2e/synth-preview.spec.ts`, on Chromium 156.0.8078.4 headless, driven by Playwright, in the desktop and the phone project (an emulated phone, not a phone). The spec runs without traces, because Playwright's trace recording gives the page a user activation, which would hide the blocked case.
- A preview started with no user gesture behind it (a click made by a script) ends as "blocked", says so and plays nothing; the next real press plays ("a sound the browser refuses to start, with no user gesture behind it, is said and does not play"). The console message of the browser for that case is "The AudioContext was not allowed to start. It must be resumed (or created) after a user gesture on the page."
- A page `<audio>` element that is already playing is not paused when the preview starts, and the two run side by side: the element's position goes on advancing, and the audio context is `running` ("a preview started while the page's audio plays leaves that audio playing, and both run"). That both are heard was not observed: a headless browser is muted, so there is no output to listen to.
- An `<audio>` or a `<video>` element in the document that starts to play while the preview plays stops the preview, and the page's own sound goes on ("an audio element in the document that starts …", "a video element in the document that starts …"). A detached `new Audio()` and an `<audio>` inside a shadow root do not: a capturing `play` listener on the document hears neither, so the preview plays on with them ("a detached audio element is not heard …", "a shadow audio element is not heard …").
- No network request: Playwright's request events, from before the editor is mounted (with the score given as text, so the page fetches nothing for it) through a preview of a melody, a second voice and a chord, and through a single-note preview, until the audio device is let go, show none, and every request of the page, load included, is to its own origin ("none leaves the page from before the editor is mounted to the stop …"). The same case checks that what sounds is what the score says: the pitches of the three kinds of sound.
- A browser with no Web Audio (`AudioContext` removed before the page's scripts run) gets a muted control with the reason, which says so when pressed and plays nothing ("a browser with no Web Audio gets a control that says so, and no preview").
- Escape stops the preview from wherever the focus is, and the key still reaches the window with its default not prevented, so a host's own Escape handler works ("Escape stops the preview …", "Escape is left to the host as well …").

**Verified directly, by throwaway probes that are not kept in the repository.** Same Chromium. A script that reads the browser's own API, so what it showed is a record here and cannot be rerun from the repository: a context created and resumed in a page that has had no gesture stays `suspended` and `new Audio().play()` is rejected with `NotAllowedError`; inside a click `resume()` resolves, the state is `running` and the clock advances (0.30s over a short wait); suspending the audio context leaves a playing `<audio>` element playing; and the `play` event reaches a capturing listener on the document for `<audio>` and `<video>` in the document and not for `new Audio()` or an element in a shadow root (the tests above now keep that last result).

**Verified only indirectly.**
- WebKit. Playwright's WebKit 27.2 for Windows was installed and run: it has neither `AudioContext` nor `webkitAudioContext`, and `<audio>` playback fails with `NotSupportedError`, so it can show the unsupported path and nothing about Web Audio autoplay, and it is not iOS Safari. What is known of Safari comes from MDN's autoplay guide, which says playback of audio that is started by a script before any user interaction is generally blocked, and that the Web Audio start rule is the same as for media; the code follows that rule by starting inside the gesture. MDN says nothing of Safari's own Web Audio rules, so that part rests on the practice of starting inside the gesture, not on a reading of Safari.
- Audio focus. The W3C Audio Session API (a working draft) gives an `AudioContext` the default session type "ambient", which "is mixable with other types of audio", and an `HTMLMediaElement` "playback", which should not mix with other playback audio and may pause other audio. The package does not set `navigator.audioSession.type`, so a browser that implements it treats the preview as ambient. Chromium 156 does not implement it (`navigator.audioSession` is `undefined`), so this is read from the specification and not observed.

**Not verified.** iOS Safari, macOS Safari and Firefox, on any device; Android audio focus; the system's silent switch on a phone; headed Chromium with real speakers (the headless browser is muted, so what was checked is that the audio clock runs and the nodes are made, not that the sound is right, which is not tested automatically); a host with its own audio player that holds an audio session of its own. A person with an iPhone should press Preview once on a page with its own audio playing and say what they hear.

**What the preview does about other sound.** It ignores it when it starts: it does not pause, duck or take over a host's audio, because that audio is the host's and an ambient, mixable sound is what the specification gives a context by default; and the evidence above is that the two go on side by side, neither paused (that they are heard together was not observed). It yields when another element starts: when an `<audio>` or `<video>` element in the page's document starts to play while the preview plays, the preview stops, because a media element is the stronger kind of audio in the specification ("playback" over "ambient"), a person who starts a track or a video did not mean the preview to go on over it, and a rough synthetic rendering is the one to give way. Escape also stops it, from wherever the focus is, so a person who hears it and has the focus in a lane does not have to find the toolbar again. The handler listens on the document, in the bubbling phase, and neither prevents the default nor stops the event, so a host's own Escape handler (a dialog it closes) still gets the key; a handler of the host's that stops the event below the document keeps it from the preview, which is then stopped by its button. A host whose audio is in a shadow root, an iframe or a detached `new Audio()` is not heard by the preview, and can call `previewPlayer(session).stop()` itself.

### Chord editing

**Where a chord can go.** A chord is written at the start of a note or a rest in a voice whose constraints allow chords (for `song2`, `Vocal`; `Ins` has no way in, and a start that only `Ins` has is never offered). A press on the chord row takes the start nearest to it, the earlier of two on a tie, so the person aims at a place on the time axis and does not have to hit a small target; the whole row answers, also in an empty track. A press on the name of a chord takes that chord instead, because a name is drawn a little to the right of its start and, where notes are short, another start can be nearer to its last letters; pressing a chord is asking to change it. Where a start already has a chord the picker offers Change and Remove, where it has none Place.

**How the user sees which start was taken.** Three states of one frame, the same box on the same stretch of the row: the stretch of the note or rest that starts there, from its start to the end of its length (at least 8px, so a very short note still shows).
- A mouse over the row shows the start a press would take, as a 1px dashed frame in the text colour. Dashed is the editor's word for "not chosen yet". Nothing is shown for a finger, which has no hover; it learns the start from the next state.
- While the picker is open the frame is solid and 2px in the text colour, and the picker's first line says the start in words ("Bar 1, beat 2"; the dialog is named "Chord at bar 1 beat 2"), so the start is never told by the frame alone. It is the selection frame's vocabulary: shape and weight, not hue.
- The keyboard cursor (below) carries the same frame, with the accent ring of keyboard focus inside it. The frame has no border at rest (so nothing is drawn where the system forces its colours either), and is gone when the picker closes by a pointer; it stays while the cursor has keyboard focus. The cursor takes no pointer: the row is the target of a press, and it is as high as the other header rows (2em), so a finger needs to aim along the time axis only, where the nearest start is taken.

**The picker.** A popover of the package's own, as the zoom menu is: native `popover="auto"`, so it stands in the top layer above a host's full-screen layer, closes on Escape and on a press outside, and returns the focus to what had it. It has the popover's surface fill, 1px strong line, radius and the one floating shadow, a dialog role and the name above. It is `min(21em, 100vw − 16px)` wide on a fine pointer and `100vw − 16px` wide on a coarse one, where it stands at the left margin whichever start was taken, so the choices are as wide as they are tall and a finger does not find the picker under the hand that opened it. It has 10px padding and is built from rows, top to bottom:
- A head line: the start in words in 600 weight, and what is there now ("Now Am", or "No chord yet") in muted text at the end of the line.
- The readout: the name that Place will write, in 1.35em and 600 weight, tabular numerals. It is a polite live region, a second one inside the picker, because the name is the one thing that changes under the focus (choosing a root renames every type chip) and the focused chip does not say it.
- **Root**: the letters C to G, A and B in seven equal columns; under them the spellings the vocabulary has on the chosen letter (`bb`, `b`, natural, `#`, `##`) in five equal columns, so a choice keeps its place when the letter changes. A letter chooses its plain root when the vocabulary has it.
- **Type**: the vocabulary's qualities as chips that show the whole chord name (`Am`, `Amaj7`, `A7sus4`), not the bare suffix, which a person who reads chord names rather than suffixes can scan; they wrap, since their widths differ.
- **Bass note**, only when the vocabulary allows a slash bass: one button that shows the bass chosen ("None" or its name) with the zoom value's chevron, which opens the letters (with None first) and spellings of the bass. It starts closed unless the chord has a bass.
- The actions: Remove at the start (only for a start that has a chord), then Cancel and the primary action, Place or Change, at the end.
Everything it offers comes from `session.dialect.constraints.chords` and is filtered to the names `splitChordName` can write, so a chord the dialect rejects cannot be built; the same grammar (`splitChordName`) is what `setChord` checks. A choice is a chip with the buttons' 28px (36px coarse) height and border; the chosen chip, and the primary action, are drawn as the view switch draws its shown view: a 12% text fill, a text-colour border and 600 weight. Where the system forces its colours the fill is lost, so a chosen chip's border thickens to 2px, as a selected note's does, and the padding gives the pixel back; no system colour is named, so the Borrowed Colour Rule keeps its one exception. The picker opens on the chord on the start, else on the chord in force before it (so repeating a chord is one press), else on the first root and first type of the vocabulary. It is placed under the chord row at the left edge of the taken start, kept inside the window, and above the row when there is more room there; when a choice makes it taller (the bass note opening) it grows downward from where it was, so the control that was pressed stays under the finger, and moves up only as far as the edge of the window makes it; its height is fitted to the window and it scrolls inside it when the window is short. Its left and right edges are kept inside the width the page lays out in, which a scroll bar, or a page that spills sideways on a phone, makes smaller than the window's. Place and Change write one `setChord`; Remove writes the same with an empty name; each is one history step. The picker closes before the command runs, so a refused command leaves no picker behind; the refusal is said in the part's live region and told to `onRefused`.

**Keyboard.** The row holds one tab stop, the cursor: a button, always present while editing is on, whose name says where it stands ("Chord place, bar 1 beat 2, Am" or "..., no chord") and whose description says how to use it. It is in the chord row's layer and not among the list items of the chords, so the list keeps only chords. In the default editor it is the first tab stop after the scroller and before the notes, which is the order the eye reads. Left and Right step it from start to start and keep it in view, with Ctrl or Cmd from chord to chord, Home and End to the first and last start; Enter and Space open the picker; Delete and Backspace remove the chord under it. The cursor keeps the arrows from moving the insertion point, since a person in the chord row is not placing a note. In the picker, Tab goes row by row (one stop for each row, as in a radio group), the arrows choose within a row and Home and End go to its ends, Enter on a chip places the chord, and Escape closes. The focus moves into the picker, to the first choice, not to the cursor; the cursor is focused first only so that it is where the focus returns when the picker closes. A redraw that replaces the cursor (an undo, an edit from elsewhere) gives the focus to the new one. The cursor's ring is drawn inside the frame, with a 4px inset, and not at the 2px offset the other controls have, because the row clips what is drawn outside it.

**Announcements.** The chord track's live region says what the person did and what the history did to a chord: "Chord Am placed at bar 1 beat 2", "Chord changed to Dm at bar 1 beat 2", "Chord removed at bar 1 beat 2", and after an undo or redo "Chord Am at bar 1 beat 2" or "No chord at bar 1 beat 2". Stepping the cursor is said too ("Chord place, bar 1 beat 2, no chord"), unlike stepping through notes, because the cursor is one button whose name changes under it and a screen reader does not reliably read a changed name on a button that keeps the focus.

**A press opens on `click`.** The picker opens when the press is released as a click, not when it goes down: the browser closes an open popover on the press, and the click that follows then opens the next one, so a person can move the picker from one start to another in one press. A pointer that moved more than 6px between press and release is a scroll or a drag, and opens nothing.

**Read-only.** The layer with the cursor and the frames is hidden, the row has no tab stop and no pointer cursor, and a press opens nothing. An open picker closes when the session stops being editable.

**Not verified.** Chromium only, at a desktop size and in a phone's emulation with real touch input; a screen reader's speech (the names, descriptions and sentences are asserted, what is read aloud is not heard); Safari and Firefox; the popover's light dismiss and its focus return on a real touch device.

### Tempo, key and transpose

Four controls in one group, after the view switch and before the Project button and the preview control, in the drawing and in the Tab order: the tempo field, the key menu and the two transpose buttons. They act on the whole song, so they are there on every view, and they are drawn only while the session is editable and its score reads. The Tab order of the default editor is therefore undo and redo, Delete, Select, Grid, Bars, Meter, the three views, tempo, key, transpose down, transpose up, the Project button, and the preview control. This is not the order the Toolbar section gives for the controls it lists, since these come after the switch, for the reason in "Keeping a place" below.

- **Tempo.** A native number field with "BPM" after it, named "Tempo (BPM)", 5em wide (4em where the pointer is coarse). Its `min` and `max` are the dialect's `constraints.tempo` (20 and 400 for `song2`), the only range there is; `step` is 1 because the command takes a whole number. The value is taken when it is confirmed (Enter, leaving the field, a spin step) as one `setTempo` command and one undo step. A value the command refuses puts the field back to the score's tempo and the reason is said as every refusal is. A field that has the focus keeps what is typed in it while the session changes under it.
- **Key.** A native select named "Key", 4.5em wide on a coarse pointer, with the dialect's keys in two groups, Major and Minor, and the score's starting key chosen. A key the score has that the list lacks is added at the top of the menu, so the control never names another key. Choosing a key is `setKey`, which moves the notes by the shortest way. A native select gives a phone its own picker and the keyboard its type-ahead.
- **Transpose.** Two icon buttons, 28px (36px coarse), a chevron down and a chevron up drawn as polylines like the other icons, named "Transpose down a semitone" and "Transpose up a semitone", one command each. They are one item of the group, so a narrow box never parts them, and they share an edge as the view switch's buttons do, so they read as a pair and not as one more chevron beside the menu's. No key is taken for them.
- **Look.** A field has the buttons' ground fill, 1px strong line and 4px radius, 28px high (36px coarse), tabular numerals, and the buttons' focus ring. Where the pointer is coarse its text is 16px, since a phone zooms the page when a field below 16px is focused. The word "BPM" and the word "Key" are muted label text.
- **Refusals.** A transposition that would leave the dialect's range is refused as a whole. The toolbar's live region says why, and `onRefused` gets the diagnostics, which the editor passes to `notify` as `command-refused`, the way every other refusal reaches the host. Nothing changes and there is no history step. The package draws no refusal of its own, as it draws none for Delete: refusals stay on the host path, said in the live region and sent to `onRefused`, so a host that gives none shows a refused tempo or seed only as the field going back.
- **What the tempo rule did.** The song-project layer's rule is not written again here: it rewrites the BPM in the style text, and the project panel shows the style it wrote. When the command comes back with a notice that the project does not state all the time (today `style-no-bpm`), the toolbar says it in one sentence in a line under its row, with a 3px bar in the text colour at its start, as the stale notice has, and in the live region. The sentence stays until the project changes by anything else. It has no button to close it: it is one sentence, read once, that goes with the next change, and a button would be one more stop for it.
- **Keeping a place.** In a toolbar with the view switch the group keeps its size while the session is editable and the score does not read, hidden from assistive technology and from the Tab order (`data-waiting`). It comes after the switch, and a control that comes after the switch and appears when the text is taken would move the switch along its line, which the Toolbar section rules out for the preview control for the same reason. Where the session is read-only the group is not there and keeps no place.
- **On a phone.** At 412px the group takes a row of its own, so the toolbar is four rows, 165px high (measured in Chromium with touch); in a 320px box it is 289px. The chrome floor and the pin rule bound what that costs the music: the chrome scrolls inside itself when it needs more, the body keeps at least the header's place, a track head and three rows, and the header is pinned only while the lane can keep six rows. In the states that had none or less than one row before, 412×420 with a conflict standing and 412×288 without one, the lane keeps 3.0 to 4.5 rows. At a short height the cost accepted is that the ruler and the chord names scroll away with the lane; the notes, the track head and the pitch column stay. The other way, to put the controls inside the Project panel on a narrow window, was left: the controls are the toolbar's, and it would put them one tap deeper.

### Song project panel

The panel holds the song project's fields that a score does not: the style text, the score mode, the seed, the lyrics as they will be joined for the next generation, and the notices the project carries. It is a view part of its own (`mountProjectPanel`), and in the default editor it opens from the toolbar.

**How it opens.** Decided with `shape` from the sources. Four ways were weighed:

- A side panel docked next to the arrangement takes the width the roll needs on a laptop and has no place on a 412px phone.
- A fourth view in the view switch: the switch and `VIEW_NAMES` are a set of three, and the fields are not a view of the score.
- A bottom sheet on a phone, the Tools panel's bottom sheet: a field that opens the keyboard inside a sheet fixed to the bottom is covered by it in Chrome for Android, where the keyboard resizes only the visual viewport.
- A button in the toolbar that opens a native popover under it, which spans the window on a narrow one. **Chosen.** It is the Select menu's and the zoom menu's way of opening, so there is nothing new to learn, it stacks above a host's full-screen layer, and Escape and the return of the focus are the browser's. Under the button it cannot be covered by the keyboard. It hangs from the button: when the toolbar wraps again while it is open (a notice comes and the count widens the button, the window changes) it is placed again. A host that wants the panel somewhere else mounts the part itself.

**The button.** A text button named "Project" ("歌曲项目") with the chevron of the Select button, there while the session has a dialect, in read-only mode too, where the panel still shows the values. While the project carries notices a number sits after the word in a ringed pill and the count is part of the button's name ("Project, 2 notices"), so a closed panel does not hide them and the count does not rest on a colour.

**The popover.** 28em wide, under the button and moved left where it would run off the window (8px margin); on a window narrower than 40em it spans the window with 8px margins. Its height is the room under the button, and it scrolls inside when it is taller (that is layout, not a limit on what the panel holds). It has no heading of its own: the button above it is the name, and the dialog carries it for assistive technology; a panel mounted on its own is a region named "Project". Opening moves the focus to the panel and not to the style box, so a phone's keyboard does not open before the person has chosen a field. Escape closes it and the focus goes back to the button.

**Fields**, from top to bottom, each a label in 600 weight, the control, and a muted hint line:

- *Style description*: a textarea, 3 rows, resizable vertically. Hint: "A BPM written here follows the tempo." The text is taken as one `setStyle` command when the box loses the focus or the popover closes; Escape closes and keeps what was typed (it is not a cancel, as the text view takes its text when its box loses the focus).
- *Score mode*: two radios, "Full" and "Melody", each with a one-line meaning. Chosen with one press: one `setScoreMode` command.
- *Seed*: a number field and a Clear button, always enabled. Confirmed, it is one `setSeed`; Clear sets `null`. A value that is not a whole number is refused as the command refuses it, and the field goes back to the project's value.
- *Lyrics*: the joined text in a read-only region that Tab reaches, at most 12em high and scrolling inside, with "N of 2000 characters" on the label's line, the numbers written as the notice for them writes them. The region is drawn as a reading, not as a field: no fill and the faint line, and the hint under it says "As the next generation receives them. Not editable here." The count is the code points of the joined text, line breaks included (`lyricCharacterCount`); over 2000 it is in 600 weight and the notice below says so. Nothing stops the person at any length. The region keeps the line breaks.

**Notices** are at the top, since they are what asks for something. A notice is a plain sentence with a 3px bar in the text colour at its start, a `note` landmark, as the stale notice is; the One Accent Rule keeps the accent for focus and for the checked dot, which the radios' own dot takes as the menus' does. For `melody-with-chords` the sentence is followed by two buttons, "Delete all chords" and "Switch to full", each one command and one undo step, and the notice goes with the chords or the mode. `lyrics-too-long` and `lyrics-unaligned` are sentences only.

**Empty fields.** A field the host did not give is empty and says so in its hint: "Not set. Describe the style you want.", "Not set. Choose one." (neither radio checked, also when the score mode is missing at run time, since a host that is not typed can leave it out), "Not set. Each generation picks its own.", and "No lyrics yet." in the lyrics region. The person can fill each one.

**Read-only.** The same fields as text: the style text, the mode's name, the seed, and the lyrics region with its count; "Not set" where a field is empty. There is no box, radio, number field, Clear or fix button. The notices stay and their fixes do not, since a fix is an edit. Nothing is said about editing in the live region.

**Keyboard.** The editing keys are not taken while the focus is in the popover (the parts skip `.sce-popover` as they skip a text box), so Ctrl+Z in the style box is the browser's own undo of the typing. Tab goes through the notices' buttons, the style box, the mode radios (one stop, arrows inside), the seed field, Clear, and the lyrics region.

**Announcements.** Each taken field is said in the toolbar's live region ("Style description updated", "Seed set to 7", "Seed cleared", "Score mode set to melody", "All chords deleted"), and a refusal is said and sent to `onRefused` as every refusal is. Said by the part itself when it stands alone.

**Not verified.** Chromium only, as everything else here. A phone's own keyboard and its effect on the popover were not tried: the narrow window was set in Chromium's emulation. iOS Safari and Firefox were not tried (the native popover, `light-dark()` and the focus return are assumed). While the popover is closed without the focus leaving the style box (a host calls `hidePopover()`), Chromium takes the text because it fires `change` on the hidden box; the panel also takes it itself on closing as a guard, and that guard is the part of it no test in Chromium can tell from the browser's own.

### Filter panel

A view part of its own (`mountFilterPanel`). In the default editor it is the last control of the toolbar's row, after the preview control, and the title and the other controls keep their place and order. It is a text button "Filter" ("筛选") that looks like the Select button, with the same chevron, and it opens a native popover, `role="dialog"`, named "Select by filter" ("筛选选中"). It does what Live's note selection filters do (Ableton Live 12 manual, Editing MIDI, "Find and Select Notes Using Filters", https://www.ableton.com/en/live-manual/12/editing-midi/#find-and-select-notes, read on 2026-10-23): the notes the criteria find are selected as the criteria change, the search can be inverted, and several criteria combine.

Why a control of its own and not an item of the Select menu: the Select menu is hidden whole while the editor is read-only, and the filter must work read-only (selecting changes no score), so an item could not outlive its menu. The cost, accepted: the button is far from Select in the row, because the row's Tab order is pinned by an existing test and a control placed before the preview control would change it.

**Rows.** A form, not a menu: one row for each condition, each with a checkbox that says whether the condition counts, then Invert with a line that says what it does, and a footer with the status line and the buttons Re-apply and Done. The conditions combine with "and". The fields of a condition that is not counted are in the muted colour, so which rows are in force shows at a glance and not only in a small box; they keep their values.

| Condition | Fields | A note passes when |
| --- | --- | --- |
| Pitch | lowest and highest note, as note names | its pitch is between them, both included |
| Time | first and last bar, as the ruler numbers them | it starts in those bars |
| Length | shortest and longest, as parts of a whole note | its whole length (a tie chain counted whole) is between them |
| Key | in the key or out of the key | its pitch class is in the scale of the key in force where it starts |
| Count | one in every N notes, skipping the first M | it is the 1st, (1+N)th, ... of its voice among those the other conditions let through, after M have been passed over |

The names of the conditions ("Pitch", "Time", "Length", "Key", "Count"; "音高", "时间", "时值", "调", "个数") are the spec's words for them. The Count row is Live's Count (its Every and Offset sliders); the Quantized toggle is not built, because a voice has no chords to group. A tie chain is one note and a rest is none, for every condition and for the number in the status line. The pitch fields offer the notes from the lowest to the highest pitch the score has, and the length fields the lengths its notes have; both keep a value that was chosen before the score changed. In the Count row each number keeps the words around it on one line, so a line breaks between the two numbers and not inside one.

**Behaviour.** Changing a field turns its condition on and selects at once, through `session.select`, so the panel always shows the conditions of the last selection it made; the checkbox turns a condition on or off and keeps its values. Opening the panel selects nothing; with no condition on, the panel selects nothing and says "Pick a condition to select notes." Invert takes the pitched notes the other conditions do not take (alone it takes none; after conditions that take nothing it takes every note). Re-apply selects again from the conditions held, against the score as it is now. Done closes the panel, and so do Escape (which returns the focus to the button) and a press outside it, the native popover's light dismiss. A selection made here is not a history step. The conditions live as long as the part does, so closing and opening the panel shows them again. A number typed into a field is taken when the field is left or Enter is pressed, as a browser sends its change.

**Status line.** One polite live region (`role="status"`) in the footer: "5 of 9 notes selected" (a tie chain counted once; the total is the pitched notes of the score); "No note matches these conditions. Nothing is selected."; the same with the reason when a condition that is on cannot match any note and the result is no note ("No note matches: a range has its ends the wrong way round, or a number is not valid. Nothing is selected."); the idle sentence; or, when the score text or the selection is no longer what the panel made, "The score or the selection has changed since. Re-apply to select again." The reason is shown only when the result is no note: under Invert the complement is every note, so "9 of 9 notes selected" is the correct result. The stale state also has a 3px rule at the start of the line, the one the stale notice has, so it does not rest on words alone. Re-apply is never disabled; the line is the only place that says the selection is out of date. Numbers use lining, tabular numerals, as every changing number does.

**Read-only.** The part works while the session is read-only, and it is hidden only while the score does not read or another view than the arrangement is shown (an open panel closes then). In read-only the arrangement draws no selection frame (see Read-only badge), so the status line is the only sign of what was selected, and it says so: "5 of 9 notes selected. This view is read-only, so the notes are not framed." That is the rule, not a gap: the frame is the mark of the selection an edit would act on, and a read-only view draws no editing mark; the count is the read-only sign of the selection.

**Place and size.** On the desktop the panel hangs under its button, over it when there is no room below, as high as the window allows when there is room nowhere (the popover rule's `max-height` makes it scroll inside), and is nudged left when it would leave the window. Between the rows is 6px (8px coarse). The footer is sticky at the bottom edge, with a hairline above it, so the count and the buttons stay in view when the rows scroll in a short window. On a phone (a coarse pointer and a window at most 640px wide) the panel is a sheet from the bottom edge, full width, at most 75% of the window's height, with the same two columns as the desktop, so on a 915px screen it covers a little over half and leaves the roll in view above it. These bounds fit the panel to the window; they do not limit what it selects. The fields are 28px high (40px coarse, with text of at least 16px so a phone does not zoom the page when one is focused, and the buttons the same height), and every colour, the hairlines and the radius come from the variable contract; the only accent is the focus ring. The toolbar title keeps at least 2em of its text in a toolbar that holds the Filter button; in a bare toolbar (one with neither the preview control nor the view switch), which scrolls sideways rather than wraps, the extra control would otherwise take the title's last pixel. In a bare toolbar at a phone's width the Filter button is past the right edge until the row is scrolled; the default editor wraps its toolbar and shows it (a host that mounts the bare toolbar can mount `mountFilterPanel` on a row of its own).

**Limits.** The panel adds no cap on how many notes can be selected, clamps no number the person types, sets no `min` or `max` attribute on a field, refuses nothing and has no disabled control. A range whose ends are crossed, and a count whose Every is missing, below 1 or not whole, or whose given Skip is below 0 or not whole, take no note, and the status line says why. A cleared Skip means 0, the filter's documented default. A bar below 1 leaves that end of the range open; a bar past the last bar is the end of the score at the start of a range and an open end at its finish.

**Verified and not.** Seam 1 (`tests/filter-notes.test.ts`) covers the filter on hand-written scores; seam 5 (`e2e/filter-select.spec.ts`) covers each condition, combining, Invert, Re-apply, closing and opening, read-only, the views, the language, keys, the panel's place and size and the status line, on the desktop and phone projects. Screenshots of every state were taken in Chromium at 1280x720 and in the Pixel 7 emulation. Not checked: a real phone's zoom on focus (the 16px rule follows the browser's documented behaviour and was measured only as computed size), a screen reader's reading of the panel, a browser other than Chromium, and the panel inside a host's own modal.

### Section menu

While the session is editable each section band is a button laid over the whole band, so a press anywhere on it opens the menu and the pinned name keeps its place. A chevron follows the name (the 5px mark of the zoom value and the Select button); hover tints the band by 6% of text, only where a pointer hovers, the open state by 10%, and keyboard focus draws the 2px accent outline inside the band, because a ring outside it would be hidden by the rows around it. A read-only session draws the band as before: no button, no chevron, no menu, no key.

**Menu.** The popover menu of the zoom control and the Select menu (`popover-menu.ts`), hung under the start of the band's pinned name, since the band's own start may be scrolled away. It is as wide as its text, so a menu near the right edge is not squeezed, and is then nudged into the window. Choices in three groups: Rename (the unnamed opening says "Name this section") and "Start a section at a bar"; Move earlier, Move later and Duplicate; Delete section. The three that ask for text end in an ellipsis. Delete comes last, because the first choice takes the focus and Enter on a destructive first choice is the wrong default, and it says "section", because the toolbar's Delete only turns notes into rests. The choices are made when the menu first opens, so a band holds two nodes until it is pressed.

**A choice that cannot be done.** A choice the commands would refuse is `aria-disabled` and muted. Their words are its `aria-description`, and for the eye they stand once, under the last of a run of muted choices that are refused in the same words, aligned with the labels: a note under each choice said one sentence three times in the unnamed section's menu. The words are not written here. The menu dry-runs each command (`sectionActions`), so a rule that changes in the commands changes the menu, and the menu adds no refusal of its own. Pressing a muted choice does nothing and leaves the menu open, so the words can be read on a touch screen, where there is no tooltip, and it says them in the live region.

**Form.** Rename, Name this section and Start a section at a bar ask for text in a popover (`role="dialog"`) under the band, not a modal: the task needs neither interruption nor protected focus. A line of context comes first (which bars the section covers), then the Bar field (Start only) and the Name field, then Cancel and a confirm in 600 weight that names the act ("Rename", "Name", "Start section"). Enter submits; Escape, Cancel and a press outside close it and give the focus back to the band. The bar offered is inside the section and does not start it: the insertion point's bar when it is such a bar, else the section's second bar. The field takes any number, and says under itself, before the form is sent, when the bar starts a section and so renames it. A refusal after a submit shows under the field it is about (`role="alert"`); that field takes `aria-invalid` and a 2px text-colour border, so it is a shape and not a colour, and takes the focus; the refusal also goes to `onRefused`. The form sends what was typed, and the commands alone decide what a bar or a name may be.

**Keys.** Bands are not tab stops: the Tab order of the arrangement is pinned, with one tab stop among the notes. Shift and F10, or the Menu key, on the ruler or the arrangement opens the menu of the section at the insertion point (the first section when there is none); Left, Right, Home and End walk the bands; Enter or Space opens the one in focus; a right click opens it too. After a choice the focus goes to the band of the section acted on (the copy, the moved section, the new section, or the one that took a deleted section's place) and the view scrolls to it, and a polite live region says what was done.

**Touch.** Menu items are 40px and the form's fields 36px with type of at least 16px (below that a phone zooms the page when a field takes the focus, as the text view's box notes). The row of bands is 25px and the control reaches 12px up into the row of bar numbers, so the target is at least 37px, as the rule for controls asks, without taking height from a phone's frame. Where a visible bar number sits over that reach, the number is the handle and takes the press; the band's reach covers the rest of its width. A 36px row did take the phone's height: in the multi-select spec the finger-drawn selection box no longer found empty lane to start on. Nothing reaches down into the marks row.

**Considered and not built.** Bar numbers as buttons (about 235 of them on a real song, thinned out at low zoom, and no path for a keyboard); the insertion point alone as the way to name a bar (it is hidden state, and a tick and not a bar); a modal dialog.


### Lyric track

A view part of its own (`mountLyricTrack`) on the same time axis, zoom and scroll as the other tracks; in the default editor it is the bottom track, under `Ins`, mounted with the voice tracks and replaced with them. It draws the project's lyric lines from `session.project` (the lines the project stores, or the layout computed from its `lyrics` text), classified against the score: a line whose phrase no longer fits the score is read as not on bars.

**Head and lane.** The head is the voice tracks' head, pinned under the header block, with the name "Lyrics", the New line button and a muted legend, "syllables / note starts", that says what the two numbers of a block are (a screen has no tooltip; the block's name says it in words for a screen reader, so the legend is hidden from it); the three stay at the pitch column's edge while the lane is scrolled past them. The button is as high as the head leaves it (the head is 1.7em, so the button is 4px shorter); on a coarse pointer it is 36px and the head grows to it with 2px above and below. The lane is a phrase row (2.3em, 3em on a coarse pointer) over a syllable row (1.6em). A song with no lines shows one muted sentence, "No lyrics in this song", pinned at the left on the lane's ground (the grid is under it, so the sentence has the ground colour behind it).

**A phrase.** A block over the bars of its line, 2px short of the last bar line, with a 1px line and the corner radius of a note (3px at most). It holds the count, "syllables / note starts" in 600 weight with tabular numerals, then the text of the line. The state is told three ways: the hue (`--sce-color-equal` or `--sce-color-unequal`, see [The two state hues](#the-two-state-hues)), the line (solid when equal, broken when they differ) and the words in the accessible name ("Line 2, bars 3 to 4, 7 syllables and 8 note starts, they differ: ..."; "equal" when they match). A chosen block has the selection frame, 2px in the text colour, drawn inside the block's own line (an inset shadow), so a chosen block whose counts differ keeps its broken line; where the system forces its colours the frame is the border, in `Highlight`. The focus ring is the accent. The count and the text stay at the pitch column's edge while the block is scrolled past it, as a chord's name does, and never leave the block's stretch. The count is left out whole when the block is too narrow for it, and never cut; the text is cut with an ellipsis, the one place the package does so inside a track (a lyric line is a sentence, so a cut one cannot be read as another line, the whole text is in the block's name and in the editor, and leaving it out whole would leave the narrow blocks of a zoomed-out song empty).

**Syllables.** When the two counts are equal, each syllable stands at the start of its note, in a cell that runs to the next note's start, with a 1px strong line at its left. When they differ, the cells are the note starts alone, with a broken line, so the person sees against the text which notes have no syllable. A syllable that does not fit its cell is left out whole (the same strut as the chord track's), so a zoomed-out song shows the ticks of the notes and no cut glyphs. The row is hidden from assistive technology: the text is in the block's name.

**The panel under the lane.** The list "Not aligned" (the spec's name for the lines that are not on bars) with its count and one muted sentence that says how a line gets onto bars, the editor of the chosen line, and the field for a new line. It stays at the pitch column's edge while the lane scrolls, is as wide as 36em or as the surface the track scrolls in (the part keeps `--sce-_view` at that width, with a ResizeObserver), whichever is narrower, so it never needs a scroll of its own, and is hidden while no line is loose, none is chosen and none is being added, so a song with every line on bars costs the track no room. An item of the list is a text button with a grip at its left (whole dots of the muted colour, a tile of 8px with 2px round it, with the line's name as its tooltip); a chosen item has the 2px frame, and the editor of a loose line opens inside that frame under the row, so the row does not move; the editor of a line on bars, and of a new line, sits above the heading. The editor starts with the name of its line ("Line 2"), in 600 weight, since its buttons say "next" and "delete" of something.

**Editing.** Every action below is one command, or one list of commands applied as one step (`session.dispatchAll`), so one undo takes it back; a refusal changes nothing and is said as the other parts say it, in the live region and through `onRefused`, in the editor's language. None of it exists while `session.view.editable` is false, and the read-only track shows the blocks, the counts, the syllables and the list, with no handle, grip, field or key.

| The person | What happens |
| --- | --- |
| Clicks or taps a phrase or an item of the list | Chooses the line and opens its text in the editor in the panel. |
| Types, then Enter or leaves the box | `setLyricLineText`, only when the text changed; Escape gives the typed text up. A refused text stays in the box, which is marked `aria-invalid` (2px line in the text colour) and described by one sentence under it, the diagnostic in the editor's language; both go when the text is changed. The part's live region says it once. |
| Presses Split at cursor, Merge with next, Delete line | `splitLyricLine` at the caret (with the bar the caret's note is in when the line is on bars and the counts are equal, in proportion to the syllables when not; no bar for a one-bar phrase), `mergeLyricLines`, `deleteLyricLine`. Split does nothing while the box holds text the project has not taken. |
| Presses New line, types, presses Add or Enter | `insertLyricLine` at the end of the list, without a phrase: the line starts in the unaligned list and is chosen. |
| Presses on a phrase handle and drags | Moves that edge to the nearest bar line, one bar at least, inside the line's section and clear of the other lines; a line that shares the edge gives up its bars first, and both `setLyricLinePhrase` commands go as one step. A guide line shows where it will land; Escape, a cancelled pointer, a lost capture or a window blur give the drag up. |
| Presses on a grip and drags onto the lane | `setLyricLinePhrase` with a one-bar phrase on the bar under the pointer, drawn as a mark while the pointer is over the lane; a bar that already has a line is drawn with a broken muted outline and refused. Letting go away from the lane sends nothing. |
| Types a bar number in the editor of a loose line and presses Place on bar | The same one-bar phrase, with no drag. |
| Tab, Left and Right, Home and End, Enter or Space, Delete or Backspace, Escape | The phrases are one tab stop; the arrows step to the neighbouring line and choose it; Enter or Space moves to the editor; Delete or Backspace removes the line; Escape drops the choice. The handle of a chosen line is a slider (the stop of that line only), moved one bar by Left and Right, and as far as it may go by Home and End. |

**Gesture choices, and what they rest on.**

- *Only a handle and a grip start a gesture, and only they stop the browser's panning.* `touch-action` is fixed when a finger goes down, and a stream the browser takes for a pan ends in `pointercancel` (W3C Pointer Events Level 3, 4.1.3.3 and 4.2.7; read from the start of the page to character 100000 of 248345). A throwaway probe, not kept in the repo (Chromium with Pixel 7 emulation, touch events sent through the DevTools protocol; WebKit and Gecko were not run), put a finger on a 44px square with `touch-action: none` inside a scroller that pans: ten `pointermove`, one `pointerup`, no `pointercancel`, the scroller did not move. The same square without it got two moves and a `pointercancel`, and a swipe on the empty lane scrolled it by 185px. Seam 5 repeats the swipe cases on a touch screen. So no long press is needed, unlike the selection box of a voice track (see Selecting several notes): the two gestures are told apart by where the finger lands, and the handle is a fingertip wide (44px by 44px) on a coarse pointer, centred on the edge.
- *The handle is a slider.* `role="slider"` with `aria-valuenow`, `aria-valuemin`, `aria-valuemax` and `aria-valuetext` ("bar 5"), a label that names the edge and the line, Left and Right as the step, and Home and End as the first and the last allowed value (W3C ARIA Authoring Practices, slider pattern; Up and Down are not used, because the axis is horizontal). A sentence of the keys, hidden from the eye, is the description of the list of phrases while the track can edit. Only the chosen line's handles are in the tab order, so Tab does not walk twice as many stops as there are lines.
- *A drop gives the line one bar.* The bar under the pointer, and nothing the pointer has not shown: the person widens it with the handles. A drop on a taken bar is refused by the model, which names the line that holds it, so the refusal is the same sentence whatever opened it.
- *A line is placed without a drag by its bar number.* WCAG 2.2 success criterion 2.5.7 (Dragging Movements, AA) asks that what a drag does can also be done by a single pointer without dragging, and says a keyboard alone does not satisfy it unless the keyboard operation also has controls that can be clicked or tapped (W3C Understanding SC 2.5.7). Placing a loose line meets it with the number field and the Place on bar button. **Moving the edge of a phrase has only the drag and the slider's keys; it does not meet 2.5.7 yet.** Home and End on a handle move the edge as far as it may go.
- *The text is edited in the panel under the lane, not on the block.* A loose line has no block, so one editor serves both kinds of line; a block can be 40px wide in a zoomed-out song and cannot hold a field with its caret; and on a phone the field (16px type, see [Typography](#typography)) and its buttons need the width the panel has, which stays at the pitch column's edge at any scroll.
- *The click that ends a drag is swallowed*, so letting go over a block does not also choose it; a press that moves less than 4px is a click.
- *The handles are always there, not only on the chosen line.* A 44px square at every edge covers part of each block on a phone (a quarter of a one-bar phrase at 100%, more than half at a zoom that fits the song), and a swipe that starts on it is a drag, not a scroll. Making the handles live only on the chosen line would stop that at the price of a tap before every edge drag. It was not done: dragging a phrase's boundary is the point of the handle, a person who aims at an edge should not have to choose first, and an edge drag by mistake is one undo. A swipe that starts on the body of a block, in the syllable row or on empty space scrolls.
- *No autoscroll while a drag is on.* A drag reaches the bars that are in view; the person zooms out first (the zoom control's Fit whole song puts a whole song in reach).

### Draft opening

While a draft keeper is reading the host's store (the `drafts` option of `mount`), the editor shows the original and does not let an edit start. The toolbar says so in the place the read-only badge takes: the same pill, with the words "Opening draft…" ("正在打开草稿…"), and the same absence of editing controls, selection, insertion point and live announcements, because the session is not editable until the keeper is ready. It is one state and one mechanism with read-only, so nothing in the view needs a second look for it, and a person who sees the badge for a moment and then the controls understands that the editor was waiting and not broken. There is no spinner and no motion (see Motion). A store that never answers leaves the badge up; the package does not time out, since how long a read may take is the host's to decide.

### Restore original

A text button in the toolbar after the Select button, labelled "Restore original" ("恢复原谱"), with the Select button's make: ground fill, 1px strong line, 4px radius, 28px high (36px coarse). It is there only while a draft keeper is ready or in conflict and the editor is editable, so a read-only editor and one without a store never show it. It is not muted for lack of edits: a person who is unsure whether a draft exists should still be able to get back to the original, and the question below says what will be lost.

Pressing it opens a question in a native popover (`popover="auto"`, the zoom menu's mechanics shared in `popover-menu.ts`, so it stacks above a host's full-screen layer and light dismiss and Escape close it), under the button and nudged into the window. Surface fill, 1px strong line, 12px padding, 22em wide and never wider than the window less 16px. A question in 600 weight, "Go back to the original score?", then one sentence of what it costs, "Every change you made is discarded and the saved draft is deleted. You can't undo this.", then the two answers at the end of the row, Cancel and "Restore original". The answer that does it is last and heavier; there is no danger colour in the theme contract and none is added, so the destructive word is on the button and the cost is in the sentence. The focus starts on Cancel, so Enter pressed by habit changes nothing. The popover is a dialog with the question as its name and the cost as its description. Confirming calls the keeper's `restoreOriginal()` and, once the store has answered, has the toolbar's live region say "The original score is back". When the removal was refused it says "The original score is back, but the saved draft could not be deleted. The next change tries again.", and the host has had `draft-save-failed`. It is asked once and is not asked again by anything else the editor does.

### Draft conflict strip

When another window wrote the draft first, a strip stands between the toolbar and the views (a part of its own, `mountDraftConflict`; the default editor mounts it after the toolbar). It is the notice strip's make (1px line under it), with the line in the strong line colour and the sentence in 600 weight where the cut notice is plain, so it reads as a decision still open and not as information. The sentence: "This draft was changed somewhere else after you opened it. Your changes are not being saved until you choose." Under it two buttons side by side, each of two lines: what it is ("Overwrite with my version", "Load the other version") and under it, muted at 0.92em, what it does ("The other version is replaced by yours.", "It opens here, and your changes in this window are dropped."). The cost is inside the thing that is pressed, so there is no second question; each button is the word and its consequence. The two buttons sit in a row with a 24px gap where there is room and one above the other where there is not, with no breakpoint (the row wraps; each button takes the width of its longer line). The second line is the button's description for a screen reader and is hidden from the accessible name, so it is not read twice. While a choice is being answered by the store both buttons are `aria-disabled`.

The strip never takes the focus and the editor keeps editing under it: a person in the middle of a note is told and not interrupted. The sentence is an `alert`, so a screen reader says it once when the strip appears. Restore original stays available. The failed-save and stale-source messages are not drawn by the editor at all; they reach the host's `notify`.

**What was measured.** In Chromium at 1280px and on a 412px phone profile, light and dark: the second line of a conflict choice on its button reads at 5.64:1 (light) and 6.94:1 (dark), the sentence on the strip at 15.98:1 and 12.82:1; a conflict choice is 43px high and 225px wide in English; Restore original is 28px high (36px on the phone); the question is 286px wide and inside the window at both widths, with the focus on Cancel; the keyboard ring is the 2px accent outline on the choices. The strip and the question were also looked at in Chinese and at a 320px width, where the two choices stack. Not verified: Safari and Firefox, and a screen reader's actual speech (the names, descriptions and alert are read from the accessibility tree).

### Change log and handoff

A word button **Regenerate…** ("重新生成…") in the toolbar after the Select and Grid buttons and before Restore original, with the other word buttons' make: ground fill, 1px strong line, 4px radius, 28px high (36px coarse). It is there only while the editor is editable and the host gave `onHandoff`; without either it is absent, not muted. It adds no row of its own, only one word button's width in the wrapping row; with the current controls that width takes one more row at 320px in English and, on a fine pointer, at 412px in English; the measured heights are in the package README. The default editor mounts it in the toolbar row but it is a part of its own, so a host that mounts `mountToolbar` alone gets no handoff. While a save is pending it reads **Saving…** ("保存中…") with `aria-busy="true"` and does not open the review.

Pressing it opens a native popover (`popover="auto"`, the Restore original mechanics) under the button, kept inside the window and bounded by the room below the trigger, 26em wide and never wider than the window less 16px. Inside: the heading **Check before regenerating** ("重新生成前核对") at the Title step in 600 weight; then the change log under the label **Changes** ("改动记录"), a list of one-sentence changes, or the sentence **No changes from the original.** ("和原版相比没有改动。"); then, only while the text view holds text the project did not take, the muted sentence that the last readable score is handed off; then the actions at the end, Cancel and **Regenerate with this version** ("用这版重新生成") last and heavier. In a short window the list scrolls inside the popover, so the actions stay reachable. The focus starts on Cancel, so a stray Enter does not hand off; Tab out of the review closes it, Shift+Tab reaches the trigger, and Escape returns the focus to it. The list is recomputed from the original and the current project each time the popover opens, so a stored draft never supplies it; it is not shown anywhere else. The dialog is described by the list when there are changes and by the empty sentence when there are none, one at a time.

The change log is a real list: no flex on the list itself, items spaced by a margin, long words wrapped anywhere, lining figures, and a hidden empty list. The change log uses no colour and no state hue: a change is a sentence, and the action's weight is its only emphasis. The trigger, list and note are ordinary text in the host's colours. The handoff control adds no notices and no source label; those are the host's.

## Do's and Don'ts

### Do:

- **Do** take every colour from the theme variable contract or a `color-mix` of bg and text; add a new public variable only when a host cannot be served by derivation.
- **Do** keep the neutral defaults described as defaults, and keep hosts' mapping optional: mapping only bg and text must stay readable.
- **Do** size type with `small` at the root and `em` below, size header rows and pinned heads in `em`, and use tabular lining numerals for any number.
- **Do** give every new interactive element a 2px accent outline with 2px offset on `:focus-visible` (inside the edge where its container would clip it), and a coarse-pointer size of 36px or larger for a control a finger presses; a keyboard-only stop is as high as its row, as the chord cursor is 2em. The section band's control draws the 2px accent outline inside the band, because an outside ring is hidden by the rows around it; its target is the 25px row plus the 12px it reaches above, at least 37px (see the Section menu Touch paragraph).
- **Do** say a state with a shape or words as well as colour, as the cut (hatch, dashed edge, a sentence) and the tie (one joined bar) do.
- **Do** leave out text that does not fit its cell, whole, instead of cutting it; thin numbers out rather than crowd them.
- **Do** place anything on the time axis in percent of its axis element, and change the zoom only by setting those elements' widths.
- **Do** gate every control and gesture that edits on the session's `view.editable`, in every part, so one flag turns the editing on and off everywhere.
- **Do** let a gesture act on the arrangement only while the arrangement is shown: clicks, Delete and the insertion keys do nothing on a hidden view, and a plus or a minus typed into the score text is text and not a zoom.
- **Do** draw a third party's SVG in a shadow root of its own, coloured by `currentColor`.
- **Do** keep a swipe on empty lane a scroll: a gesture that needs a drag there starts with a hold, and the lane's `touch-action` stays `pan-x pan-y pinch-zoom`.
- **Do** build an icon from polylines or other attribute-geometry shapes in an inline SVG; a path's `d` is reverted by the reset.
- **Do** put any new floating layer in a native popover so it reaches the top layer.
- **Do** prefix every class with `sce-`, inject styles once per container, and release them on destroy.
- **Do** start sound only inside a user gesture, say wherever it is offered that it is a synthetic preview, and stop it when its owner goes.

### Don't:

- **Don't** state a brand: no fixed brand colour, no bundled font, no logo.
- **Don't** hard-code `px` or `rem` font sizes (but for the one exception in The Keyword Size Rule), or a font family other than through `--sce-font-family`. The one exception is a form field's `max(16px, 1em)` on a coarse pointer, because below 16px a phone zooms the page when the field takes the focus.
- **Don't** add shadows at rest. A shadow marks a floating thing.
- **Don't** add decoration or motion, and don't tint a selection or the insertion point with the accent: they are the text colour, so shape and weight carry them.
- **Don't** hold the zoom, or anything else that changes while the user zooms or scrolls, in an inherited custom property on the root.
- **Don't** rely on a host's cascade. Style isolation is a constraint on all future work: the root resets everything (`all: initial`), descendants revert (`all: revert`) under a doubled `.sce-root.sce-root` selector so a host rule such as `.page div` does not reach in, and component rules are written under `.sce-root`. Notes are the one exception: they reset only the few properties they need by hand, because reverting every note made first render about three times slower. A new note-like element that is created in the thousands must follow the notes, not the rest.
- **Don't** publish or depend on `--sce-_*` variables outside the stylesheet.
- **Don't** import styles as a CSS file or leave anything behind: the stylesheet is a string, delivered as a constructed stylesheet (a style element only where that is unavailable, since a strict style policy blocks injected style elements) into the document or the host's shadow root, and removed with the last editor.
- **Don't** draw the playhead with a transition, an accent or a flag, or keep its position in the session's view state; it is a readout of the audio clock.
- **Don't** count on isolation against ID selectors or `!important` rules in the host's page when the editor sits in the page itself: they reach in. A host with such rules mounts the editor inside a shadow root.
